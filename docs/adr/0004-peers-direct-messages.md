# ADR 0004: Peers P5, two workbenches send each other typed messages directly

Date: 2026-11-22. Status: accepted. The build is #154 (P5). The plan requires this record and a threat review before any P5 code (Milestone 6, P5). The threat review is "Peers: direct messages between paired workbenches (P5)" in `docs/security/threat-model.md`, boundary B16.

Context: `docs/product/peers-concept.md` (rules that must hold), findings 5, 6 and 7 of `docs/reviews/design-vs-paperclip.md`. Approaches below are borrowed from Rakazo and Paperclip as described there and in the task that asked for this record. Their source is not in this repository's copy (`.reference/` is absent here), so no file of theirs was re-read for this record and nothing is copied from them.

## Decision

1. **Transport: Botbench to Botbench over a network the owners already have.** Each Botbench may open a second listener, the peer listener, separate from the owner's API. It is off by default and listens only on the address and port the owner writes in the settings file (`peers.listen`). Botbench refuses to start if that address is public: only loopback, a private range (RFC 1918, RFC 4193) or the carrier-grade range (100.64.0.0/10) that private overlay networks use is accepted. For two people, the address is on a private network that can share one machine with another person's account. For the first slice, both installations are on one Mac, on loopback. The listener has four routes and nothing else: pair, message, settings, end. It never takes the owner's session cookie, and no owner route is reachable through it. Botbench runs no service of its own: no relay, no directory, no account.
2. **Identity and signing.** At its first pairing, each workbench makes one Ed25519 key pair with `node:crypto`. The private key is kept in the data folder (file mode 0600), never leaves the Mac and is never shown. A workbench's identity is its public key. Its name (P1) is only a label. Both screens show a short fingerprint of each key, and the two owners compare it once. Every message, including a refusal, a settings notice and an end, is signed over a fixed byte form of the whole envelope: pairing id, kind, message id, thread, parent, repository, sender and recipient keys, sequence number, time and body. The receiving side checks the signature against the key it stored at pairing, before it reads anything else.
3. **Pairing: an invite with a pairing key that is safe to retry.** Owner A chooses Invite in Settings. Botbench makes an invite holding A's listener address, A's key fingerprint, the repository and a 32-byte one-time secret. A keeps the secret in its store (the data folder, owner-only) only while the invite is open. It is erased when the invite is used, expires or is withdrawn, and it is never shown again or logged. The invite is used once and expires after 15 minutes. A passes it to B outside Botbench. B's owner pastes it and sees A's name, fingerprint and repository, then confirms. B's Botbench makes a random pairing key and sends the pair request: B's public key, name and address, the pairing key, and an HMAC of the request made with the invite secret, so the secret itself never crosses the network. A recomputes the HMAC with the secret it kept and compares the two in constant time. A's answer carries A's public key, B's pairing key and a new pairing id, signed with A's key. B accepts it only when that key's fingerprint is the one in the invite, so a listener that answers in A's place is refused. B sending the same pairing key again with the same content gets the same answer, so a retry after a dropped connection makes no second pairing. A different pairing key on a used invite is refused. A's owner then confirms B's fingerprint. B's owner confirmed A's fingerprint before the request was sent. The pairing is in force only once both owners have confirmed. A's confirm sends B a signed confirmation naming the pairing id, retried like any outgoing message until B acknowledges it. Until B holds that confirmation, B shows the pairing as "Waiting for bob to confirm" and sends no message. Each side refuses every message on a pairing it does not yet hold as confirmed by both owners. If A's owner refuses B's fingerprint, A sends a signed end instead. This is the approach of Rakazo's device pairing (`apps/desktop/src/main/auth/user-device.ts`, `packages/contracts/src/account/user-devices.ts`): a device is added through an invite, with a key the client chooses so the request can be retried.
4. **Ending a pairing.** Either owner chooses End pairing, behind the confirm "End pairing with bob? bob's workbench can no longer send you messages, and nothing more is sent to it. To work together again, one of you sends a new invite." Botbench writes an end row (append-only) and from then on refuses every message that names that pairing's id. Every envelope carries its pairing id, and a key counts only together with a pairing that is in force, so the same key can pair again through a new invite. It closes the peer's cards that are still waiting and drops any unsent messages to that peer. It then sends a signed end notice once, without waiting for an answer. The other side records the end the same way when the notice arrives. If the notice never arrives, every later message for the ended pairing gets a refusal with the reason `pairing_ended`. The refusal names the pairing id and the refused message id, and it is signed with the ending side's key. The other side checks that signature against the key it holds for that pairing, then records the end exactly as if the notice had arrived: the end row, its waiting cards closed and its unsent messages dropped. An unsigned refusal, or one signed with another key, changes nothing. An ended pairing is never started again: a new invite makes a new pairing, with a new id, which both owners confirm again.
5. **Scope: one pairing, one repository.** A pairing names one repository, identified by its delivery remote (`host/owner/name` on GitHub, or the remote's address as git reports it for a bare remote on the Mac). Each side must have that repository among its own. Every message names it, and a message for any other repository is refused. **Pairing gives a peer no access** to private files, credentials, the other machine's files, its tasks, transcripts, diffs, settings or the store. No route on the peer listener reads any of them. Code moves between the two only through branches and pull requests the owner chose (delivery, P3, P4).
6. **Message kinds and the cap on round trips.** There are eight kinds: question, answer (to a question), interface proposal, counter (to a proposal or a counter), accept (of a proposal or a counter), blocker (a statement of what this side is waiting on), review request, and verdict (to a review request). Each kind has a fixed shape: a plain-text body of at most 8,000 characters, and a parent of the right kind where one is needed. An interface proposal is text that describes a contract. Botbench never writes it into a file, runs it or applies it. A thread allows at most 3 round trips (`peers.roundTripsPerThread`, 1 to 10): 6 messages, 3 from each side. A seventh message is refused at both ends. A new thread needs an owner's own message or the owner's approval of the agent's draft, like any outgoing message.
7. **What is stored.** Messages are durable, idempotent and typed, scoped to one repository, in the store. They go in `peer_messages` (append-only, enforced by triggers): direction, kind, message id, thread, parent, repository, peer, sequence, body, signature, times. A message id appears once per peer (`UNIQUE(peer_id, message_id)`). The same id with the same bytes is answered with the same acknowledgement. The same id with other bytes is refused and logged. An outgoing message is written before it is sent and retried with back-off until the other side acknowledges it, the pairing ends, or 24 hours pass, after which it reads "Not delivered". This is the approach of Paperclip's case handoffs (`server/src/services/case-handoffs.ts`, `doc/case-handoffs.md`): a durable, idempotent record handed from one side to the next.
8. **What an incoming message may cause, and what it never causes.** An incoming message is outside text. It is never a command and never a grant, and it never starts, wakes or answers an agent by itself. It only becomes a card for the owner ("bob asks a question about api", with the Outside text badge), and the owner chooses one of: Answer it yourself, Give it to Claude Code (a new task or chat in that repository), or Dismiss. A run, task or chat the owner gives it to is marked as having read outside text, under the rules of the threat model's Intake (B14) section. The text goes in an `<outside-text>` block it cannot close, no allowed command or Always allow applies, the run cannot be fully autonomous, and no network hosts are allowed unless the owner ticks them. Nothing in a message is read by Botbench as an instruction, a path, a branch, a command or a setting. To keep cards readable, each peer may send at most 30 messages an hour and have at most 10 cards waiting. Past that a message is refused, with at most one action-log row a minute. A request on the peer listener is at most 64 KB.
9. **The outbound gate: the owner approves every message before it leaves.** The owner writes a message, or an agent drafts one. A draft is a fenced `botbench-peer-message` block in the agent's reply, parsed and checked like a plan. This needs no new tool or MCP server for the CLI (see ADR 0002). Each draft becomes a card, in manual and semi-autonomous runs and in a chat: "Send this to bob?", then "A question about api, from Claude Code in task 3.", the full text exactly as it will be sent, and "Only this text leaves this Mac, and only to bob's workbench. No files, branches or settings are sent." The buttons are Send and Don't send. In a fully autonomous run a draft is refused and logged, never sent. No message of the eight kinds leaves without the owner's Send, and the owner's own message is sent when they press Send. Five kinds of protocol traffic leave without a Send. Each has a fixed shape and carries no text from the owner, an agent or the repository, and each is in the action log:
    - the pair request and its answer, after the owner confirms the invite, and the inviter's confirmation, after its owner confirms the fingerprint;
    - acknowledgements, which carry the message id only;
    - refusals, which carry the message id and Botbench's fixed reason code;
    - settings notices, which carry this side's receive settings after the owner changed them;
    - the end notice, after the owner's End pairing.
10. **Finding 5: who asked, on every action and approval.** Every approval and every action-log row records who asked: the owner, this workbench's agent, or a named peer workbench (`asked_by` of `owner`, `agent` or `peer`; for `peer`, the pairing's id, and the peer's name and fingerprint as they were then). Work the owner gave a peer's message to carries that peer, fixed by trigger, onto every approval and row it causes. Its cards read "Asked by Claude Code, working on a message from bob's workbench". A verdict is accepted only as the answer to a review request this workbench sent to that same peer, in that thread, and is shown to whoever sent the request. A verdict from another peer, without a matching request, or a second verdict for one request is refused. This is the approach of Paperclip's review policy (`server/src/services/issue-review-policy.ts`): verdicts matched to who requested them, by actor type and id.
11. **Finding 6: each side can switch off kinds of requests, per peer.** For each peer and each kind, the owner sets whether it may be sent and whether it may be received. All are on at pairing, and the pairing screen shows them for the owner to change. Each side tells the other its receive settings in a signed settings message, at pairing and on every change. A message goes only if both allow it, checked twice. The sending end checks its own send setting and the peer's last receive settings before making a card. It checks both again at every send attempt, the first and each retry, after the owner's Send. A message whose kind has been switched off by then is not sent. It reads "Not sent: switched off" and is logged as `peer_kind_refused`. The receiving end checks its own receive setting before anything is stored, and its check decides. An explicit no is never overridden by a mode, an allowed command, Always allow, the other side's settings, an agent's reply or a message. Only the owner changes it, in Settings. A refused kind creates no card, stores no body, and leaves one action-log row naming the peer and the kind (`peer_kind_refused`). The sender gets a signed refusal. This is the approach of Paperclip's agent interaction permissions (`server/src/services/agent-interaction-permissions.ts`, `server/src/lib/agent-interaction-permissions.ts`, `packages/shared/src/agent-interaction-permissions.ts`, `doc/agent-interaction-permissions.md`): a sending and a receiving setting, both of which must allow, and a no that no role overrides.
12. **Finding 7: a small cap per run on what an agent sends.** A run may send at most 5 agent-drafted messages to peers (`peers.messagesPerRun`, 0 to 50; a chat counts as one run). Every draft is logged first (`peer_send_attempt`) and counted, including drafts later refused for another reason. Over the cap a draft is refused without a card, logged under its own rule (`peer_send_over_limit`, never `owner_declined`), and the agent is told in its next prompt: "Botbench did not send this: this run may send at most 5 messages to other workbenches, and it has used them." The owner's own messages do not count. This is the approach of Paperclip's cross-issue limit (`server/src/services/cross-issue-influence-limit.ts`): log every attempt, then refuse past a fixed count per run.
13. **The first slice.** It must be provable end to end with two installations on one Mac: two Botbench processes, each with its own data folder, owner port and peer listener on 127.0.0.1, and one temporary git repository with a bare remote both use. It does this:
    - invite, pair (including a retried pair request that makes one pairing), and compare fingerprints;
    - question and answer only, written by the owner or drafted by an agent in a manual or semi-autonomous task;
    - every control above: the outbound card, the incoming card with Outside text, who asked, per-kind settings on both ends, the cap per run, the cap per thread, idempotent delivery and retry, End pairing.

    The first slice will NOT do:
    - no relay and no Botbench service;
    - no remote execution: a message never runs anything on either Mac;
    - no transfer of code or files: no patches, attachments or file contents as such, only text the owner approved;
    - no A2A, and no protocol meant for other products;
    - no more than two peers: one pairing per installation;
    - no test across two Macs or a real private network;
    - no message kinds beyond question and answer (proposals, counters, accepts, blockers, review requests and verdicts follow, each with its own tests);
    - no messages from a fully autonomous run;
    - no agent started or woken by an incoming message without the owner;
    - no notifications to the phone for peer cards;
    - no changes to P3 claims or P4 shared checks.

## Why

1. **Transport.** Local by default, and nothing leaves except what the owner chose: a direct connection carries only approved messages to the one paired peer. The private network gives two people a path without Botbench running anything. On one Mac the slice needs only loopback.
   Rejected:
   - A Botbench relay or service. It would hold every message on someone else's computer and would need accounts, which is the central control plane `design-vs-paperclip.md` rejects. It is a later question, as `peers-concept.md` says.
   - GitHub as the transport (issue comments, a message branch). It writes to GitHub where others can read it, mixes messages with project history and adds delay. It also breaks the rule that Botbench pushes only a task's own branch.
   - SSH or a shared folder. Either gives file access to the other machine, which the concept forbids.
   - A2A over the network. A real standard, but a prerequisite the first slice does not need, and it would widen the boundary before the controls are proven. It stays a possible interoperability boundary later.
2. **Identity.** A name can be chosen by anyone, and two Macs can share a host name (P1). A key cannot be copied, and a signature proves who sent each message and that it was not changed. That serves both owners, because each keeps the other's signed messages. Ed25519 is in `node:crypto`, so no dependency is added. The key is Botbench's own and is not a provider credential, so the hard rule on credentials is kept.
   Rejected:
   - Trusting the network's own identity. It differs per network and is absent on loopback.
   - TLS client certificates. They need a certificate authority or pinning, and signing covers what is stored.
   - A shared secret. It cannot tell the two sides apart.
3. **Pairing.** An invite passed outside Botbench means only someone the owner handed it to can pair. One use, a short life and erasing the secret afterwards limit what a leaked invite is worth, and the HMAC keeps the secret off the network. A stored hash alone cannot check an HMAC, so the secret is kept while the invite is open, in the data folder that already protects the login token. The signed answer checked against the invite's fingerprint authenticates the inviter to the side that joins. The pairing key makes a retry harmless. Confirmation by both owners and the fingerprint check stop an invite that was intercepted.
   Rejected:
   - Discovery on the local network. It is open to anyone on it.
   - Pairing by name alone. Names can be spoofed.
   - Pairing that is in force when one side confirms. The other owner would never have seen the key.
4. **Ending.** Each owner must be able to stop without the other's help. Refusing the pairing locally does that at once, and the notice is a courtesy. Re-pairing through a new invite keeps an old pairing from coming back by mistake.
   Rejected:
   - A soft pause that can be undone. It would be a second state with its own rules, for no use yet.
   - Blocking the key for good. A workbench keeps one key, so the two owners could not work together again unless one of them made a new key.
5. **One repository.** The concept scopes messages to one repository, and that is where the two owners' work meets. A message never carrying another repository's name keeps one pairing from becoming a general channel.
   Rejected:
   - One pairing for every repository both owners have. A message could then steer work in a repository the owner never paired for.
   - Naming the repository by its folder path. The two Macs' paths differ, and the shared remote is what both have.
6. **Kinds and round trips.** Typed messages keep Botbench from parsing free text for intent, and they make per-kind settings possible. The eight kinds are the ones `peers-concept.md` names: questions, interface contracts, status and review. Two agents can talk forever. Three round trips is enough to settle a question or a contract, and after that the owners decide.
   Rejected:
   - Free text with no kinds. Nothing could be switched off by kind.
   - No cap on round trips. Agents could loop.
7. **Storage.** Two machines lose connections. Writing before sending and deduplicating by id means a message arrives once, survives a restart and can be shown later. Append-only matches the action log and the events.
   Rejected:
   - Fire and forget. It loses messages.
   - Storing only on the sending side. The receiving owner would have no record.
8. **Incoming.** "An incoming message is never permission to run anything", and the concept requires the outside-text rule for messages. B14 already defines that rule and its tests, so P5 reuses it.
   Rejected: letting an agent read a peer's messages by itself. That would give the other workbench a voice inside this owner's agent without the owner.
9. **Outbound.** Anything that would leave asks first (hard rules), and a fully autonomous run refuses what would ask. The card shows the exact bytes, so the owner approves what is sent. A fenced block in the reply avoids a Botbench MCP server, which would need its own record.
   Rejected:
   - Sending the owner's grants or a mode's allowance as approval. Nothing that leaves is pre-approved.
   - A Botbench MCP tool for sending. It needs its own decision (ADR 0002) and is not needed yet.
10. **Who asked.** Today `action_log` has no principal and every decision is assumed to be the owner's (`docs/security/threat-model.md`, Repudiation). Once a peer can cause work, the owner must see whose request a card serves, and the log must keep it. Matching verdicts to requests stops a peer from issuing a verdict nobody asked for.
   Rejected:
   - Recording only `owner` or `agent`, with the peer kept in the message row alone. A card raised several steps later would no longer say whose request it serves.
   - Attribution as free text. It cannot be matched to a request or fixed by a trigger.
11. **Per-kind settings.** An owner may want questions from a colleague but no review requests. Checking at the receiving end is the one that counts, because the sending side may be a modified Botbench. Checking at the sending end saves the owner a card that would be refused anyway.
   Rejected:
   - One on-or-off setting per peer. It cannot keep questions while refusing review requests.
   - Checking only at the receiving end. The sending owner would approve cards that are then refused.
   - Letting a mode or Always allow switch a kind back on. The no would no longer be the owner's.
12. **Cap per run.** Two agents asking each other questions could fill both owners' screens with cards (finding 7). Logging before refusing keeps the evidence. A rule of its own keeps "Botbench refused" apart from "the owner said no".
   Rejected:
   - Relying on the owner's Send alone. Every draft is still a card, and a flood of cards is the harm.
   - A cap per hour. A long run would refill it, and the run is what the owner started.
   - Counting only drafts that were sent. An agent that keeps being refused would keep trying at no cost.
13. **First slice.** Two installations on one Mac use real processes, a real store and real git, and show every control without a second machine. Question and answer are enough to prove pairing, signing, storage, both gates, both caps, who asked and ending. The other kinds add shape checks, not new boundaries.
   Rejected:
   - All eight kinds at once. More to build before any control is proven.
   - Two Macs from the start. That needs a private network in the test, which the test suite cannot set up.

## Consequences

- A second listener is new attack surface (B16). It is off by default, bound only where the owner says, never public, and has four routes, each signed.
- A Botbench key exists in the data folder. Anyone who can read the data folder can act as this workbench to its peer. That is already true for the login token, and no confined command can read the folder (U27).
- Confidentiality on the wire comes from the network: the private network for two people, loopback on one Mac. Messages are signed, not encrypted. Encrypting each message is left until a relay is considered.
- `approvals` and `action_log` gain `asked_by` and a peer reference in one migration. Existing rows read as `owner`, which is true of every row before P5.
- The owner reads every outgoing message. A draft can still carry repository text or a secret that the agent read, and the card is the control, as for any approval.
- A peer's message, once given to an agent, can persuade it as an issue can. The B14 limits apply, and so does every card.
- Clock skew between Macs matters only for display and the 15-minute invite. Ordering uses the per-pairing sequence numbers.
- Each later kind, a second Mac, more than two peers, a relay or A2A needs its own tests, and the last two each need a new decision record and threat review.

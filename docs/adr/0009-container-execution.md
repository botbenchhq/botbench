# ADR 0009: Where a repository's commands run: on the host, or in one container per task

Date: 2026-11-23. Status: accepted (plan U28, ADR 0002 step 2).

## Decision
1. **A named seam with two kinds.** Each repository's settings may say `"execution": { "kind": "host" }` or `{ "kind": "container", "image": "node:24" }` beside `setup`, `checks` and `allowedHosts` (`src/execution.ts`, `src/config.ts`). "host" is the default and is U27's confinement, byte for byte: the agent's launch settings and the setup and check argv are held to a digest taken from the code before this change (`test/execution.test.ts`). An unknown kind, an unknown key, `image` on the host kind and a container with no image stop Botbench at start with a sentence naming the setting. Settings, under This workbench, shows each repository's kind ("On this Mac" or "In a container", with the image), read from the settings file and never written.
2. **Nothing falls back.** A repository set to "container" runs no command of a task on this Mac. When the container cannot be had, the task fails before its setup with why: no docker program, `docker info --format {{.ServerVersion}}` failing or not answering within 10 seconds, the image not on this Mac (it is never pulled), a refused mount, hosts allowed, a builder whose agent cannot have its commands rewritten (only Claude Code can; asked of the task's own builder, so a task built by Codex, which runs its own commands, is refused, and the Codex driver also refuses to start when handed a container), or a container that, once started, is not what was asked for.
3. **One container per task, started before setup.** `docker run -d --pull never`, named `botbench-<workbench>-<data>-task-<id>` (where `<data>` is the first eight hex digits of the SHA-256 of the data folder's real path, so two Botbench installations under one workbench name do not want the same container name for their task 7), labelled `botbench.workbench`, `botbench.task` and `botbench.mount` (the copy it holds), running `sleep infinity` from the owner's image, exec'd by `env -i` (`--entrypoint env <image> -i HOME=/tmp PATH=<minimal> sleep infinity`), so not even the first process has the image's `ENV` lines. Hardened: `--cap-drop ALL`, `--security-opt no-new-privileges`, `--pids-limit 1024`, `--memory 4g`, `--cpus 2`, `--ipc private`, `--cgroupns private`, `--network none`, `--user <owner uid>:<owner gid>`, and exactly one `--mount type=bind` of the task's copy, read-write, at the same absolute path as on this Mac, which is also the working folder. Its environment is `HOME=/tmp` and a minimal `PATH`: no variable of this Mac, no credential, no home folder, no sign-in folder, no Docker socket. Every command Botbench runs in it starts under `env -i HOME=/tmp PATH=<minimal>`, so the image's own `ENV` lines do not reach it either (the image must have `env`, as every image with `sh` does).
4. **The mount is checked before the start.** Refused: a path a mount spec cannot hold (a comma, a quote, a control character), the home folder or a folder that holds it, anything that is, holds or lies inside `~/.ssh`, `~/Library`, a vendor sign-in folder (moved ones included) or any other place on U27's unreadable list, Botbench's data folder or a folder that holds it, and anything but one task's copy in the data folder (`<data>/worktrees/<run>/<task>`). The copy itself lies inside the home folder and the data folder; it is the one place inside them that may be mounted.
5. **Proved after the start, not assumed, and addressed by id after.** Botbench reads the container's own record (`docker inspect --type container <name>`) and refuses one whose network is not `none`, that kept a capability, may gain privileges, is privileged, shares IPC or cgroup namespaces, has other process, memory or CPU limits than asked, runs another image (by name, and by the id `docker image inspect` gives for that name now, so a retagged name is not taken for the old image) or as another user, or has any mount but the copy itself (its source exactly the copy's path), read-write, at that path. The mount itself is the task's copy at its own real path: a copy reached through a symlink, or one that is gone, is refused before `docker run`, so the runtime is never asked to resolve a link into a mount. Seen in the shape OrbStack's and Docker's `inspect` give; a runtime that reports the source under another path is refused, not guessed at. It then looks from inside: `ls /sys/class/net` must list `lo` and nothing else. A container that fails either is removed again and the task does not start. The record carries the container's own id (a 64-hex-digit string); that id, not the name, is what every later `docker exec` (setup, checks, the rewritten agent command, the leftover sweep) and removal use, so a container made under the same name after this one was removed is never mistaken for it. A container found running after a restart is used again only when it passes the same checks, and is then addressed by the id that pass found.
6. **Setup and check commands** run as `docker exec --workdir <copy> <id> env -i HOME=/tmp PATH=<minimal> sh -c -- <command>`, argv with no shell on this Mac between, instead of `sandbox-exec`, with the same time limit, process group, tracking and evidence (`src/engine/stations.ts`). The `--` after `-c` means a command that begins with `-` is the script, never options of the container's `sh`. When one ends, however it ended, `kill -9 -1` in the container stops what it left running, as its process group is killed on this Mac.
7. **The agent's commands are rewritten in the permission answer.** In the container kind the builder's launch settings carry, as for the host kind, the bare `Bash` ask rule, no allow rule for Bash, and `autoAllowBashIfSandboxed: false`, so every shell call reaches Botbench's answer. The safety rules and the permission check judge the command as the agent asked it (`src/approvals/gate.ts`, `broker.ts`, unchanged). Only an allow is rewritten, in the driver's answer (`permissionAnswer` in `src/drivers/claude-code.ts`): `updatedInput.command` becomes `'<docker>' 'exec' '--workdir' '<copy>' '<id>' 'env' '-i' 'HOME=/tmp' 'PATH=<minimal>' 'sh' '-c' '--' '<original>'`, each word in single quotes (a `'` written `'\''`), checked by reading it back with a real `sh` for quotes, `$`, backticks, backslashes, heredocs and newlines. A refused or declined call is never rewritten. A shell call with no command to rewrite is refused. A question the agent asks the owner (`AskUserQuestion`) is answered exactly as on the host, before any of this: it runs nothing. File tools (Read, Edit, Write) run on this Mac, in the same copy the container mounts.
8. **How the rewritten command gets past the CLI's own sandbox**, which blocks the Docker socket: in the container kind, and only there, `sandbox.allowUnsandboxedCommands` is true, and Botbench's answer sets `dangerouslyDisableSandbox: true` on the one input it rewrote. It rebuilds that input from scratch: the rewritten command, and the call's `description`, `timeout` and `run_in_background`; every other field, the agent's own `dangerouslyDisableSandbox` among them, is dropped. So the only commands that run outside the CLI's sandbox are the exact `docker exec` lines Botbench wrote. Because `allowUnsandboxedCommands` is open in this kind, the answer also refuses — without asking — any allow whose tool is not `Bash` yet carries `dangerouslyDisableSandbox`, and any `Bash` call it cannot rewrite, so no other tool the CLI may expose can ride that one open setting out of the sandbox. `excludedCommands` was not used: it is a standing pattern the CLI matches by its own prefix rules, which Botbench cannot make exact to one container and one command. That is the one launch setting that differs between the kinds (asserted in `test/execution.test.ts`).
9. **Botbench still commits on the host.** The copy is the same folder on both sides of the mount, and the container runs as the owner's ids, so a file a command writes in the container is an ordinary file in the copy, committed to the task's branch with the same evidence as for the host kind.
10. **Removal.** The container is removed with `docker rm -f` once its task is no longer live: accepted, rejected or cancelled, or what it left discarded by the owner. A task that failed or was stopped keeps it, as it keeps its copy. One sweep owns removing (`src/engine/containers.ts`): at start, whenever a docker program is on this Mac (so a repository switched back to the host or taken out of the settings leaves nothing behind), every container carrying this workbench's label whose mount lies in this data folder and whose task is not live is removed; then, each time a task this process started a container for is announced, its container goes once the task is no longer live.
11. **Allowed hosts.** A repository that allows hosts is refused the container kind, at start in the settings file and again when a task starts. Proving that a container reaches only Botbench's host proxy would need a Docker network whose only route is that proxy and a probe that the route holds; neither is built, so it is not claimed, and the setting is refused.

## What was adapted, not copied
No file was copied (nothing is added to `NOTICE`).
- **OpenMausBot** `server/container-isolation.ts` (`dockerSecurityIsHardened`, `desktopCapArgs`) and `server/container-computer.ts`: the hardening flags (`--cap-drop ALL`, no new privileges, private IPC and cgroup namespaces, no auto-remove), reading the container's `HostConfig` back after the start and refusing one that does not match, the host user's ids for files written in a bind mount, and running the docker CLI in a process group of its own with a time limit. Botbench keeps no capability at all (OpenMausBot adds some for its desktop's supervisor) and runs no init script in the container.
- **rakazo** `infra/sandboxes/supervisor/src/egress-probe.ts`: a network restriction is probed from inside before work starts, and a probe that cannot finish counts as the restriction not holding. Botbench's probe is smaller because its claim is smaller: no network at all, so only loopback may be listed.
- **paperclip** `server/src/index.ts` (the orphan sandbox sweep): one sweep is the single owner of removing what is left, run at start and after committed changes, so a container is never left only because one removal path was missed.

## Limits
- **The CLI stays on the host** (ADR 0002, decision 3), under the owner's sign-in. Its file tools, its hook and the reviewer's commands run on this Mac: a review stays read-only and confined as U27 says. Only shell commands of the builder, and setup and check commands, run in the container. Checking together (P4) is not run for a repository whose commands run in a container: it would run them on this Mac, so it is recorded as Did not run, with why, and nothing runs instead.
- **No sign-in in the container.** Nothing of the owner's is passed in; a command that needs a registry token or a git credential has none.
- **git in the container.** A task's copy is a linked git worktree whose `.git` points at the repository's shared git folder on this Mac, which is not mounted: git inside the container does not work in the copy. Botbench's commit, on this Mac, is unchanged.
- **The image's own environment** (its `ENV` lines) stays in Docker's record of the container (`Config.Env`), as Docker has no flag to start from none; no process gets it, as the first one and every command Botbench runs are started with `env -i`.
- **Removing after a failed start** removes the container of the task's name only when its mount label is this copy, and removes it by the id that look found, so a container another process made under the same name meanwhile is left alone.
- **A command stopped on this Mac may run on in the container.** Killing `docker exec` does not stop the process it started. For setup and check commands Botbench runs `kill -9 -1` in the container after each; for an agent's command the CLI's own time limit stops the docker client only, and what it started runs until the container is removed. A restart that finds a check left running stops its docker client, not its process in the container.
- **The working folder of an agent's command** is the copy's top folder each time: a `cd` in one call does not carry to the next.
- **The image is the owner's choice and is trusted as code**: Botbench checks how the container is started, not what the image holds.
- **Docker on macOS runs a Linux VM** (Docker Desktop, OrbStack). The VM's own isolation, and the file sharing that makes the copy visible to it, are the runtime's, not Botbench's.
- **A renamed workbench** still finds its containers: the sweep lists every container carrying the `botbench.workbench` label, under any name, and removes only those whose mount lies in this data folder; a task change removes the container by the id this process recorded when it started or found it, not by name.
- **Measured here**: the run arguments, refusals, mount checks, quoting and permission answer, by fast tests. `test/live/container.live.test.ts` runs a real container and is skipped where Docker does not answer or `BOTBENCH_TEST_CONTAINER_IMAGE` is unset or not on this Mac (a builder's sandbox cannot reach the Docker socket, so it is skipped there). Measured on the owner's Mac on 2026-11-23 (Docker 29.8.2 through OrbStack, `alpine:3`, Claude Code on haiku): a command sees the copy and writes a file that lands on the task branch, cannot read a decoy outside the mount, and has only loopback; an image not on the Mac is refused and not pulled; and a real Claude Code builder's shell calls were each answered by Botbench's permission check, ran in the container (`uname -s` said Linux, `ls /sys/class/net` said `lo`, a decoy beside the repository was not there), the file one wrote was the task's one change, and the container was gone once the task was rejected.

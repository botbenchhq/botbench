# ADR 0010: Releases, and Botbench updating itself to a published release

Date: 2026-11-23. Status: proposed. Issue #116, part 3. The threat review is "Releases and updating Botbench itself" in `docs/security/threat-model.md`. (Number 0010: 0007 was never used and 0009 is the container ADR.)

Context: the owner wants Botbench to publish versioned releases like a product, and the installed Botbench (a git checkout of `main`, run by a launchd LaunchAgent) to run a new release with no person at the Mac. The repository is public, so a self-hosted Actions runner on the owner's Mac would let a stranger's pull request run code there. Every other person's Botbench will update the same way, so this is product, not only the owner's deploy.

## Decision

1. **Releases by release-please**, as jon-lange/settleview does (`.github/workflows/release.yml`, `release-please-config.json`, `.release-please-manifest.json`; the action pinned by commit hash, v5.0.0). It keeps one release pull request open from the Conventional Commits on `main`; merging it bumps `package.json` and `package-lock.json`, writes `CHANGELOG.md`, tags `vX.Y.Z` and publishes a GitHub Release with the changelog section as notes. Nothing is built or attached: an installation runs the tagged commit itself. Only `feat:`, `fix:` and `feat!:` commits (squash-merge titles) count toward a release.
2. **The release pull request's checks, with no secret.** A pull request made with `GITHUB_TOKEN` starts no `pull_request` run that can pass (GitHub creates it approval-required), so `main`'s required checks would never be met. `workflow_dispatch` is the event `GITHUB_TOKEN` may start ("workflow_dispatch and repository_dispatch events always create workflow runs", GitHub's GITHUB_TOKEN page). After release-please opens or updates the pull request, the Release workflow runs `gh workflow run ci.yml --ref <release-please's branch>`; that run's jobs report the required checks, by the same names and app, on the pull request's head commit. Rejected: a GitHub App (the owner creates an app and two secrets), a fine-grained personal token (a long-lived secret that acts as the owner), and waiving checks for the bot (a bypass on the ruleset).
3. **Updating is a pull from the installation, never a push to it** (`src/update.ts`). The check is one unauthenticated `GET api.github.com/repos/jon-lange/botbench/releases/latest` at start and every 6 hours (`BOTBENCH_UPDATES=off` turns it off). Settings shows "Update available: <version> — <summary of the notes>" and "Update now"; the owner chooses "On a tap" (the default) or "Automatically". Approach from OpenMausBot's `server/update-check.ts` (one cached check against `releases/latest`, semver compare that never offers what it cannot parse) and `deploy/update.sh` (prove the new version is healthy before keeping it; go back when it is not). No code was copied.
4. **What an update does, and refuses.** It waits until no task is queued, building, checking or being reviewed, no run is being planned and no chat is answering (an update interrupts nothing, so it relies on no turn being retried by restart recovery). The checkout must be clean and on `main`. It fetches `main` and the tag from `https://github.com/jon-lange/botbench.git` with no credential helper and no hooks; the tag's commit must be on that `main`, a fast-forward of the checkout's commit, with package.json naming the version. Otherwise it refuses and changes nothing; it never resets to a release and never forces.
5. **The new build proves itself before the checkout moves.** The tag's commit is unpacked with `git archive` into the data folder, `npm ci` runs at the root and in `web/`, and the client is built. That build is started (`node src/server.ts`) on a free loopback port with an **empty** data folder and settings file, and must serve the client, sign in, answer `/health` and report the release's version. Then the new build's store code alone opens a `VACUUM INTO` copy of the owner's database, proving its migrations on the real data. An empty data folder for the server, not a copy: the new build's restart recovery on a copy would see the owner's recorded process groups and issue claims and could stop the first or release the second on the remote. If either check fails, the checkout never moved and Settings says why.
6. **Then the switch.** The database is copied aside (`before-update.sqlite`), the checkout fast-forwards (`git merge --ff-only`) and is installed and built in place. If that install fails, it goes back to its exact previous commit with `git reset --keep` (which refuses to lose a file) and is built again. `update.json` records the version and both commits. When launchd has `dev.botbench.server`, Botbench waits once more for work to rest and runs `launchctl kickstart -k gui/<uid>/dev.botbench.server`; otherwise Settings says a restart is needed. The next start confirms the record against the checkout's commit and sends the phone one notification, "Botbench updated to <version>".

## Consequences

- The update path is code execution by design. It trusts the repository's own commits on `main` reached by a release tag, the packages its lockfiles pin, and GitHub's TLS; it trusts GitHub's release metadata only to name a version, never to supply what runs. Releases are not signed: anyone with write access to `main` and its tags can run code on every updating installation.
- A failure of the real start that neither check covers (restart recovery on the owner's data, the owner's settings file) shows only after the restart; going back is by hand (threat model, open item 13), because an older Botbench refuses a database a newer one migrated.
- The release pull request's dispatched CI is proven only when the first release pull request opens; if GitHub ever stops counting a dispatched run's checks for a pull request, the owner can re-run its checks or close and reopen it.
- Not here: a stable channel (OpenMausBot promotes a release after 48 hours on its own instances), signed releases, and updating an installation that is not a git checkout.

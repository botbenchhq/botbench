# Botbench threat model (STRIDE)

Scope: Botbench as built through units 1 to 13, unit 26 and unit 27, plus the boundaries the plan adds next. Update this file in the same pull request as any unit that adds or changes a trust boundary.

## What is being protected

- The owner's repositories and working trees.
- The owner's vendor logins and subscription allowance.
- The owner's machine: files and commands outside a task's worktree.
- Botbench's own records: transcripts, evidence, approvals, the action log.

### How a tool call is decided (U7)

A task's Claude Code is started with Botbench's own settings object on the command line (`--settings`), no settings files (`--setting-sources ""`), the edit rule `Edit(./**)`, and `--permission-prompt-tool stdio`. Three things then stand between a tool call and its running:

1. **The pre-tool hook** (`src/approvals/permission-proxy.ts`, matcher `*`). The CLI runs it before every tool call. It asks the broker over B7 and prints `ask`, `deny`, or nothing. It never prints `allow`. Edits and reads inside the worktree pass (nothing printed), and so do the CLI's own bookkeeping tools (`ToolSearch`, `TodoWrite`); every shell command and every other tool gets `ask`.
2. **The CLI's own rules.** The only allow rule is file edits below the worktree. An ask rule for `Bash` makes every shell command ask even when the hook did not run; a hook's answer cannot get past it.
3. **The permission prompt**, which the CLI sends to the driver on its stdout and the driver answers on its stdin. The broker first puts it to the gate with the input the answer would hand back: what the gate lets run without the owner (an edit or read inside the worktree, a read of the session's own saved output, and the shell commands described under the pre-approved list, standing permissions and the modes) is answered at once and, where it is a change or a command, logged before it runs. Anything else becomes an approval row and waits for the owner. Only `POST /api/approvals/:id` with a session resolves it.

The socket answers one question (pass, ask or deny) and has no message that allows a call or answers an approval. The owner's decision travels only inside the Botbench process and down the CLI's own stdin.

### An approval across a restart (U8)

An approval that is pending when Botbench stops, by a shutdown or a kill, stays pending. The next start marks it parked (`parked_at`), stops what is left of its attempt's CLI process, and leaves its task at `building` without re-driving it. Nothing waits in the new process, so the owner's answer cannot be handed to anyone: it is stored on the approval (`stored_decision`, with the log entry, in one transaction) and the approval stays `pending`. Botbench then starts a new attempt that resumes the same CLI session in the same worktree and tells the agent, in words marked as Botbench's, to make its unanswered call again. The stored answer is given to that attempt's request only if all of these hold:

- the request comes from the attempt the engine admitted as resuming the attempt that asked, for the same task and role;
- tool, command (the text the card showed) and worktree-relative directory are equal to the stored ones, and the directory was reported by the hook;
- the approval is still `pending` with that stored decision, and the log holds the owner's decision for it.

The approval is moved to `allowed` or `declined` and the use logged (`stored_answer_applied`) in one transaction before the answer goes to the CLI, so one answer is given at most once, whatever fails afterwards. If the resuming attempt's first request is anything else, including one Botbench itself refuses, or the turn ends without a request, the stored answer is discarded: the approval ends `superseded` with a `stored_answer_discarded` entry, and the new request is an ordinary new card. A request the run's pre-approved list allows counts as "anything else" here: it runs, and the stored answer is discarded (tested). A stored answer survives no further restart: the next start discards it and marks the task interrupted with the reason.

### Pre-approved commands and the safety floor (U9)

When the owner starts a task, the request may list commands that task's run may use without asking (`preapproved`). They are stored as grants in the same transaction as the task row. A grant is the command's words, the role, the source repository's real path, the directory relative to the worktree (always its top in this unit) and the run. Grants are never changed or removed. Nothing is granted that the start request did not list: the per-repository list in the config file is only what the New task screen offers for the owner to confirm or edit.

The gate (`src/approvals/gate.ts`) is a function of the request, the grants and the floor. For a shell command it goes in this order:

1. **The floor** (`src/approvals/floor.ts`), a table of named rules, tried in this order: `recursive-delete-outside-worktree` (`rm -r`, `find … -delete`, `rsync --delete…`), `git-push` (any word after `git` that is `push`, `send-pack`, `send-email`, `http-push` or `dcommit`), `git-config-override` (`-c`, `--config-env`, `--exec-path`, a `GIT_…=` word, any `git config`), `sudo` (`sudo`, `doas`, `su`), `download-into-shell`, `shell-runs-text` (`sh -c`, `-s`, `--rcfile`, `eval`), `recursive-permissions-outside-worktree` (`chmod`, `chown`, `chgrp`, `chflags` with `-R`), `disk-tool`, `guarded-place`, `not-a-plain-command`. A command under any rule asks, whatever is granted. How the rules read:
   - Every word is looked at as if a program could start there (`env sudo`, `xargs rm -rf`, `find -exec`), and program names are compared without case. An argument with a space in it is read as a command of its own (`env -S 'sudo ls'`, `git submodule foreach 'git push'`).
   - A path is inside the worktree only if it is strictly below it as written and with links followed. A `..` is never followed, `~user`, `~+` and `~-` are never inside, and an operand may start with a dash (`rm -rf sub -x/../..`).
   - `guarded-place` asks for any word, any value after `=`, or any value glued to a one-letter option (`-o/path`) that points at: the shell profiles (`~/.zsh*`, `~/.bash*`, `~/.profile`, fish, oh-my-zsh), `~/.ssh`, `~/.gnupg`, the keychains and login items, `~/.gitconfig`, `~/.config/git`, `~/.npmrc`, `~/.netrc`, `~/.aws`, `~/.kube`, `~/.docker`, `~/.claude`, `/etc`, the cron tables, the home directory itself or a folder that holds one of these, and Botbench's own data directory outside this task's worktree (its token, database and other tasks' worktrees). The keychain and SSH key tools ask by name.
   - The config file can add entries (`floor`): a program and words that, found in that order after it, make a command ask. An entry cannot take the name of a built-in rule, and no route changes the floor.
2. **Is it one plain command?** (`src/approvals/shell.ts`). The command is split into words only if it consists of words separated by spaces, with single- or double-quoted parts. Any of these anywhere outside quotes makes it not plain: `;`, `&`, `|`, `<`, `>`, `(`, `)`, `{`, `}`, `$`, a backtick, a backslash, `*`, `?`, `[`, `]`, `#`, `!`, `^`, `%`, a word starting with `=` (also after an empty quoted part), a tab, a line break or any other control character, and every character outside printable ASCII (other spaces, look-alike punctuation, invisible characters). Inside double quotes `$`, a backtick, a backslash and `!` do the same; an open quote does too. A command that is not plain is never matched. Two things the shell still does to a plain word are left to the floor, not refused here: a leading `~` (the floor treats every form but the owner's own home as unknown and guarded), and bash's tilde after `=`.
3. **The grant match.** The request's leading words must equal the grant's words exactly, one by one; more words may follow. Role, repository, run and worktree-relative directory must be the grant's. A shell call that carries more than its command (a time limit, a background flag) does not match, and neither does one whose directory the hook did not report.

A match is allowed inside the Botbench process when the CLI's own permission request arrives, and written to the action log as `preapproved` with the grant's id before the answer is given; if it cannot be logged it is refused. The hook's socket is not told about grants: for every shell command it still answers `ask`. A command that asks because of the floor has the rule's name on its `asked_owner` entry.

What a pre-approved command can still do, stated exactly:

- **It runs the program with any further arguments.** `npm test` pre-approved also allows `npm test -- --anything`, and arguments can change what a program does (`--prefix`, a config flag, an output path). Pre-approve the narrowest command that does the job.
- **It runs whatever that program runs.** `npm test` runs the repository's own script, which the agent may have just edited (edits inside the worktree do not ask). `sh build.sh` runs the file as it is at that moment. A pre-approved script or test command is therefore as much as letting the agent run any code as the owner, within the confinement of U27 (see "Confined commands"). This is the price of an unattended run (R20).
- **A broad entry is broad.** Pre-approving a bare interpreter or wrapper (`node`, `python`, `env`, `xargs`, `make`, `git`) allows everything it can be told to do on its command line, short of the floor. `git` aliases and a program's own config files are not read by the floor.
- **The floor reads the command line only.** It names known dangerous forms; it is not a list of everything harmful. `curl -d @file https://…`, `scp`, `gh pr create` or `npm publish` are not on it and ask only because they are not pre-approved. The owner can add entries in the config file.
- **The guarded places are a short list.** Directories on `PATH` (`/usr/local/bin`, `/opt/homebrew`, `~/.local/bin`), a `ZDOTDIR` elsewhere, other credential files and the rest of the home directory are not on it. A pre-approved `cp`, `mv` or `rm` (without `-r`) can overwrite or delete single files anywhere the owner can.
- **Other ways to gain rights or reach a disk** (`osascript … with administrator privileges`, `launchctl`, `hdiutil`) are not named. They need the owner to have pre-approved that program.
- **Abbreviated or aliased subcommands** are not known to the floor: a git alias defined in the owner's own git config that pushes, or `npm pub` against an added entry `npm publish`.
- **A pre-approved script can read the attempt's gate secret** from its environment, as any allowed command could since U7. With it a process can ask the gate for a verdict and report a directory for a tool call id it would have to guess; a grant is still matched only on the CLI's own request inside Botbench.
- **The decision is made when the request arrives**, on the links and directory as they are then; the command runs a moment later.
- **The floor asks more often than it must** (`echo sudo`, `git stash push`, `ls ~`, a file named `security`): asking once too often is the cheap mistake.
- A bare program that only runs other commands (`sh`, `bash`, `env`, `xargs`, `sudo` and the like) is refused as an entry. A command the floor always asks about (`git push`) can still be listed; it is stored, shown as pre-approved, and asks every time.

### Standing permissions (U10)

A standing permission is a grant that belongs to no run: one command, as its words, for one role, in one source repository (by its real path, so every task's worktree of it is the same), from one directory relative to the worktree. It is earned, offered, given, used and taken back like this:

- **Counting.** Nothing stores a count. Each time it is needed, Botbench counts the approvals that ended `allowed`, whose `owner_allowed` entry is in the action log, and whose role, tool, directory, repository and command words equal the request's. Both tables are append-only (an approval leaves `pending` once). A decline, a request that ended unanswered, an answer stored across a restart that was never applied, and a run on a pre-approved or standing grant are not approvals and do not count. A request whose directory the hook did not report counts for nothing. Approvals from before a standing permission for the same key was taken back do not count: what was taken back is earned again from nothing.
- **The offer.** A pending card carries an offer only when the broker, from its own records, finds all of: the request waits in this process (not one parked by a restart); it is a `Bash` call whose shown command is one plain command (`src/approvals/shell.ts`); the floor does not name it; it could be a pre-approved entry (no leading variable or option, not a bare program that only runs others, at most 500 characters, reads back as the same words); it is not one of the forms that are never eligible (below); its directory was reported, is written plainly, and is inside the worktree with links followed (the hook's directory is recorded with links followed); no standing permission for it is in force; and the count has reached `autonomy.offerStandingAfter` (default 3; the config loader and the broker both refuse anything but a whole number of at least 1). A request the floor names, or that is not plain, never offers, however often it was allowed (AE6). Tools other than the shell are never offered: a grant for a tool's name would allow any input, and the floor reads command lines only.
- **Never eligible, though not on the floor** (`standingProblem` in `src/approvals/grants.ts`; a standing grant of such a form, however stored, is not matched either): a command with a `~` in any word (the reading drops quotes, so `cat '~/x'` and `cat ~/x` are the same words and only a shell knows which is the home directory); a program that runs the command handed to it (`env`, `xargs`, `nice`, `timeout`, `exec`, `find` and the like); a program that reaches beyond the machine or changes what starts on it (`curl`, `wget`, `scp`, `rsync`, `ssh`, `nc`, `gh`, `docker`, `kubectl`, cloud CLIs, `open`, `osascript`, `crontab`, `launchctl`); an interpreter handed its code on the command line (`-c`, `-e`, `--eval`, `-p`, and `awk`, `sed`, `jq` always); and any command with a word `publish`, `push`, `deploy`, `release`, `upload`, `login`. This is a list of known forms, not of everything that sends data away: a script or a test command can do all of it (next list), and a program not named here is eligible. These still ask every time and can be allowed from each card.
- **Giving.** Only `POST /api/approvals/:id` with `{ "decision": "allow", "standing": true }` and the owner's session gives one. The flag asks; the broker decides eligibility again, inside the transaction that also marks the approval allowed, stores the grant, and writes `owner_allowed` and `standing_granted` (with the grant's id). If any of it cannot be written, none of it is and the card still waits. An ineligible card answers 409 and is neither granted nor allowed. The scope granted is computed from the approval's own row, which cannot be changed once written, and its task's repository: nothing a client sends names a command, a repository, a directory or a role. In the client the offer is a secondary control below Allow that opens a statement of the scope and does nothing until that is confirmed.
- **Use.** The gate asks the floor first, then the grants. A standing grant matches only a request whose words are exactly the grant's, no more, with the same role, repository and directory, on a call that carries nothing but its command, from an attempt whose directory the hook reported. It is honoured only if it names no run, was not taken back, and the log holds its `standing_granted` entry. The use is written to the log as `standing` with the grant's id before the answer is given; if it cannot be logged the request is refused. The transcript says the command ran on standing permission, not that the owner allowed it.
- **Taking back.** `POST /api/grants/:id/revoke` with the owner's session adds a row to `grant_revocations` and a `standing_revoked` log entry in one transaction. Grants and revocations are never changed or removed (triggers, which with `recursive_triggers` on also refuse `INSERT OR REPLACE` on every append-only table; tested); a grant is taken back once; only a standing grant can be. Grants are read from the store for every request, so the very next request asks. `GET /api/grants` lists what is in force with how often and when each was used, counted from the log.

What a standing permission can still do, stated exactly:

- **It outlives the task.** Unlike a pre-approved command it applies to every later task of that repository for that role, until the owner takes it back. Injected text in any such task can make the agent run it as often as it likes, with no card.
- **It runs whatever the command runs at that moment.** `npm test` runs the repository's script and `sh build.sh` the file, which the agent may have just edited without asking. A standing permission for a script or test command is as much as letting agents in that repository run any code as the owner. The same price as a pre-approved command, paid for longer.
- **Exactly the words, and nothing about the environment.** No further argument is allowed, but the files the command reads, the branch the worktree is on and the environment are not part of the grant.
- **The repository is a path.** A task stores its repository's real path when it is started, and grants and counts compare that stored path; a link pointed elsewhere afterwards carries nothing over (tested). A different repository later placed at the very same real path inherits the grant.
- **Words, not quotes.** Two spellings that split into the same words are the same command for counting and for the grant (`npm  test`, `'npm' test`). The one case where quoting changes what a shell does with a plain word, a leading `~`, is never eligible.
- **Three approvals may be one afternoon.** The count has no time window and does not look at which tasks the approvals came from; an agent that asks for the same command repeatedly in one task reaches the number as soon as the owner has allowed it that often. Every one of those is the owner's own Allow.
- **The Trust screen is read when it is opened.** It does not follow the stream: a permission used or given in another tab shows after a reload of the screen.
- **A stolen session can give and take back.** It could already allow any card; with an eligible card it can also make that allow permanent. It cannot make a card eligible except by allowing real requests of an agent, and cannot grant what the floor names.
- **A process that rewrites the database file** can forge a grant together with its log entry, as it can forge the rest of the log: accepted, as before. The floor still applies to a forged grant (tested).

### Runs, the planner and the plan gate (U11)

New boundaries: a client names a file for Botbench to read (the spec), a planner agent reads a repository, and what the planner writes becomes the tasks later agents are given.

- **The spec file path (information disclosure, denial of service).** `POST /api/runs` takes `specPath`, behind the session like every route. Botbench reads it only when it is a full path whose real location is a regular file named `.md`, `.markdown` or `.txt`, outside Botbench's own data folder, at most 200,000 bytes, with one name only (a hard link is refused: it could be a second name for a file in Botbench's folder), valid UTF-8 with no NUL. The path is resolved once, the real path is opened with no-follow and non-blocking flags, the open file is the one measured and read, a pipe or device is refused without being read, and the whole read ends after 2 seconds. A refused file's content is never echoed. The repository and the spec are checked before a run row or a worktree exists. What remains possible: whoever holds the owner's session can make Botbench read any text file with one of those endings that the Botbench process can read, see it again through `GET /api/runs/:id`, and have it sent to the model provider as the planner's prompt. That is the feature; the session is the control. A read that stalls in the file system past the limit keeps one of Node's file threads busy until the system lets go.
- **The planner is read-only (elevation of privilege, tampering).** Enforced three times over. (1) At launch: Claude Code is started with `--tools Read,Glob,Grep,Bash` and `--disallowedTools Write,Edit,MultiEdit,NotebookEdit` (and the tools that outlive a turn, as every attempt; see Modes), so the model has no tool that writes, fetches or starts an agent, and with `--setting-sources ""` so no settings, hooks or MCP servers of the repository or the owner load. (2) At the gate: the planner's admission is read-only, so the pre-tool hook is answered "deny" for every tool but Read, Glob, Grep and the shell, also inside its worktree, and "ask" for every shell command; the CLI's own request for any other tool is refused in the broker as well, should the hook not have been heard; its request is then decided with no grants at all (a run's pre-approved list belongs to the implementer role, and a planner's request earns no standing permission), so every command becomes a card under the role `planner`, naming the run. (3) By place: it works in a detached worktree of the base commit under the Botbench home, on no branch, never the owner's checkout, removed with `--force` when planning ends however it ends; at every start, before any planner works, every planning worktree still under the home is removed, whatever its run says by then. A shell command the owner allows runs in Claude Code's sandbox (U27) with no network, the repository's allowed hosts never applying to the planner; reads inside the worktree are not asked about.
- **Plan content is untrusted model output (tampering, injection).** The reply is parsed as JSON from its last fenced block and validated (1 to 20 tasks, a one-line title of at most 200 characters, 1 to 10 one-line criteria of at most 500, none holding a line break, control character or direction override, so the owner approves the text the builder is sent); anything else goes back to the planner once and then fails the run with the reason. Titles and criteria are stored as text and rendered as React text children, never as markup, and are never run or read as instructions by Botbench. Repository text can steer the planner (prompt injection): the result is still only a plan, which the owner reads, edits and must approve before any task row exists. The owner's prompt, the current plan and feedback are set apart in the planner's prompt as data. An approved task's title and criteria become an implementer's prompt in unit 12; that agent is behind the gate and the floor like any other.
- **The plan gate (tampering, repudiation).** A plan changes only while the run waits for approval: the engine refuses otherwise (409) and triggers on `plan_tasks` refuse it in the store. Every edit, approval and request for changes names the plan version it saw; a stale window is refused, so what is approved is what was on screen. Approval, its task rows and its event are one transaction; two approvals at once yield one. Run events are append-only, runs are never deleted, and a trigger keeps an ended run ended and an approved plan closed. A cancel that arrives while start-up recovery is at work stands: recovery moves only a run that is still planning.
- **Restart.** A run found `planning` at start is failed with the reason (or returned to approval with its plan as it was), its planner process stopped, its pending cards ended, its worktree removed. An approved run's queued tasks are left queued by the task engine's recovery.

### The build line and setup commands (U12)

New boundary: commands Botbench runs itself, outside the permission gate, in a worktree. An approved run's tasks are now built: one at a time, in plan order, each in its own worktree from the run's base commit, after the repository's setup commands.

- **Setup commands are the owner's, run by Botbench (elevation of privilege, tampering).** They come only from the owner's settings file (`repositories.<path>.setup`), which no route writes; a client cannot add, change or reorder one, and nothing an agent or a repository writes becomes one. They do not pass through the gate: the owner configured them, so asking the owner about them would only ask the owner to approve their own settings. Each runs as `/bin/sh -c <command>` with the owner's rights, in the task's worktree, with Botbench's environment less every `GIT_*` variable (as for Botbench's git calls), no input, in a process group of its own. They are run before any agent of that task has started, in a worktree freshly made from the base commit, so what they run is the repository's own code as the owner committed it. Since U27 each runs confined (see "Confined commands"): it cannot read the owner's sign-ins, Keychain, keys, cloud credentials or Botbench's data folder, can write only its worktree and a temporary folder, and reaches only the hosts the repository allows, through Botbench's proxy. It gets the allowlisted environment a CLI gets, not Botbench's whole environment.
- **A worktree that already holds agent-written files.** Setup runs only in a worktree no agent has worked in: a new one, or, after a restart or the owner's Resume (U15), one whose setup was stopped before the task named any attempt. An agent is sent its prompt only after its task names its attempt (a CLI started just before that is stopped on start, unprompted), so a task with an attempt is never set up again: only its turn is re-driven (tested with a setup that is not repeatable). Check commands (unit 13) always run agent-written code; see below.
- **Time limits and leftovers (denial of service).** Each command has a time limit: 10 minutes, or the `timeoutSeconds` the owner gives it (1 to 86,400). When it passes, the whole process group is killed with `SIGKILL` and the command is recorded as timed out; the task fails with the reason, before any agent starts. When the command ends by itself, whatever it left running in its group is killed too. A cancel or a shutdown stops a running setup command the same way and records it as stopped. Tested with a real script that leaves a background child (gone afterwards, checked with `ps`). What escapes: a process that leaves the group on purpose (`setsid`, a daemon that double-forks) is not followed.
- **A Botbench that is killed outright (closed, U15).** Setup and check commands run in process groups of their own, so they outlive a `SIGKILL` of Botbench. Each is recorded in `command_processes` before it starts, with its process group and the time it was started once it runs and its temporary folder, and the row is closed in the same transaction that stores its evidence. On the next start, before any task is taken up or committed, every open row's group is stopped if it is still that command's (the same check as for a CLI: the machine has been up since the record and the leader began no later than it, times read in UTC, or the leader is gone while members remain; never on the bare number, and never when no start time was recorded), its temporary folder is removed (only a `botbench-command-*` folder directly in the system's temporary folder), and the command is recorded as stopped by the restart. Evidence stays append-only: the stopped command keeps its row, and the list is run again from the start as the next round. A task one of whose commands could not be stopped is stopped for the owner with nothing more run or committed in its copy. Tested with real surviving groups, a leaderless group, and an unrelated process under the recorded number.
- **Evidence (repudiation, tampering).** Each command's text, outcome, exit code or signal, the last 200,000 characters of its combined output, its limit and its times are one row in `evidence`, which triggers keep append-only (update, delete and `INSERT OR REPLACE` are refused; tested). Output is shown as text, never as markup, and is not sent anywhere. What setup writes into the worktree is committed by Botbench with the agent's work unless the repository ignores it: an output that holds a secret is then on the task's branch.
- **One agent per worktree, one task at a time.** The line is one queue for every task of every run and every task started on its own; a task's worktree is made only when its turn comes, and a task waiting for the owner's answer holds up the tasks after it. Tested: the second task's worktree does not exist while the first is building, and stays absent while the first waits on an approval.
- **Cancel after approval.** The run and its tasks not yet started are cancelled in one write; the task at work has its setup command or its turn stopped, what it did committed to its branch, and is recorded as cancelled; finished tasks keep their branches; the run's pending approvals are closed as superseded, never allowed. A task cancelled while its worktree was being made has that unused worktree and branch removed again. A cancelled run stays cancelled (a trigger keeps an end an end).
- **Restart (U15).** A task that was at work when Botbench stopped (killed or shut down) is taken up again once, from where it was: its setup again from the start (no agent had started), its agent's turn re-driven from the session it reported (or with the task's own prompt when it reported none), or its checks again from the start on the committed work, nothing a check left being committed. The count is in the store (`tasks.restarts`), so a second restart stops the task for the owner, its turn's work committed, and no loop is possible; the owner's Resume (409 for a task in any other state, or with no copy left, or being discarded) sets the count to 0 and takes it up the same way. A run being planned is planned again once, from the start, in a fresh read-only copy, and fails the second time (`runs.restarts`). The run then goes on with its tasks that had not started. A task parked on an approval across a restart holds up its run until it is resumed.

### The verify station: check commands (U13)

After a task's builder finishes and Botbench has committed its work, Botbench runs the repository's configured check commands in that task's worktree, the same way it runs setup commands (owner's settings only, `/bin/sh -c`, own process group, time limit of 10 minutes or `timeoutSeconds`, killed with the group at the limit, on a cancel and on shutdown, leftovers in the group killed when it ends).

- **Checks run code the agent may have just written (elevation of privilege).** `npm test` runs the test files and the `package.json` scripts the agent may have edited, on the host, with no card. The approval gate does not stand in front of it: the owner configured the command, the agent chose what it does. Since U27 checks run confined, as setup commands do (see "Confined commands"): they cannot read the owner's sign-ins, Keychain, keys, cloud credentials or Botbench's data folder, can write only the worktree and a temporary folder, and reach only allowed hosts. They can still read the rest of the owner's home folder and print it into evidence, and do anything the confinement allows. The task and run screens say so beside every check result: "Checks run this repository's own commands on the agent's work, on this Mac, in a sandbox: they cannot read the sign-in, key and credential folders Botbench keeps them from or Botbench's own files, can change files only in this task's copy and a temporary folder, and reach the internet only at hosts allowed for this repository in Botbench's settings file. They can still read the rest of your home folder. The agent may have changed the code they run, so read the output, not only the result." Point Botbench only at repositories you trust, and read the diff before accepting.
- **A check cannot forge its own result into the work (tampering).** Checks run after Botbench's commit; nothing they write is committed, so the branch is what the builder produced. What a check prints is stored as text and shown as text. A check can still lie about passing (exit 0); the output and the diff are the evidence.
- **Evidence is immutable (repository).** Check rows go into the same append-only `evidence` table as setup rows (migration 11 rebuilds it to allow the new kind, keeping every row and id, and puts the triggers back; tested from a literal copy of the version 10 schema). The task's `checks` mark (passed, failed, none) is written once; a trigger refuses changing or clearing it. A timed-out check counts as not passed. A repository with no checks is marked `none` and shown as "No checks are set up for this repository", never as a pass.
- **Restart and cancel.** A task found at Checking on start is ended as interrupted with its committed work; nothing a check left in the worktree is committed. A cancel stops the running check (recorded as stopped) and ends the task as cancelled.
- **Files a check leaves behind** (coverage output, caches) stay uncommitted in the worktree. Unit 14's decisions list them and remove them only once the owner confirms; see below.

### The silence limit: a builder or planner that goes quiet

No new trust boundary: this closes a denial of service on B2. Before it, a CLI process that stopped sending events and stayed alive left its task Working, and its run's queue held up, with nobody told (finding 1 of `docs/reviews/design-vs-openmausbot.md`).

- **What it is.** `autonomy.silenceLimitSeconds` in the settings file: a whole number of seconds from 0 to 86,400, 600 (10 minutes) when absent, 0 for no limit; anything else (negative, fractional, not a number) stops Botbench at start with a plain message, as the other autonomy settings do (tested). It applies to every builder turn (the build, a round of fixes, a resume, a re-drive after a restart) and every planner turn, through one watcher (`src/engine/silence.ts`). The review keeps its own 10-minute limit, unchanged; a chat turn has none.
- **What counts as silence.** Every event the session stores restarts the clock, so a long build that keeps reporting is never stopped however long it runs in total (tested at more than four times the limit). While the CLI waits on the owner's answer to a request, the clock does not run at all, however long the owner takes; the answer is itself an event, so the clock starts again from it (tested: not stopped after four times the limit of waiting, stopped one limit after the answer). A shell command that runs quietly for longer than the limit inside the agent's turn does count as silence: the agent is stopped, as an owner who set the limit asked for.
- **The stop.** Past the limit the turn is stopped through its driver (for Claude Code: the interrupt request, then the process group is killed with `SIGTERM`, then `SIGKILL`). Before the stop is recorded, Botbench itself confirms that the attempt's recorded process group is empty, killing whatever is left of it; the task's work up to then is committed as for any stop, and nothing else is: a silent agent that wrote nothing leaves no commit on its branch (tested). A group that cannot be confirmed gone fails the task saying so, rather than reporting a stop. On macOS, signalling a group whose leader has just exited and is not yet collected gives `EPERM`; that is treated as nothing left to signal, not as an error, and the group counts as gone only once the system answers `ESRCH` for it (tested with a real exited group leader).
- **Where it leaves the work.** A builder that went silent leaves its task Stopped (`interrupted`), never Failed, with a reason that names the limit ("Claude Code went silent: it sent nothing for 10 minutes …"), the "A task stopped" notification, and Resume, which tells the agent why it was stopped. In every mode it goes to the owner: a fully autonomous run never accepts or merges it, because it never reaches Ready for review (tested). A planner that went silent fails its run with the same kind of reason; its read-only copy is removed as on any planner end.
- **Cleared.** The watcher ends with its turn, also when the owner cancels the run or Botbench stops (tested: a cancelled task is Cancelled, and nothing more happens after the limit).
- **What escapes.** As for every process-group kill: a process that leaves the group on purpose (`setsid`, a daemon that double-forks) is not followed. A CLI that keeps sending events while doing nothing useful is not silent and is not stopped.

### Decisions: accept and reject (U14)

New boundary: a client request now deletes things in the owner's repository: a task's worktree, the files in it, and, for a reject that discards, the task's branch. The routes are `POST /api/tasks/<id>/accept` and `POST /api/tasks/<id>/reject`, behind the owner's session and the `Host`/`Origin` checks like every other route.

- **Only Botbench's own things are removed (tampering, elevation of privilege).** The worktree removed is the task's stored path, and only after the same check every worktree operation makes: a linked worktree of that repository, on a Botbench task branch, whose git folder is the repository's own entry. A copy already removed by hand is forgotten by its own path only (`git worktree remove --force <path>`); nothing repository-wide is pruned, so the owner's own worktrees on a drive that is not mounted keep their records (tested). A branch is deleted only when it is a Botbench task branch (`botbench/` or the old `smelt/` prefix), still points at the commit Botbench made, and is checked out nowhere but the task's own copy; all three are checked before anything is removed, so a refused reject changes nothing (tested for a commit added by the owner and for the branch checked out in the owner's own worktree). The delete itself is `git update-ref -d <ref> <commit>`, an atomic compare-and-delete, so a commit added in the meantime keeps the branch. Accept and a reject that keeps the branch are refused when the branch is no longer there, so the screen never offers a merge of a branch that does not exist. Nothing is merged, pushed or written to the owner's checkout or current branch (tested: the checkout state is unchanged after accept and both rejects). No path, branch or file name from the request reaches git: the request carries the decision, keep or discard, and the list of files the owner confirmed, which is only compared.
- **Work is never deleted unasked (tampering).** Files in the task's copy that are not on its branch (what the checks wrote after Botbench committed, or tracked files changed since) go with the copy. A decision is refused with 409 and the list while there are any, until the request carries `removeLeftovers` with exactly that list, which the client sends only from the dialog that showed it. A file that appeared after the dialog opened makes the lists differ: the decision is refused and the new list shown (tested). Files git ignores (dependency folders, caches) are not counted. Messages and the log name at most 20 files and say how many more; the decision row stores them all.
- **One decision, recorded (repudiation).** A decision is one row of `decisions` (migration 12): decided by the owner, accept or reject, branch kept or deleted, the branch name and commit, the files removed, the time. Triggers refuse updating or deleting it, refuse a row for a task that is not ready for review, and refuse moving a task to accepted or rejected without its row (tested). Each decision is also an `owner_accepted` or `owner_rejected` entry in the append-only action log, shown on Permissions → Activity. Two requests for one task at once: one is made and the other refused (tested).
- **A half-made decision (denial of service).** The worktree is removed before the branch is deleted, and the decision is written only after both. If the branch still cannot be deleted after those checks, the task stays ready for review with its copy gone, says so, and a second reject finishes the job (a missing copy is forgotten, not an error; tested). The task screen then shows only that its changes cannot be read from the copy; saying plainly that the copy is gone is left for later.
- **A run's end.** A run is done once none of its tasks is left to decide and at least one was decided; a run whose every task failed or was stopped stays at Ready for review, as unit 13 left it.

### Confined commands (U27)

New boundary B8 (ADR 0002, step 1). Before this unit a command the owner allowed, a pre-approved or standing one, and every setup and check command ran with the owner's rights anywhere on the machine; measured on 2026-11-22, such a command could read Claude Code's sign-in from the Keychain. Now each runs confined. Claude Code 2.1.322 on macOS 27.2; every key below was checked against the settings reference (code.claude.com/docs/en/settings-reference, sandboxing) and against the CLI by experiment.

**An agent's commands.** Every Claude Code attempt (a task's builder, a run's planner, a chat turn) is started with Botbench's one settings object on the command line (`--settings`, with `--setting-sources ""` for an attempt in a worktree and for a chat turn), holding:

- `sandbox.enabled: true` and `sandbox.failIfUnavailable: true`: every shell command, and every process it starts, runs under macOS Seatbelt, and the CLI refuses to start rather than run commands unconfined.
- `sandbox.autoAllowBashIfSandboxed: false`. Critical: with `true` (the CLI's default before 2.1.324; this Mac runs 2.1.322) a sandboxed command runs without a permission prompt and the bare `Bash` ask rule is skipped, so Botbench's gate would silently disappear. Live-tested: with the sandbox on, every shell command of a task still became a request to the owner, and each ran only after its allow (`test/live/sandbox.live.test.ts`, `e2e/sandbox.e2e.ts`).
- `sandbox.allowUnsandboxedCommands: false` and no `excludedCommands`: the model's `dangerouslyDisableSandbox` is ignored, and no command runs outside the sandbox. A call that carries that field is not a plain command to the gate either, so no grant lets it through without a card.
- `sandbox.filesystem.denyRead`: `~/.claude`, `~/.claude.json`, `~/.codex`, `~/.grok`, `~/.gemini`, `~/.antigravity`, `~/Library/Application Support/Antigravity`, `~/Library/Keychains`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/gcloud`, `~/.azure`, `~/.kube`, `~/.docker`, `~/.netrc`, `~/.npmrc`, `~/.config/gh`, `~/.git-credentials`, `~/.config/git/credentials`, the token files of common registries and tools (`~/.pypirc`, `~/.cargo/credentials{,.toml}`, `~/.gem/credentials`, `~/.m2/settings.xml`, `~/.gradle/gradle.properties`, `~/.terraform.d`, `~/.vault-token`, `~/.pgpass`, `~/.yarnrc.yml`, `~/.config/op`, `~/.password-store`, `~/.config/configstore`), shell history (`~/.zsh_history`, `~/.bash_history`), browser profiles (`~/Library/Safari`, `~/Library/Cookies`, `~/Library/Containers/com.apple.Safari`, and Chrome, Chromium, Brave, Edge, Arc and Firefox under `~/Library/Application Support`), so no confined command reads a saved Botbench session cookie (tested with a decoy cookie file under the real `sandbox-exec`), the old data folder `~/.smelt`, a sign-in folder moved with `CLAUDE_CONFIG_DIR` or `CODEX_HOME`, and Botbench's data folder, each as a full path and, where a link leads elsewhere, where it leads too (one list, `src/confinement.ts`, shared with setup and check commands).
- `sandbox.filesystem.allowRead`: the attempt's own folder, by its real path. A task's copy and the chat folder lie inside the denied data folder. Seen on 2.1.322: with the deny alone the copy was unreadable to its own commands (and still writable); with the narrower allow added, the copy is readable and writable and the rest of the data folder (login token, database, broker socket, other tasks' copies) is not. Other tasks' commits stay readable through the repository's shared git folder (below). The sandbox settings reference says the narrower entry wins; the experiment and the live test confirm it.
- `sandbox.filesystem.denyWrite`: the repository's shared git folder, for a task's copy and the planner's, found by asking git in the source repository the task was started on, never in the copy (whose `.git` file an agent can rewrite). For a linked git worktree the sandbox would otherwise open that folder for writes; seen on 2.1.322, a command could then create a branch in the owner's repository. With it, `git status`, `git log` and `git diff` still work in the copy, and `git add`, `git commit` and `git branch` by the agent fail. Botbench makes the task's commit itself, outside the sandbox. Live-tested: the agent's `git branch` fails and no branch appears in the owner's repository.
- `sandbox.network.allowedDomains`: the repository's `allowedHosts`, none by default; `sandbox.network.strictAllowlist: true`, so a host outside the list is refused rather than put to a prompt (honoured from `--settings`, per the sandboxing guide). For an attempt that builds (a task's builder), and no other: `sandbox.network.allowLocalBinding: true`, so a project's own tests can listen on a port and connect to this Mac (the settings reference: "listen on any local address and connect to any port on localhost"), and `sandbox.network.allowUnixSockets` holding the attempt's own folder, so a Unix socket there works. Not the CLI's temporary folder (`/tmp/claude-<uid>`, the commands' `TMPDIR`): every Claude Code session of the owner shares it, so a socket another session keeps there would be reachable. Live-tested (`test/live/sandbox.live.test.ts`): a server on 127.0.0.1 and on ::1 answers a client in the same command, a Unix socket in the copy works and one in the CLI's temporary folder is refused, 1.1.1.1, an IPv6 internet address and 192.0.2.1 are refused, Botbench's permission socket is refused, and Botbench's own port answers 401. The planner and a chat turn get neither setting.
- `sandbox.credentials.envVars`: `BOTBENCH_BROKER_SOCKET` and `BOTBENCH_BROKER_SECRET` denied, so no command sees the gate's address or secret; the hook, which runs outside the sandbox, still has them. Live-tested.
- `permissions.blockReadsOutsideWorkingDirectories: true`: Claude Code's own file tools (Read, Glob, Grep, and the LSP tool), which run outside the sandbox, refuse every read outside the attempt's folder in every permission mode, before the hook or a prompt is reached. Live-tested: a Read of a decoy in the data folder is refused with no card, for a task and for a read-only attempt as the planner is started. The same key also closes the rest of the home folder to sandboxed commands, apart from the folder, the CLI's temporary folder, parts of `~/.claude` the CLI needs (skills, plugins), the repository's shared git folder and the owner's global git configuration (`~/.gitconfig`, `~/.config/git/{config,ignore,attributes}`), which the CLI re-opens so git keeps working.

The planner's commands reach no network whatever the repository allows; a chat turn's neither.

**Setup and check commands.** Botbench runs them itself, so Claude Code's sandbox does not apply. Each runs as `sandbox-exec -p <profile> /bin/sh -c <command>` (`src/engine/stations.ts`, profile from `src/confinement.ts`): everything is allowed except opening apps through LaunchServices and sending Apple Events (`(deny lsopen)`, `(deny appleevent-send)`: a review found, and an experiment confirmed, that without them `open` of an app the command wrote starts it through launchd with the owner's full rights; tested), reading the same list of places (the copy is opened again by a later rule; seen on macOS 27.2 that a later rule wins, and that the folders above the copy must be allowed metadata reads, not listing, for git to resolve its path); writing anywhere but the copy, a temporary folder made for the command and removed after it (`TMPDIR`), and the terminal devices; and all network except this Mac's own addresses and Unix sockets in the copy and the temporary folder. A project's own tests start servers: before this was allowed, this repository's own `npm test`, run as a check, failed 197 of 381 tests with `listen EPERM` (on 127.0.0.1 and on a Unix socket under the command's temporary folder). The rules, found by experiment on macOS 27.2 with real child processes: `(allow network-inbound (local ip "localhost:*"))` lets a command listen (`network-bind` alone does not; listening is checked as inbound); `(allow network-outbound (remote ip "localhost:*"))` lets it connect to this Mac, on any port; `(allow network-bind (local unix-socket (subpath <place>)))` and `(allow network-outbound (remote unix-socket (subpath <place>)))`, one rule each for the copy and for the temporary folder (a second `subpath` in one rule was not matched), let it make and reach a Unix socket there and nowhere else. Seatbelt's only host names are `*` and `localhost` ("host must be * or localhost"), and `localhost` means any address of this Mac, not only loopback: see the limits below. With the same profile the repository's `npm test` fails 42 of 381, none of them on a port or a socket: Botbench's own tests run `sandbox-exec` inside the check, which Seatbelt does not allow (`sandbox_apply: Operation not permitted`, exit status 71), and look for or signal processes with `ps`, which the sandbox refuses (`spawnSync ps EPERM`). A project whose tests start servers is no longer stopped for that. Names still do not resolve: the resolver is a Unix socket outside the copy. When the repository allows hosts, Botbench's own proxy is started for the command on 127.0.0.1 and closed after it, and the proxy variables point at it; it is the only way out to an address that is not this Mac's. The proxy opens a tunnel (HTTP `CONNECT`) only to an allowed host name, on any port, and refuses a name that resolves to a loopback, unspecified or link-local address, an address given directly, and any plain request. A name that resolves to one of the Mac's own network addresses or a private range is let through, as an intranet host the owner allowed may lead there. So hosts are filtered by name for these commands too, as for an agent's. Seen on this Mac: the rules hold for child process trees; with the network denied a name does not resolve; `npm ci` fails when npm's cache in the home folder cannot be written, and passes with `npm ci --cache "$TMPDIR/npm-cache"` and `registry.npmjs.org` allowed (live-tested), and fails without the allowance. The commands get the allowlisted environment a CLI child gets (`src/drivers/launch.ts`): no provider key variable, no `GIT_*` variable, the owner's own proxy settings replaced. Where `/usr/bin/sandbox-exec` is missing or the system is not macOS, a setup or check command is not run and has failed, with the reason in its output.

Writes from setup and check commands are stricter than an agent's: not even the repository's shared git folder or the home folder's caches. Reads are looser: only the listed places and the data folder are closed to them, not the rest of the home folder, because the owner's own toolchains often live there (a version manager's `node`, `~/.cargo`). A credential kept anywhere else in the home folder is readable to them, and a check could write it into the copy, where an agent's next turn would read it; the screen beside the check results says they can read the rest of the home folder.

**The per-repository network allowance** is `repositories.<path>.allowedHosts` in the owner's settings file, a list of plain host names such as `registry.npmjs.org`: lower case, at least two labels of letters, digits and `-`, no wildcard, no address, no port, no scheme or path, not `localhost`. Anything else stops Botbench at start with a message naming the file, the repository, the setting and the value; the driver checks again before a host reaches the command line. No route or screen writes it. A host allowed is allowed for that repository's builder commands and its setup and check commands.

**When the sandbox cannot run.** The driver's probe asks first: on anything but macOS, or without `/usr/bin/sandbox-exec`, Claude Code is reported as not usable, with the reason, and no attempt starts (a task fails, a chat turn is refused with that sentence). The same holds when Claude Code has managed settings on this Mac (`/Library/Application Support/ClaudeCode/managed-settings.json`, `managed-settings.d`, `managed-mcp.json`, or the `com.anthropic.claudecode` preferences file a device-management profile leaves): they come before `--settings` and could set `autoAllowBashIfSandboxed`, exclude commands or allow hosts. An attempt folder whose path holds `*`, `?` or `[` is refused too, as the read block then does not reach sandboxed commands. Should the CLI itself then refuse to start (`failIfUnavailable`), the turn ends with "Claude Code did not start: its sandbox cannot run on this computer (...), and Botbench does not let an agent run commands without it. Nothing was run." That stderr text is taken from the CLI's own code; it was not seen, because this Mac's sandbox works.

**Reporting a refusal.** A tool result whose output holds the CLI's `<sandbox_violations>` block (`deny network-outbound example.com:443 ...`), macOS's "Operation not permitted", or the CLI's own read rule, carries `confined` (hosts, files) in the transcript. The task screen says so on the call's line ("kept from the network", "kept from a file"), opens it, and says in plain words what the output says, with the output and the technical details below. This is read from the output, which the command also writes: a program can print the block or the phrase itself. It is a report, and Botbench decides nothing on it. A file refusal of the CLI's read rule with no hook in front of it is said as "The agent may read only the folder it works in." (Since a chat asks for approval, every Claude Code attempt has the hook; the sentence stays for a refusal reported without one.)

**What the confinement does not cover**, stated exactly:

- **The CLI itself, its hooks and MCP servers** run outside the sandbox with the owner's rights. Botbench gives the CLI no settings file of anyone's, no MCP server, and one hook of its own; a future MCP server or plugin would run unconfined. The CLI's web tools (web search, and fetch where the CLI offers it) are not limited by the sandbox's network list; they go to the owner through the gate.
- **A secret a command prints reaches the model provider** in the transcript, as everything a tool returns does. The control is that the secret cannot be read; there is no second one.
- **Network filtering is by host name only.** Neither Claude Code's proxy nor Botbench's looks inside the encrypted connection. A command allowed to reach a broad host (for example `github.com`) can send anything there, and domain fronting can reach other hosts behind the same front. Allow as few, and as narrow, hosts as the repository needs.
- **Places not on the list.** An agent's commands cannot read the home folder outside their folder; files elsewhere on the machine that the owner's account can read (`/tmp`, `/etc`, `/opt`) stay readable to them; `/Volumes` is closed by the read block. Setup and check commands can read the home folder apart from the listed places. A credential the owner keeps somewhere else (a project `.env` in another folder, a password manager's export) is readable by setup and check commands, and by an agent's commands outside the home folder.
- **The task's own copy is fully writable**, its `.git` file included, and so is a temporary folder. Whatever a command writes into the copy is committed by Botbench unless the repository ignores it.
- **The repository's shared git folder is readable** to an agent's commands (the sandbox re-opens it so git works): its `config`, where a remote URL can carry a token, every object, the owner's stashes, and other tasks' branches. Denying its `config` would stop git. So are the owner's global git settings.
- **A process a setup or check command leaves behind** with `setsid` stays confined but outlives the command and can still write the copy until Botbench commits or removes it.
- **The per-user temporary folder** (`/private/var/folders/.../T`, where setup and check commands get their own folders) is readable to an agent's commands, which may read the temporary folder of a setup or check command running at the same time.
- **This Mac's own addresses are open to a confined command that builds or checks** (setup and check commands, and a builder's commands), on any port, since the self-build run (see above). So: any service listening on this Mac that does not ask who is calling (a database, a debugger, another dev server, a local proxy or tunnel) can act for the command outside the sandbox. A local HTTP or SOCKS proxy the owner runs, a corporate proxy agent, an `ssh -D` tunnel, a DNS forwarder on 127.0.0.1, or the network proxy of another Claude Code session running on this Mac (which lets through the hosts that session allows), would be a way out to the internet past the repository's host list. Botbench's own port is reachable and answers every route but sign-in and the client's static files with 401 (tested for setup and check commands and live for an agent's): a command cannot read the login token (it is in the denied data folder) and Botbench keeps sessions in memory only, and the profiles of the common browsers (Safari, Chrome, Chromium, Brave, Edge, Arc, Firefox) are on the unreadable list, so a session cookie they saved cannot be read. A browser not on the list, or a profile kept elsewhere, is not covered. Guessing at sign-in delays the owner's own sign-in (capped at 10 seconds). Botbench's permission socket stays out of reach: it is a Unix socket in the denied data folder, outside the two places Unix sockets are opened (tested both ways).
- **A server a confined command starts on all addresses is reachable from the network.** Seatbelt cannot tell loopback from this Mac's other addresses, so listening on `0.0.0.0`, `::` or the Mac's network address is not refused (seen on macOS 27.2: such a server answered a connection to the Mac's network address from outside the sandbox). The command cannot open a connection to another machine, but a machine on the same network that connects in while the check runs can receive what the command sends. The macOS firewall (System Settings, Network, Firewall) refuses such connections; it is off on this Mac. Claude Code documents the same for `allowLocalBinding`.
- **macOS Seatbelt is deprecated** by Apple, though every vendor CLI relies on it, and both mechanisms here depend on it. Only macOS is supported: elsewhere nothing an agent would run is started.
- **The Keychain** is closed by denying `~/Library/Keychains`; the `security` command then cannot find the item (exit status 44, tested with an attribute lookup that never decrypts the item). Other ways a process can reach the Keychain service were not explored.
- **Managed settings from a server.** Botbench refuses to start an agent when a managed settings file or profile is on the Mac, but does not detect server-managed settings of a Team or Enterprise login, which could set `autoAllowBashIfSandboxed: true` (then no shell command would ask; the driver's watch stops the attempt after the first one that ran unasked), exclude commands or allow hosts.
- **Other CLIs.** This unit confines Claude Code only. Codex, since, reviews under its own permissions profile (B9); no other driver exists yet (ADR 0002: a driver that cannot do this is offered for read-only roles only).

### Codex as a reviewer (U17 and U20, in part)

New boundary B9. A run may name Codex as its reviewer (New run, Review). Once a task is built, committed and checked, Botbench starts `codex exec --json … -` once in the task's copy, sends the task's title, criteria and diff on the program's input, and stores the reply on the task as a review, append-only, labelled a model's opinion and not a check. Codex 0.171.0; every flag and setting below was checked against `codex exec --help`, the configuration reference (learn.chatgpt.com/docs/config-file/config-reference, permissions) and real runs. Codex reports a setting it does not know ("ignoring 1 unrecognized configuration setting"), and seen on 0.171.0 it reported none of Botbench's; should a later version report one, the driver stops the turn, as a confinement setting may then be missing.

- **No `--sandbox` and no `sandbox_mode`.** Either sets permission profiles aside. The review runs under Botbench's profile `botbench-review`, given with `-c`: `default_permissions`, `extends = ":read-only"` (commands write nothing, the copy included), filesystem rules that deny the home folder, every place of the one list in `src/confinement.ts` (`~/.codex` and `~/.claude` among them), a Codex folder moved with `CODEX_HOME` and Botbench's data folder, and read only the copy and the repository's shared git folder (the narrower rule wins, seen on 0.171.0), and `network.enabled = false`. Seen with `codex sandbox -P` and live: a write in the copy fails ("operation not permitted"), a decoy in the data folder reads as "Operation not permitted", `~/.codex` cannot be listed, a host name does not resolve. Git in a command gets `GIT_CONFIG_GLOBAL=/dev/null`, as `~/.gitconfig` is denied.
- **Never asks.** `approval_policy = "never"`: what the profile forbids is refused, and nothing waits on a prompt Botbench cannot answer. Codex cannot put a permission request to the owner here, so it is offered for no role that needs one; the configuration refuses Codex as builder or planner in words, and the run route accepts only Codex as reviewer.
- **None of the owner's own setup.** `--ignore-user-config` (no `config.toml`, so no personal MCP servers, profiles or `sandbox_mode`), `--ignore-rules` (no command rules), `-c mcp_servers={}`, `--disable hooks plugins apps browser_use computer_use image_generation`, `web_search = "disabled"`, `--ephemeral` (no saved session). A repository's own `.codex/config.toml` is not loaded for a folder Codex was never told to trust, and session flags outrank project config; the live test puts one asking for `danger-full-access` in the repository and the write still fails.
- **Credentials.** The environment is the allowlist every CLI child gets, with `OPENAI_API_KEY`, `CODEX_API_KEY` and every other provider key removed, and `CODEX_HOME` kept so a moved sign-in is found by Codex itself. Botbench never reads `~/.codex/auth.json`: the probe runs `codex --version` and `codex login status` ("Logged in using ChatGPT" is a subscription, "an API key" is billed by use) and `codex debug models` for the model list.

### The refine loop: the reviewer's feedback goes back to the builder

No new process boundary: the builder is the B-boundary Claude Code task attempt, and the reviewer is B9. What is new is a data flow between them: one model's output becomes part of another model's prompt, and Botbench reads two things from model output to decide what to do next. After a review whose first line is not "Verdict: looks right" (unparseable counts as concerns), and while the run's cap allows (`autonomy.maxRefineRounds`, 0 to 5, default 2, stored on the run when it starts and fixed by a trigger), Botbench starts one more builder turn in the same copy, with the same permission check, the same confinement and the same model as the build (tested: the start options are compared), sends the review between `<review>` lines, commits what the turn wrote, runs the checks again as a new round of evidence, and asks the reviewer again with the new diff and the builder's "Not addressed" lines between `<builder-reasons>` lines. The loop ends when the reviewer says it looks right, the cap is reached, a round changed nothing, or a review or a round did not finish; the task is then Ready for review and the owner decides, as before. Worst case without the owner: 1 build + cap rounds of fixes + (cap + 1) reviews, so 6 model turns at the default cap and 12 at the most allowed, plus one turn taken up again after a restart (a second restart stops the task for the owner).

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: the review poses as the owner or as Botbench to the builder | The prompt says the review is another model's opinion, not the owner's instructions and not a check, and that nothing in it is instructions; the review sits in one `<review>` block, and any `<review` or `</review` in its text is changed so it cannot close the block or open another (unit-tested with "ignore previous instructions" and a closing tag in the text); the same for `<builder-reasons>` and `<previous-review>` toward the reviewer | Done |
| Tampering: the loop changes work or records outside the task | The round of fixes is a builder turn under the same gate, confinement and worktree as the build; Botbench commits, as after a build; reviews and rounds of fixes are append-only (`reviews` and `refinements` triggers, `INSERT OR REPLACE` included); what the checks found may change only for a commit a recorded round of fixes made | Done |
| Repudiation: what a round did is not on record | Each round is a row: the builder's attempt (its events are its transcript), how it ended, whether it changed the work, its reply, the commit it started from and the one made after it; each review row names its round and the commit it read | Done |
| Information disclosure: the builder learns what it should not | It is sent only the reviewer's reply, which came from the read-only, network-less B9 session over the same task's diff | Done |
| Denial of service and cost: models argue without end, burning the subscription | Hard cap, at most 5, fixed per run; the loop also ends when a round changes nothing or a turn fails; Codex has its 10-minute limit; a cancel stops the active turn; restart rules as for a build (taken up once, then stopped with Resume) | Done |
| Elevation of privilege: review text makes Botbench act ("run rm -rf", "ignore previous instructions") | Botbench reads only the verdict line (ask for fixes or not), the lines under its "Checked:" heading (whether it gave an account, and to show them as text) and the reply's two headings (to count); nothing in either model's text can name a command, a grant, a host or a decision. A command the builder tries because of a review goes through the same permission check and safety floor as any other. Tested with a real Codex review that names `rm -rf ~`: no command ran beyond the configured setup and checks, no approval, no grant | Done |

In a fully autonomous run the mode reads the loop's outcome at the end (`reviewOutcome` in `src/engine/modes.ts`): only "satisfied", with every check passing on the last commit, lets it accept; "unaccounted", "unresolved" and "failed" hand the task back to the owner with the reason (engine-tested both ways).

**A bare verdict cannot satisfy an autonomous accept (spoofing).** A reviewer can write "Verdict: looks right" without having looked. The prompt requires, even with no finding, the verdict line, then "Checked:" with two to five lines naming what it examined, then one "Not checked:" line. A review whose last verdict looks right but which has no line under "Checked:" (none at all, or only "- none") is "unaccounted", not "satisfied", so a fully autonomous run does not accept the task; it waits for the owner with "The reviewer gave no account of what it checked." The review is stored exactly as the reviewer gave it, and the task screen shows the Checked lines under the verdict, as text, or the same plain note (engine-tested with Grok's recorded bare-verdict review, replayed unchanged, and with a review that has Checked lines, which still counts as satisfied). What this does not cover: Botbench does not judge whether the Checked lines are true or enough; a reviewer can still name things it did not examine. The lines make the claim visible to the owner, and a missing account is never read as approval.

What it does not cover: a review can still persuade the builder to make a bad change inside its copy; that change is committed, checked and reviewed again, and the owner decides. The model's wording inside the block is not filtered, only its delimiters.

### Notifications to the phone (U23)

New boundary B6: Botbench now sends requests out of the machine, to the push service of each device the owner turned notifications on for (Apple's for an iPhone, Google's for Chrome on Android). The owner turns them on per device in Settings; nothing is sent while no device is subscribed. The routes (`/api/push…`) are behind the session and the `Host`/`Origin` checks like every other route.

- **What the push service sees (information disclosure).** Each message is encrypted to the device's own key (RFC 8291, aes128gcm; tested against the RFC's Appendix A vector, and every pushed body is decrypted in the tests with the device's private key). The push service sees that a message was sent, when, its size (a few dozen bytes), the device's endpoint it issued itself and Botbench's VAPID public key; it cannot read the text. The text itself is fixed: "An approval is waiting", "A task is ready for review", "A task failed", "A task stopped" or "A run ended with nothing to review" (or the test notification), and the screen to open (`/#/tasks/<id>` or `/#/runs/<id>`). A failed or stopped task's reason, which can quote a command's output or the builder's last message, is never sent (tested on the decrypted body). Never a command, code, a path, a repository's name or the words of a task; KTD16 would allow the run's name, but a run has no name apart from the first line of the owner's prompt, so none is sent (tested on the payload and on the bytes as sent). The VAPID contact is a fixed `mailto:botbench@example.com`, which names nobody. Once shown, the text is on the phone's lock screen, as any notification is.
- **Keys (information disclosure, spoofing).** Botbench's P-256 VAPID key is made on first use and kept in `push-keys.json` in the data folder, owner-only (narrowed again if loosened; tested). Whoever holds it could send this owner's devices notifications that look like Botbench's, but only to endpoints they also know. Each device's endpoint and keys are in the `push_subscriptions` table of the owner-only database. Logs name only the push service's origin, never the endpoint's path, which is the device's secret (tested).
- **Where Botbench sends (elevation of privilege, SSRF).** Only to endpoints a signed-in client stored, and only plain `https:` addresses without credentials (plain HTTP only in tests, by a start option no setting reaches). Redirects are refused, and each request has a 10-second limit. A signed-in client can make Botbench POST a small encrypted body to an HTTPS address of its choice; only the owner signs in.
- **Never in the way (denial of service).** Sending is started after the approval, the task or the run is written and never awaited by them; a push service that fails, refuses or cannot be reached leaves the approval pending and answerable, and a task still fails or stops and its run still ends (tested). A task's or run's notification is first recorded in the `push_sent` table (the task or run, the fixed text and when), so the same one is never sent twice, also across a restart; when that record cannot be written, nothing is sent and the error is logged (tested). A 404 or 410 deletes that device's subscription (tested); other failures are logged and the subscription is kept.
- **Opening (spoofing, tampering).** The service worker shows only the title and opens only a path of the forms above; anything else opens the start screen. Opening a screen grants nothing: the screen asks for the session as always, and an approval is still answered on its card.
- **Served without a session.** The manifest, the service worker and the four icons, at fixed names, alongside the page and its hashed assets (as before). They hold no data. The browser fetches the manifest without credentials and the home screen reads the icons on its own, so they cannot require the session cookie; the list is exact (tested: other files beside them need a session). The service worker is served with `Content-Security-Policy: default-src 'self'`; the page's policy is unchanged (its `default-src 'self'` covers the worker and the manifest).
- **Not proven without the phone.** Delivery through Apple's push service, the notification on the iPhone, and tapping it to open the card are verified only on the owner's iPhone (AE11).

### Modes: manual, semi-autonomous and fully autonomous

A run's mode is chosen on New run (default from Settings, kept in `owner_settings`, else `autonomy.mode` in the settings file, else manual), stored on the run and never changed (trigger `runs_mode_fixed`; no route changes it). The broker reads it from the store for every request; the pre-tool hook is never told it.

**Approvals are for actions and changes, not for using a tool (owner direction, 2026-11-22).** The owner: "why are we having approvals on tools… Approvals are for actions and changes." The modes are now about the owner's decisions, not tools. In every mode, for a task, a run and a chat: reads and searches the agent may make, edits inside the copy (or the chat's folder), a confined shell command no piece of which is on the floor, the CLI's own bookkeeping tools (`ToolSearch`, `TodoWrite`), and web search and fetch where the owner's setting Web access allows it run without asking. What asks (manual, semi-autonomous) or is refused (fully autonomous) is as before: anything on the floor, a read or write outside the copy, an unconfined request or one that is not exactly what the hook reported, and any other tool. Broker failure still denies.
- **Manual**: the owner approves the plan and decides on each result. Commands are decided as semi-autonomous's were (below). A task started on its own is always manual. The owner's setting **Ask before every command** (Settings, Runs; `owner_settings.ask_every_command`, off by default, read from the store at each request; one that cannot be read counts as on) brings back a card for every shell command of a manual run or single task (`every_command`, "Ask before every command is on in Settings."); then a pre-approved command or a standing permission still runs without a card, as before. It does not change a semi-autonomous run or a chat.
- **What Manual now relies on, stated exactly.** For a command the floor does not name, nothing but the sandbox stops a write outside the copy and any use of the network: there is no card in between any more (unless Ask before every command is on). Two gaps of that sandbox are known and stay open: the CLI's shared temporary folder is writable by every confined command (it is shared by every Claude Code session of the owner, so one session can leave files another reads), and a repository with allowed hosts lets a confined command send to those hosts, the task's code included, without asking. Before this change Manual put each such command to the owner; semi-autonomous and fully autonomous already relied on the sandbox alone.
- **Semi-autonomous**: building starts on the plan as the planner gave it, without the owner's approval (`planApprovedByMode` in `src/engine/modes.ts`; the run's history says "plan approved by the run's mode, semi-autonomous"); the owner decides on each result. A run that read outside text (a GitHub issue) still waits for the owner's plan approval: a stranger's text does not start a build on its own (decision; engine-tested).
- **How a confined command is decided, in every mode** (was semi-autonomous's rule alone): a shell command runs without asking when it runs confined: the attempt was admitted as one whose driver runs every shell command in its sandbox (`confinedCommands`, true for Claude Code: sandbox on, `failIfUnavailable`, `allowUnsandboxedCommands` false), the request is exactly the call its hook reported (same command and input, a directory the hook reported), and the call carries nothing beside its command but a description, a time limit or a background flag (`dangerouslyDisableSandbox` or any unknown field asks). Each such command is logged before it runs under `mode_allowed`; what cannot be logged does not run. The floor still asks, by rule name. The floor's last rule, "not a plain command", is not read as a danger here: it exists because a chained command cannot be compared with a grant word by word, and every other rule reads each piece of a chained command. So a confined command of any shape (a pipe, a loop, `perl -0pi` or `python3 -` editing a file in the copy) runs without asking unless a piece of it is on the floor. Every attempt of the builder (its build, a round of fixes, a resume, an answer after a restart) is admitted the same way, in one place (`admitBuilder` in `src/engine/task.ts`); before that, a round of fixes was admitted as unconfined and asked about every command (found in the self-review run, run 3). Tools that are not shell commands still ask, and the ones that outlive a turn are not offered at all (below).
- **A glob or a variable in a guarded place (found in the self-review of the modes).** The floor named a guarded place only when a word's whole path was known, so `for f in ~/.ssh/*; do cat $f; done` was "not a plain command" alone and would have run confined, unasked, in semi-autonomous (the sandbox still refused the read). The floor now reads the text before a glob or a variable and asks when a guarded place lies in it or where the rest of the word could lead (`~/.ss*`, `~/*`, `/e*`, `/Users/*`, Botbench's data folder outside the task's copy); a glob inside the copy or a temporary folder does not ask.
- **The critique of these fixes (fresh context, about 560 commands through the real gate, branch against main).** No verdict became looser. It found gaps that were already there and that semi-autonomous makes matter, since a chained confined command runs unasked unless a piece is on the floor. Closed now: a program or git subcommand the shell builds (`g=git; $g push`, `git $'push'`, `git pu$@sh`, `git $(echo push)`, `git {push,}`, `=git push`, `echo push | xargs git`) asks under "program-named-by-the-shell"; a backslash-newline is joined before the floor reads (`git pu\<newline>sh`); a shell handed `/dev/stdin` or `/dev/fd/N` runs text; `osascript`, `launchctl`, `crontab` and `open` with an argument ask under "leaves-the-sandbox" (whether Claude Code's agent sandbox refuses `open` and Apple events is not tested; the setup and check profile does). Still open, each stopped by the sandbox's read, write and network rules rather than by the floor: an interpreter given code on its command line (`python3 -c`, `node -e`, `perl -e`, `awk 'BEGIN{system(…)}'`; asking for them would ask for the file edits the builder makes with `perl -0pi -e`); a path that starts with a variable (`$PWD/../../../../.ssh`, `${HOME%/}/.ssh`, `$ZDOTDIR/.zshrc`, `$'…'` quoting); a relative path after `cd` with no argument or `cd -`; places missing from the guarded list (`.zprofile`, `.zlogin`, `~/.config/gh`, `~/.git-credentials`, `~/.local/bin`, `/usr/local`, `/opt/homebrew`); the data folder compared case-sensitively; `GIT_*` set by `export` apart from git; a disk device behind a glob (`of=/dev/disk*`).
- **Fully autonomous** (unchanged by "approvals are for actions") approves its own plan as the planner gave it, refuses what would otherwise ask (a floor-listed command, an unconfined or unreadable request, a tool that is not a shell command, an edit outside the copy) without putting it to anyone, logs each refusal under `mode_refused` and tells the agent why, and accepts a task without the owner only when every check passed (so at least one ran), the review is satisfied or the run has no reviewer, nothing refused during the task blocks the accept (the refusal rule, below; a web tool refused because Web access is Off, `web_refused`, counts as a blocking `network` refusal), and the checks left no file in the copy. It refuses to start on a repository with no checks, and when the agent's commands cannot be confined. The accept is the owner's Accept made by the mode: the branch is kept, the copy removed, nothing merged or pushed; the decision names the mode as its maker with the reasons (`decided_by = 'mode'`), and the store refuses such a decision for any task not of a fully autonomous run or whose checks did not pass (trigger `decisions_by_mode_only_full`). A task that does not qualify waits for the owner with the reason on it.

**Work that outlives the turn.** In run 2 of the self-review the builder started read-only subagents in the background, asked for a 20-minute wakeup, and its turn ended while they ran: nothing was changed, and the task was offered for review. Two controls now. A background shell command (`run_in_background`) is still allowed; whatever it leaves running is killed with the attempt's process group when the turn ends. (2) A build whose branch holds no change from its base once Botbench has committed ends the task as failed ("Claude Code finished without changing any file", with the builder's last message), with no checks, no review and no Accept; the owner can resume it in the same session or discard it. - **The folder of every call is recorded.** The hook records the folder of each call it hears, by tool call id, whatever its verdict; before, only calls it answered "ask" were recorded, so a call it let pass and the CLI then asked about anyway (an edit after the agent moved into a sub-folder: the CLI's own `Edit(./**)` rule is narrower than the copy) reached the broker with no folder, could not be tied to the call that was checked, and asked. The record stays per call: a request is matched to its own call, in whatever order the requests come, and is used once.
- **File tools are decided by the broker as by the hook.** A Write, Edit, NotebookEdit or Read the CLI asks about is put to the gate with the same input the allow hands back to the CLI, so the path checked is the path used: inside the copy (links followed, not `.git` or `.claude`) it runs without asking in every mode, an edit logged under `auto_worktree_edit` before it runs; outside it asks, and in fully autonomous it is refused. Before, every request for a tool that was not the shell asked (semi) or was refused (full). A relative path or a search with no path whose starting folder was not reported asks, and so does a search with no path from a folder outside the copy (found by Codex's review). A path the CLI reads differently from a plain join with the folder it starts from is never taken as inside: Claude Code trims the path and turns a leading `~` into the home folder, so `~/.zshrc`, `~/.ssh/id_ed25519` or a path with spaces around it asks (or is refused), and its card shows where the CLI would land it (found by the integration review of #86: before, such a Write or Read was let through as a file inside the copy; tested).
- **The floor reads quotes for "program-named-by-the-shell".** The rough reading of a chained command split at `|`, `(`, `{` and the like even inside quotes, so `grep -n "admit(" src/*.ts` read `src/*.ts` as a program built from a glob and asked. That rule alone now reads each piece with its quotes (`quotedPieces`, `src/approvals/shell.ts`): an operator inside quotes does not split, a single-quoted part is literal, a double-quoted part is live. Where that reading is not sure of itself (an open quote, a backslash outside quotes) the rule reads as before; where a substitution stands inside double quotes it reads both ways. Every other rule still reads the quote-blind pieces, which only ever adds asks. Found while trying to get round the new reading, and closed: a program a substitution prints was never seen (`ls; $(echo rm) -rf x`, `ls | "$(echo rm)" -rf x`, backquotes, `FOO=1 $(…)`); it now asks under this rule. Still open, as before: a command held in a quoted argument of a chained command (`ls; env -S '$P status'`) is not read as a command by this rule (the plain form is).
- **The keychain and key tools by name only.** `security`, `ssh-add` and `ssh-keygen` ask when a word names the program: alone, by a full path, or from `~`. A relative path shown to lie inside the task's copy whose last part has that name (`docs/security`) is a file of the project, which a confined command may read, and no longer asks, but only as an argument of a program known only to read files (`ls`, `cat`, `grep`, `git` and a few more, with no `-exec`, `-c`, `-x`, `--pre`, `--extcmd` or the like in the piece, and not as the value of an option such as `--extcmd=docs/security`); given to any other program (`./security`, `env docs/security`, `stdbuf -o0 docs/security`, `find . -exec docs/security`) it asks whatever file it is (found by Codex's review); one after a `cd`, with `..`, or from a folder outside the copy (`cd /usr/bin; ./security …`) still asks, as do `env security …`, `xargs security` and `/usr/bin/security` (tested; found by the self-critique of this change, which had first let every relative path through). The bare word still asks wherever it stands, so `grep -rn security docs` asks, as `echo sudo` does.
- **The CLI's saved output of the task's own session (decision).** Claude Code saves a tool call's output that is too long to hand the model whole under `<config>/projects/<copy's path, every other character a dash>/<session id>/tool-results/` and tells the agent to Read it there; `<config>` is the configured folder, else `CLAUDE_CONFIG_DIR`, else `~/.claude`. A Read of a file inside that one folder of the attempt's own session runs without asking, in every mode, unlogged like a read inside the copy. The session id is the one the CLI reported for the attempt (`attempts.resume_cursor`, letters, digits and dashes only), read from the store for each call, never from the request; only for a Claude Code attempt; links are followed and must stay inside, and neither the `tool-results` folder nor its session folder may itself be a link (one leading to another session's output asks; found by Codex's review, tested). Everything else under the CLI's folder asks: another session's saved output, the session's transcript, settings, and a link planted in the folder that leads out of it (tested). Why it is safe enough: the file holds output of a call this session already made and was shown; a confined command cannot write under `~/.claude` (the sandbox denies it), so only the CLI writes there. Should a CLI version keep the folder elsewhere, such a Read simply asks.
- **Each card says why it asks**, in one line from the gate's reason (`askWords` in `src/approvals/gate.ts`, worded per `docs/product/voice.md`): on the always-ask list, with what the rule is about; outside the task's copy; git's own files or Claude Code's settings; a manual run; not shown to run confined; not matched to the call that was checked; a tool that always asks. It is stored with the approval (`asks_because`) and fixed by trigger. A file tool's card shows the file (`target`: relative to the copy when inside it, a full path when not), never the folder the agent stood in.

STRIDE for these changes: Tampering, a request whose path differs from the one checked: the gate decides on the very input the allow returns. Elevation, a read of another session's or project's saved output, or a link out: refused by the path and link checks (tested). Information disclosure, the saved output of a call made under an earlier grant: it was already shown to the agent; no new reach. Repudiation: edits allowed this way are logged before they run; reads, as before, are not. Spoofing of the session id: it comes from the CLI's own stdout through the driver, never from the hook message or the model.

**The refusal rule: which refusals block a fully autonomous accept.** Before, any refusal during a task handed it back to the owner, so a harmless request that happened to be refused (a read-only command whose call could not be tied to the one its hook checked) stopped the accept as a push would. A refused request never runs, whatever its kind; what the kind decides is only whether the owner must look before the task is accepted. Each refusal's kind is worked out once, when it is refused, from the request and the gate's reason (`refusalKind` in `src/approvals/refusals.ts`), and stored with its `mode_refused` entry (`action_log.refusal`, migration `refusal_kinds_and_one_task`; the store takes a kind on no other rule). One pure function decides from it (`refusalBlocksAccept`). **A refusal blocks the accept when the request was on the safety floor or would have left the confinement:**
- `floor`: a rule of the safety floor names it (every rule but "not a plain command", which is no danger of its own);
- `network`: a tool that reaches the network itself (web fetch, web search). It runs in the CLI's own process, outside the sandbox and its proxy, so no host counts as allowed for it;
- `outside_copy`: a file tool, or any tool whose input names a path, not shown to stay inside the copy (outside it, through `~`, a folder that was not reported), or one aimed at git's own files or Claude Code's settings inside it (a hook in `.git` runs outside the sandbox);
- `unconfined`: a shell command not shown to run confined that is not a harmless read-only command, one that asks to leave the sandbox (`dangerouslyDisableSandbox` or any field beside the command, description, time limit and background flag), and any request Botbench could not check or could not tie to its attempt. A refusal recorded before kinds were has none, and blocks.

**It does not block** for `read_only`, a shell command that only reads inside the copy (`readOnlyCommand`): every piece starts `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `egrep`, `fgrep`, `rg`, `stat`, `du`, `diff`, `pwd`, `echo`, `true`, or `git` with `status`, `log`, `diff`, `show`, `ls-files`, `rev-parse`, `blame` or `grep` as its first word; no option that runs a program or writes a file (`--pre`, `--output`, `--ext-diff`, `--textconv`, `-exec`, `git grep -O`/`--open-files-in-pager`, `rg -z`/`--search-zip`, `rg --hostname-bin` and the like; for git, any start of such a name too, as git takes `--outp` for `--output`); no redirection but to `/dev/null`; no variable, substitution, glob (it may match a link out of the copy), `..` (the shell takes it after following a link, which a lexical reading does not), `~`, assignment or `cd`, each found by Codex's review; after `--` every word, a dash-prefixed one too, is a path that is checked; and every word that could be a path inside the copy (an option's value included, after an `=` or attached to a short option's letter as in `grep -f<file>`, where every ending of the word after its first letter is checked, found by Codex's last review), links followed, from the folder the agent stood in, which must itself be inside. Nor for `other`: a tool that is neither the shell, a file tool, nor the network (asking the owner a question, a to-do list). The reading leans towards "blocks": a wrong "blocks" only hands a task back. A refusal that does not block is still logged, its entry in Activity says in words that it does not stop the accept ("It only reads files in the task's copy, so it does not stop the task being accepted."), the agent is told it was refused as before, and the accept's reasons name it. Tested: the matrix of kinds through the real gate (`test/approvals/refusals.test.ts`), the record through the real broker and socket (`test/approvals/broker-modes.test.ts`), and the accept with a replayed builder session (`test/engine/modes.test.ts`: a harmless refusal is accepted, a floor refusal and an unconfined one beside a harmless one are handed back).

STRIDE for the refusal rule: Elevation, an agent dressing a request up as harmless so its task is accepted: nothing refused runs, so the most it gains is an accept of work whose checks passed and whose review, if any, is satisfied, which is what the mode promises; its other requests are judged on their own, and any one that blocks hands the task back. Tampering, the kind changed after the fact: it is written with the append-only entry and never again. Repudiation: every refusal, blocking or not, is in the log with its kind and shown in Activity. Spoofing, a request of another attempt or a request Botbench cannot place: counted as unconfined, so it blocks. Denial of service is not made worse: a false "blocks" is the behaviour before this change.

**Keep it to one task.** A run may be started kept to one task (`runs.one_task`, chosen on New run in every mode, on unless chosen otherwise in fully autonomous, fixed by trigger `runs_one_task_fixed`). Its planner is told to plan exactly one task; a plan of several is sent back to the planner once; if the reply still holds several (or holds no plan), Botbench merges the latest plan of several into one task, the titles joined in order and the criteria one after another, and says so in the run's reason and its history. That one task may hold up to 200 criteria and a title as long as 20 joined, only in such a run (`validatePlan` with `oneTask`), so a merge never loses text; every criterion keeps its own limit and its plain-text rule, and the owner's edit and the approval check the plan the same way. The plan of such a run holds exactly one task: an edit that adds a task is refused, and so is storing or approving a plan of several (found by Codex's review). No new trust boundary: the merged text is the planner's own text, still data, and the builder is sent it as it is stored.

What fully autonomous removes: the owner's gate on the plan and on acceptance, and every card (what would ask is refused). What remains: the confinement, the floor (as a refusal), the checks, the append-only log, and that nothing is merged or pushed and nothing leaves the machine but what the vendor CLI sends its provider and what Web access allows. Semi-autonomous removes only the gate on the plan, and not for a run from an issue. No mode has a gate on confined commands any more, unless the owner turns on Ask before every command for manual. CLAUDE.md's "Dangerous actions always ask" holds for manual and semi-autonomous; in fully autonomous they are refused, never run.

### Grok and Antigravity as reviewers (no tools)

New boundary B12. A run may name Grok (1.0.92) or Antigravity (`agy` 1.5.14, Google's successor to the Gemini CLI) as its reviewer. Neither CLI's own sandbox can be relied on for a reviewer (ADR 0002: Grok's leaves its sign-in readable and does not block the network on macOS; Antigravity's covers terminal commands only). So the arrangement is the other way round: the model is given **no tools**, the CLI works in a new empty folder and never in the task's copy, and the **whole CLI process** runs under a `sandbox-exec` profile made by Botbench (`src/drivers/cli-sandbox.ts`). The diff is in the prompt; the prompt says the reviewer has no tools and sees only what it is sent. Everything below was measured on this Mac on 2026-11-22 with real runs, decoy files and marker files, never with a real credential.

- **No tools.** Grok: `--disallowed-tools` names every tool 1.0.92 offered (28, MCP's `search_tool` and `use_tool`, `update_goal` and subagents among them); its own `available_commands` event then lists `"tools":[]` (in the recording and in the live test). `--tools ""` does not do this: it keeps them all. Antigravity has no flag that removes tools; Botbench writes its own agent definition (`tools: []`, `subagent: false`, `mcpServers: []`, `commandExecutionPolicy: off`) into the review folder and starts it with `--agent`. Asked to run a command, read a file, list a folder and fetch a page, it was offered only `manage_task` (lists, stops or writes to the conversation's background commands; none can exist) and said it had no tool for any of them. As a second layer, `--settings` (session only, never saved) denies every action Antigravity has rules for (`command`, `unsandboxed`, `read_file`, `write_file`, `read_url`, `execute_url`, `download_url`, `mcp`); measured alone, these refused a command and a file read but let `schedule` and `define_subagent` run, so they are not the control. **Fail closed:** the driver stops the turn and kills the process group at the first line where Grok offers any tool, either CLI reports a tool call, or Antigravity starts as any agent but Botbench's. (While recording, Grok offered `update_goal` under Botbench's environment; the stop fired, and the tool was added to the list.)
- **Files named with `@` in the prompt.** Grok 1.0.92 reads `@path` in a headless prompt as a file to attach, even with `--verbatim` and with `ui.at_picker_outside_workspace = false`, and sends the file to xAI: `@/tmp/…/decoy.txt` was attached. A diff can hold such a word, so every `@` Grok is sent is written as the full-width `＠` (not attached, measured), and a line at the end says so. Antigravity did not attach an `@` path in this mode (measured), and its prompt is sent as written.
- **Nothing of the repository.** Antigravity, started in a repository, ran that repository's `.agents/hooks.json` hooks and started its `.agents/mcp_config.json` MCP server, in headless mode, with no trust asked and outside any sandbox (marker files appeared). Grok skipped a repository's hooks, MCP servers and `AGENTS.md` because the folder was not trusted. Both now work in a new folder `~/.botbench/reviewers/<random>`, owner-only, removed when the review ends; the live test puts hooks, MCP servers and rules for both CLIs in the repository and no marker appears.
- **The process sandbox.** The profile denies reading every place of the one list in `src/confinement.ts` and Botbench's data folder, then opens again only what each CLI needs: Grok its own folder (`~/.grok`, or `GROK_HOME`) and the review folder; Antigravity `~/.gemini/antigravity-cli`, `~/.gemini/config`, `~/Library/Keychains` (read only; its sign-in is in the Keychain, and it fails to sign in without it) and the review folder. Writing is denied but in those folders (not the Keychain) and the temporary folder; `lsopen` and Apple events are denied. The network stays open: the CLI must reach its provider, and with no tools that is the model's only channel. Seen: with the profile, an `@` to a denied decoy attached nothing.
- **Credentials and billing.** The environment is the allowlist every CLI child gets, with `XAI_API_KEY`, `GROK_API_KEY`, `GROK_CODE_XAI_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS` and every other key-named variable removed. Grok also gets its compatibility with Claude's and Cursor's hooks, MCP servers, skills, rules and agents turned off, and memory, workflows, subagents and updates off; Antigravity gets updates off. Botbench reads no sign-in file and no Keychain item: Grok's probe runs `grok --version` and `grok models` ("You are logged in with grok.com." is a subscription), Antigravity's runs `agy --version` and `agy -p /usage`, which the CLI answers itself with the plan's quotas (a subscription) or a sign-in link (signed out; the link is not kept).

STRIDE for B12:

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: the review passes for a check, or for the owner's decision | As for Codex: its own table, called a model's opinion, read by nothing Botbench decides | Done |
| Tampering: the reviewer changes the work, the owner's branches or Botbench's records | No tools; the CLI never works in the task's copy; the process cannot write outside its own folders, the review folder and the temporary folder; tested live (asked outright to write a file in the copy: no tool call, file absent) | Done |
| Repudiation: what the reviewer did is not on record | Its events are stored under its own attempt; a tool call, were one to appear, is stored and stops the turn | Done |
| Information disclosure: the reviewer reads a sign-in, a key or Botbench's files, or sends what it read away | No tools; `@` neutralised for Grok; the process profile denies the shared list and the data folder; tested live with a decoy in the data folder named with `@` and asked for outright: its text is in no event | Done, with the limits below |
| Denial of service: a reviewer that hangs or fails holds the task | The station's 10-minute limit, then the process group is killed; failures are recorded on the task in plain words | Done |
| Elevation of privilege: the diff or the repository steers the reviewer, or its reply steers Botbench | No tools, so the model's words are its only output; nothing of the repository is loaded; the reply is shown as text, never run or sent to the builder | Done |

What it does not cover, stated exactly: each CLI process reads its own sign-in (Grok `~/.grok/auth.json`; Antigravity the Keychain item, and the Keychain's files are readable to it) and sends the prompt to its vendor (xAI, Google); Grok's own folder, its other sessions included, is readable to Grok, and an `@` written some other way than the ASCII character, should a later Grok accept one, could attach from there; places outside the home folder that the owner can read (`/tmp`, `/etc`, `/opt`, `/Volumes`) are readable to the process; the network is open to the process, so the only control on what leaves is that the model has no tool. What could not be turned off: the owner's own Grok hooks, MCP servers and enabled plugins in `~/.grok` (none and one plugin's skills on this Mac; skills need a tool or a slash command, and the prompt is neither), Antigravity's global hooks and MCP servers in `~/.gemini/config` (no hooks on this Mac; its MCP servers start, confined by the profile, and the agent is offered none of their tools), Antigravity's always-on `manage_task` tool, and each CLI's saved record of the conversation (`~/.grok/sessions`, `~/.gemini/antigravity-cli`). A `per-model api_key` in the owner's own `~/.grok/config.toml` would bill Grok by use and cannot be seen without reading that file, which Botbench does not.

### Chat with any agent, or several at once

New boundary B13. A chat with no repository can ask Codex, Grok or Antigravity as well as Claude Code, one at a time or several at once, and can ask one of them to compare a round's answers (`src/api/chat.ts`). None of the three keeps a conversation here, so each chat message to one of them is **one turn in exactly the review's confinement**: a new empty owner-only folder `~/.botbench/reviewers/<random>` (removed when the turn ends), the same `startAttempt` options as the review station (read-only, no host, no way to ask, no edits; asserted in `test/api/chat.test.ts`), so for Codex the same read-only permissions profile with no network (the arguments differ only by the folder and `--skip-git-repo-check`, which Codex needs outside a git repository; asserted in `test/drivers/codex.test.ts`), and for Grok and Antigravity no tools and the whole-process sandbox of B12. Key variables are stripped as for every CLI child. The time limit is the review's (10 minutes), then the process group is killed. Codex keeps its read-only shell in that empty folder; it can read nothing of the owner's that a review could not.

**What newly leaves the machine.** Before this, a chat's text went only to Anthropic, through Claude Code. Now it goes to whichever vendors the owner asks: OpenAI (Codex), xAI (Grok) and Google (Antigravity), and each is sent **the chat so far, including what the other vendors' models wrote**. Claude Code is also sent other agents' replies when another agent answered since its last reply. The Agent view says so in one line ("Your message and the chat so far, with what each agent wrote, go to every agent you tick."), and its hint says the others answer from the conversation alone. Nothing else of the owner's leaves: only a chat's own attempts are read back as its conversation (`chat_attempts`), so a task's, plan's or review's transcript is never passed on, and only text (the owner's messages and the agents' replies), never tool output.

STRIDE for B13:

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: an earlier reply poses as the owner, or as Botbench | Every earlier message is set apart between marked lines and labelled with who wrote it; a model's reply is marked as another AI model's; text that would open or close a block is changed so it cannot (`dataBlock`); unit-tested with "ignore previous instructions" and a forged closing mark | Done |
| Tampering: an agent changes files or Botbench's records | The review's confinement, unchanged; the live test asks each agent outright to write a file: none is written | Done |
| Repudiation: what was sent is not on record | The framed prompt each agent was sent is its attempt's first stored event, append-only; `chat_rounds` and `chat_attempts` are append-only | Done |
| Information disclosure: a chat's text reaches a vendor the owner did not choose, or an `@` attaches a file | Only the agents the owner picked or ticked are asked; `@` is neutralised for Grok in everything it is sent, earlier replies of other agents included (unit test); the owner is told in the Agent view what goes where | Done |
| Denial of service: a slow or failed agent holds the others | Each agent's turn runs on its own, with its own Stop and time limit; a failure is stored as that agent's failed reply; tested with one agent failing and one stopped | Done |
| Elevation of privilege: a reply steers Botbench or another agent | Nothing a reply says is run; it is shown as text and passed on only as labelled data; Compare is the owner's own action, never automatic: no voting, merging or hidden turns | Done |

What it does not cover, stated exactly: each vendor keeps what it is sent under its own terms; another model's reply passed on as data can still sway the model that reads it (it can do nothing but write text); the conversation sent is capped (60,000 characters, oldest messages left out first, with a note to the agent), so a long chat is not passed on whole.

### A chat asks for your approval

Before this, a chat's Claude Code ran with no gate: `--permission-prompts none`, so everything it would have asked about was denied ("there was no way to ask you here"), which made a chat useless for anything that needs the web or a command. Now a chat's attempt is admitted to the same broker as a task's builder (`src/api/turns.ts`, `admit({ chat: true })`), started with the gate (the pre-tool hook, the `Bash` ask rule, `--permission-prompt-tool stdio`) and with `--setting-sources ""`: the agent may write in the chat folder, and a settings file it left there must not be loaded by its next turn (nor a `CLAUDE.md` handed on as instructions). It keeps the CLI's full set of tools; only the tools that outlive the turn are denied, as for every attempt. What it may do:

- **Commands** are decided as in a semi-autonomous run, so a chat is no more tedious than Claude Code used directly: a command that runs confined (the chat attempt is admitted confined; the request is exactly the call the hook reported; it carries no field beyond `command`, `description`, `timeout`, `run_in_background`) and of which no piece is on the floor runs without a card, in the chat folder, in the sandbox of "Confined commands", with no network, logged first under `chat_confined`. A floor-listed piece anywhere in the command, or anything that may take it out of the sandbox (`dangerouslyDisableSandbox`), asks, and the card says why. Before, a command outside Claude Code's own read-only class was denied, so this too is a loosening, inside the confinement. There is no grant of any kind.
- **Reads and edits inside the chat folder** run without asking, as inside a task's copy; an edit is logged first. Anywhere else they ask ("Outside the chat's folder."). This is a loosening: before, an edit in the chat folder was denied. The folder holds nothing of the owner's and is shared by the chat turns only.
- **Claude Code's bookkeeping tools** (`ToolSearch`, which loads a tool's description before its first use, and `TodoWrite`) are let pass by the hook, in a chat as for every agent, so the CLI's own rules decide, as when it is used directly; should the CLI still ask, they run. Each one that runs is logged first under `bookkeeping`; what cannot be logged does not run. They reach nothing outside the CLI.
- **Web fetch and web search** (`WebFetch`, `WebSearch`) follow the owner's setting "Web access" (Settings, Web; `owner_settings.chat_web_access`, its first name from when it was "Web access in chat"): **Allow**, the default, runs each one without a card, shows it in the transcript as an ordinary step and logs it under `chat_web_access`; **Ask** puts each one to the owner as a card; **Off** refuses each one, telling Claude Code (and the owner) where to turn it on. This is a deliberate loosening the owner asked for ("Botbench must never make an agent less capable than using its CLI directly"). What leaves the machine is the URL, to that site, or the query, to the search provider; the page text or results then go to the model provider (Anthropic) as part of the turn. The CLI makes the request itself, outside the sandbox of commands, which still reaches no host. The setting is read from the store at each request. Since "approvals are for actions and changes" it applies to a task's and a run's web tools too (decision: the simplest honest rule is one setting for every agent, rather than tying it to the repository's allowed hosts, which govern commands' network): Allow runs them logged under `web_allowed` with the task, Off refuses them under `web_refused` (which, in a fully autonomous run, keeps the task from being accepted without the owner), Ask, or a fetch of a local address, asks or in a fully autonomous run is refused. A run that read outside text does not follow the setting: each of its web tools asks, as no grant applies to it either; such a page could otherwise carry a stranger's text, or the code, to a site unasked. Allow covers the public web only: Claude Code fetches from this Mac, so a fetch whose address is not http or https, or whose host is this Mac, a local-network name (`localhost`, `.local`, `.internal`, `.lan`, a bare name) or a loopback, private, link-local, shared or unique-local address (Botbench's own port, a router, the cloud metadata address) asks even on Allow ("It reaches this Mac, your local network, or something that is not a public web page."). The local names also include `.home`, `.localhost` and the public names made to answer with the address they spell (`localtest.me`, `*.nip.io`, `*.sslip.io`, `*.xip.io`); the local addresses also include site-local IPv6 (`fec0::/10`), NAT64 (`64:ff9b::/96`, all of it), `198.18.0.0/15` and `192.0.0.0/24` (unit-tested, `test/approvals/web-access.test.ts`). The check reads the address as written and resolves nothing: any other public name whose DNS answer is a local address, or a public page that redirects to one, is not caught by it.
- **Anything else** asks.

The card stands in the chat's transcript, right after the call that asked, with Allow once, Deny and "Deny and say what to do instead"; the header's tray counts it and opens the chat; the notification "An approval is waiting" opens the chat. A chat's request never offers Always allow: there is no grant of any kind for a chat (a per-site "Allow fetches from <host> in this chat" was left out of this unit). A chat's approval has neither task nor run (`approvals.chat`, exactly one of the three, a check in the store); one left pending when Botbench stops is ended as not answered at the next start ("Botbench restarted before you answered…", `ended_unanswered`), since nothing re-drives a chat, and the store refuses to keep an answer for one.

| STRIDE | Control | State |
|---|---|---|
| Spoofing: another process answers or asks as a chat | The hook's secret is the attempt's alone, as for a task; a request that says it is a chat's but comes from no admitted chat attempt gets no setting and asks (broker test) | Done |
| Tampering: a chat leaves rules for its next turn | No settings file and no `CLAUDE.md` of the chat folder is loaded; edits to `.claude` or `.git` in the folder ask | Done |
| Repudiation: a web fetch ran without a record | Every web tool decided by the setting is logged under `chat_web_access` before it runs; what cannot be logged does not run | Done |
| Information disclosure: a URL or query leaves without the owner knowing | Allow is the owner's default by choice, stated in Settings and here; each fetch and search is a transcript step; Ask and Off are one setting away. Page text reaches the model provider only | Accepted |
| Denial of service: a card nobody answers holds the turn | The turn waits, as a task's does; Stop ends it and the card with it; a restart ends it | Done |
| Elevation of privilege: page text steers Botbench | Fetched text is a tool result the model reads; Botbench never reads it, and nothing in it is an answer to a card or a setting. It can sway the model, whose every further action goes through the same gate | Done |

What it does not cover, stated exactly: with Allow, a page the model was led to (by the owner's message, an earlier page, or another agent's reply) is fetched without a card, and its URL can carry text from the chat to that site; Off or Ask is the control for that. A fetched page can steer the model into asking for more; each such request still asks, except fetches and searches under Allow.

### Pull requests: delivering an accepted task (delivery)

New boundary B13: GitHub is a new outside party. An accepted task of a run started with "Open a pull request" (fixed when it starts; accepted by the owner, or by the run's fully autonomous mode, whose accept is recorded at the same place), or the owner's own "Open a pull request" on an accepted task that kept its branch, makes Botbench itself, on the host, push the task's branch and open one pull request (`src/engine/delivery.ts`, `src/github.ts`, `src/worktrees.ts`). Agents are unchanged: their commands are confined, the repository's shared git folder is not writable to them, and `git push` stays on the safety floor, always asked; no agent command or text starts a delivery itself: only an accept of a pull-request run (see the fully autonomous row below) or the owner's own request over the authenticated API does.

**What is sent.** The task's commits, from the commit recorded at the decision; the pull request's title (the plan task's title, one line, at most 200 characters) and body: what was asked, the acceptance criteria, each check's command and pass or fail (not its output), a Review section, the run's mode when runs have one, and a line saying it was built with Botbench. The Review section says "No review was run" and nothing else when there was none; otherwise it names the reviewer's agent and model, gives the task screen's own outcome line (`outcomeLine`, so the two cannot differ), the number of reviews and of rounds of fixes, the last review's findings (at most 10 lines, with how many more were left out), the builder's "Not addressed, and why" lines from the last round of fixes when there are any, and who accepted: the owner, with the owner's note when one was given, or the run's fully autonomous mode, with its recorded reasons. So the reviewer's findings, the builder's reasons and the owner's note now leave the machine with the pull request, on the remote the owner chose for it (the mode's reasons are Botbench's own words). Every piece of text the owner, the planner, the builder or the reviewer wrote, and the model's name (the owner may type it), is put in a fenced block longer than any run of backticks inside it, so no mention, issue reference, closing keyword, link or image in it acts on GitHub, and no fence in it can close the block (unit-tested with reviewer, builder and owner text holding "@someone", "Fixes #1" and fences: none of it is outside a fence, `test/engine/pull-request-body.test.ts`). Nothing else: no diff text, no transcript, no evidence output.

**The commands, exactly.** Each is an argument list with no shell, in its own process group, with a time limit after which the group is killed (git: 2 minutes; gh: 1 minute), prompts off (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, no controlling terminal), and Botbench's own environment (the owner's) without any `GIT_*` variable and without `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN`, so git's credential helper and `gh` use the sign-in they keep. Botbench reads no token and no file of `gh`'s.

- `git -c core.hooksPath=/dev/null -c core.fsmonitor=false config --get remote.<remote>.url`, `git remote get-url <remote>` and `git remote get-url --push <remote>`: where the remote is; no network. A remote that pushes to another address than it fetches from is refused, as the remote's branch is asked where git fetches.
- `gh auth status --hostname=<host> --active --json=hosts`: who is signed in (that JSON holds no token).
- `gh repo view <host>/<owner>/<name> --json=nameWithOwner,defaultBranchRef`: the default branch.
- `git ls-remote --refs <remote> refs/heads/<branch>`: what the remote's branch holds.
- `git push --porcelain --no-verify --no-follow-tags --recurse-submodules=no --no-signed <remote> <commit>:refs/heads/<branch>`: never `--force`, `--force-with-lease`, `+`, `--mirror`, `--all`, `--tags` or `--delete`; the source is the recorded commit, so a branch moved after the check is not what is sent; hooks of the owner's repository do not run. Tested: with `push.followTags` set and an annotated tag in the repository, only the branch reaches the remote.
- `gh pr list --repo=… --head=<branch> --state=all --json=number,url,state,headRefName,isCrossRepository --limit=100`, then, only when it lists none of this repository's own, `gh pr create --repo=… --base=<base> --head=<branch> --title=<title> --body-file=-`, the body on standard input. Every value is joined to its flag with `=`; branch names are checked against a plain pattern, so nothing an agent wrote can become an option of `gh`.
- Never `gh pr merge`, `gh repo delete`, `git push --delete` or a push to the base or default branch.

**Checks before anything is sent**, each a plain refusal recorded on the task ("Nothing was sent."): the task is accepted and its branch kept; the branch has Botbench's own prefix (`botbench/`, not the old `smelt/` and not the owner's); the repository has the remote (`origin`, or the repository's `remote` setting); that remote's address is a GitHub repository; the branch is still at the commit recorded at the decision; `gh` is installed and signed in for that host; the branch is neither the base (`baseBranch` setting, else the default) nor the default branch. A remote whose branch of the same name holds other commits, when Botbench asks, is refused even when a push would only fast-forward it (tested: the remote's refs are unchanged). Between that question and the push there is a moment in which a branch created on the remote at an earlier commit would be fast-forwarded by the plain push; nothing can be overwritten, as the push is never forced. The pull request's own arguments (base branch, title) are checked before the push too. The owner's confirmation names the remote, the branch and the address it showed; an address changed since is refused. More than one push address, or a push address other than the fetch address, is refused.

**Exactly once.** The ledger `deliveries` (migration 19) is append-only (triggers refuse update, delete and `INSERT OR REPLACE`), takes rows only for accepted tasks, and refuses a second pull request for a task. The request is recorded after the checks and before the push; the push and the pull request (opened, or found already there) after each. A delivery started again (Try again, or the next start after a restart, which takes up every task whose ledger ends at a request or a push) asks the remote first and pushes only when it lacks the branch, and asks GitHub for a pull request of the branch in any state before opening one; tested with a restart between the push and the pull request (one push in the remote's reflog, one pull request), and with captured gh output for a pull request already there (adopted, none opened). The live test shows the ledger refusing a second delivery and GitHub listing one pull request. A start also takes up a pull-request run's accepted task whose ledger is empty (Botbench stopped between the decision and the first check; tested). Two deliveries of one task at once are refused in the process, and one that ends unexpectedly is recorded as failed, with Try again.

**Credentials in addresses.** A remote's address may carry `user:token@`. Every sentence Botbench stores, logs or shows that holds an address or git's or `gh`'s words passes through one redaction (`scheme://***@`), the ledger, the action log, failures and the confirmation's address included (tested with a token in the address: it is in no row). Botbench never puts a token on a command line: commands name the remote, not its address.

| Threat | Mitigation | Status |
|---|---|---|

What it does not cover, stated exactly: the owner's own git configuration still applies to the push (`url.*.insteadOf`, credential helpers, `core.sshCommand`; a `pushurl` that differs is refused): Botbench pushes where the owner's git sends that remote. The remote's own hooks and GitHub's rules run on GitHub. `gh` itself talks to GitHub with the owner's sign-in and its scopes, which can do far more than Botbench asks of it. A pull request already there for the branch, in any state and by anyone, is taken as the task's. Stand-alone tasks get no automatic choice; the owner's "Open a pull request" works for them. Updating an existing pull request with new commits, merging, comments, and hosts other than those `gh` signs in to are not built.

### Intake: a run started from a GitHub issue

New boundary B14: the people who write a GitHub issue are a new outside party. Until now every word a planner or builder was given came from the owner (a prompt or a spec file the owner named), or from the repository and models already treated as data. An issue's title, text and comments can be written by anyone who can open or comment on an issue in that repository, and are aimed at a model on purpose. (`src/engine/intake.ts`, `src/github.ts`, `src/api/issues.ts`.)

**How it is read.** Only when the owner names one issue in the composer's From an issue view: its number, `#number`, or its address on the same repository the composer chose (an address on any other host or repository, a pull request's address, or anything else is refused in words before `gh` is started; unit-tested). The repository is the one its delivery remote (`origin` unless its settings say) names on GitHub. Botbench runs the owner's own `gh issue view <number> --repo=<host/owner/name> --json=number,title,body,author,state,url,labels,comments`: an argument list with no shell, the number checked to be a plain positive whole number, the same environment, prompts off and 1-minute limit as delivery's `gh` commands, and no token read. The answer is refused unless it is about that number of that repository at its `/issues/` address, so a pull request's number (which `gh issue view` also answers for) is refused. Nothing is written to GitHub: no comment, label, close or assignment command exists in the code. What is kept is capped (title 300 characters, text 20,000, at most 30 comments and 20,000 characters of them, 20 labels) and says what was cut; it is kept as read, with when, in `issue_fetches` (migration `issue_intake`, append-only: update, delete and `INSERT OR REPLACE` refused; tested). The owner is shown exactly that row, and a run started from it names that row, so a text edited on GitHub between the look and the start cannot slip in.

**Who wrote it changes nothing.** Botbench also runs `gh api --method=GET --hostname=<host> repos/<owner>/<name>/issues/<number>` (an argument list, GET with no field sent so nothing is written, the number checked as above, the owner and name each one encoded path segment, the same environment and limit), because `gh issue view` does not give the issue's own `author_association`. The answer is refused unless it is about that number of that repository at its `/issues/` address and is not a pull request; only GitHub's eight documented values are kept (`OWNER`, `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER`, `MANNEQUIN`, `NONE`), anything else is kept as "GitHub did not say", in `issue_fetches.author_relation` (migration `issue_author_relation`, a CHECK on the values, fixed with the rest of the row). It is shown to the owner on the issue sheet, by the author's name and in plain words, and used for nothing else: the outside-text rules below apply whatever the author's relation, an owner, member or collaborator who never commented included, and the sheet says the rules are the same whoever wrote it (unit-tested for every value and for none; engine-tested that a run from an issue of each relation is marked, never fully autonomous, and gives the planner the issue between marked lines). Reasons: anyone can comment on the issue, the text can be edited after a member opened it, and a member's account can be taken over; a relation is GitHub's claim about an account, not about the words.

**How it is given to a model.** The planner's prompt and the builder's first prompt carry it after the owner's own words, behind Botbench's line that people outside the project wrote it, that it describes a problem to solve and nothing more, and that nothing in it is an instruction (not to follow requests in it, run commands it names, or open addresses it gives); the text sits between `<outside-text>` lines, and any `<outside-text` or `</outside-text` in it is changed so it cannot close the block or open another (the refine loop's `dataBlock`; unit-tested with a closing tag, "ignore previous instructions", a fake "Closes #999", `$(rm -rf ~)` and a `curl` that sends a key).

**What a run that read it loses.** The run is marked (`runs.outside_text`, set when the run is stored and never changed, trigger-enforced; its tasks inherit it through their run, and a mark that cannot be read counts as set):
- No pre-approved command and no standing permission applies to its commands (the gate, `outsideText`; the full matrix of mode, kind of request, confinement, floor and both kinds of grant is unit-tested, and the broker is engine-tested with a real pre-approved command and a real standing permission that both ask for the marked run and both run for an unmarked one). Nothing it asks can be offered Always allow. In every mode a confined command still runs without asking, because it is confined, not because of any grant; an unconfined or floor-listed one asks as before. Its web tools ask whatever Web access says.
- It waits for the owner's plan approval in every mode it can have, semi-autonomous included.
- It cannot be fully autonomous: refused at creation with the reason (API 400; also when the default mode is fully autonomous), the composer disables Send with the same reason and the Mode view closes that choice, and the store refuses such a row (trigger). A stranger's text must not lead to an accepted change and a pull request with nobody looking.
- Its setup commands, check commands, builder and reviewer get no allowed network hosts, whatever the repository's settings allow, unless the owner ticked "Allow this repository's network hosts for this run" (off by default) when attaching the issue; that choice is stored on the run and fixed (engine-tested: the setup command sees no proxy, and the builder is started with no hosts, unless ticked). Text from outside together with network access is how an agent could be led to send the code away. Ticked, the hint under the box, the run's mode line and its tasks' say the hosts are allowed and name them, as the repository's settings list them when the screen is read (API- and unit-tested), so no screen says the network is off when it is not.
- The run, its tasks and each of its approval cards say it read an issue ("Outside text").

**The one piece Botbench acts on.** A pull request of such a run says `Closes #N` (or `Closes owner/name#N` when opened on another repository), built from the stored number and repository alone, once; nothing the issue says is put in the body, so a closing keyword or mention in the issue does nothing (engine-tested with an issue whose title and text hold other closing references). The pull request's title is the plan task's title, written by the planner, which read the issue: it stays one line in `--title=`, as before, and the branch name and commit subject are Botbench's own (`botbench/run-N/task-N`, "Botbench task N: …" passed to git as one argument).

**On screen.** The issue is shown as plain text: React writes it as text, no markdown is drawn, no link or image in it is made or fetched (browser-tested: the markdown shows as written, the preview holds no image, link or heading from it). The link to the issue on the run and task screens is the address Botbench checked when it read it.

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: issue text poses as the owner or as Botbench to the planner or builder | Botbench's line before it, the `<outside-text>` block it cannot close, the owner's words in their own `<work>` block; nothing in the text is read by Botbench | Done (unit-tested). A model may still be persuaded; what it then does goes through the gate as below |
| Spoofing: an issue of another repository, or a pull request, is taken for the one the owner named | Only a number, or an address on the same repository; the answer must be that number's `/issues/` address there | Done (unit- and API-tested with captured gh output) |
| Spoofing: an issue opened by a member's account (taken over, or edited or commented on by others) is trusted as the project's own words | The author's relation is shown to the owner and changes no rule: the run is marked as outside text for every relation | Done (unit- and engine-tested for every relation). The `gh api` answer's shape is checked against the real gh only by the live test, `test/live/issue.live.test.ts` |

What it does not cover, stated exactly: a planner or builder that is persuaded by the issue can still write bad or hostile code inside its copy, and in manual and semi-autonomous a confined command runs without asking (with no network unless ticked); the owner reviews and decides, as for any run. The planner's task titles and criteria, which the owner approves, may echo the issue. Bidirectional-text and look-alike characters in the issue are shown as they are. Only the comments `gh issue view` returns are read (GitHub's first page of them). Watching a repository for new issues, labels as triggers, posting back to GitHub, and other trackers are not built.

### Peers: named workbenches that see each other's work (P1, P2, P3)

Two developers each run their own Botbench on one repository and share its GitHub remote. (`src/workbench.ts`, `src/engine/peers.ts`, `src/api/peers.ts`, `src/worktrees.ts`, `src/github.ts`.)

**P1: a workbench has a name, and its branches carry it.** No new boundary. Each installation has a workbench name: the settings file's `workbench` when set, else the one kept in the data folder (`workbench_names`, append-only: update and delete refused by trigger; the name checked by a `CHECK` too), made once from the host name at first start and changed only in Settings. The name is held to `^[a-z0-9](?:[a-z0-9-]{0,28}[a-z0-9])?$` everywhere it is set (settings file, Settings, store), since it becomes part of a git ref. New task branches are `botbench/<workbench>/<run>/<task>`. A task branch is one of exactly three forms, and nothing else (`parseTaskBranch`; unit-tested with `botbench/../x`, upper case, over-long names, extra levels): the named form, `botbench/<run>/<task>` from before workbenches had names, and `smelt/<run>/<task>` from before the rename (never pushed). Decide, Discard and delivery each refuse a branch in the named form whose name this installation never had (every name it has had stays in the table, so a rename keeps old branches its own), before anything is removed, deleted or sent: another workbench's branch is never deleted, discarded, pushed or adopted here (engine-tested with real git). Pull requests are adopted only by exact head branch, which is this task's own. A remote branch of another workbench has another name, so it neither blocks a delivery nor is touched by one (engine-tested: two stores, one bare remote, run 1 task 1 each). The pull request's body names the workbench ("Built on <workbench> with Botbench"); the name is Botbench's own, checked text.

What is not covered: two installations given the same name (two Macs with the same host name, or a copied settings file) are one workbench to each other: their branches can collide on the remote again, and delivery then refuses to overwrite, as before. Each sees the other's work as its own in P2's view (it is left out).

**P2: each workbench sees the others' work, read only.** New boundary B15: what other workbenches (other people's installations) put on the shared remote. Read with the owner's own `gh` and `git`, never written: `gh pr list --repo=<host/owner/name> --state=open --json=number,title,url,state,headRefName,isCrossRepository,closingIssuesReferences,files --limit=100` (an argument list with no shell, the same environment, prompts off and 1-minute limit as every `gh` command, no token read) and `git ls-remote --heads --refs <remote> refs/heads/botbench/*` (the remote name checked as for delivery, the safe git options, a 20-second limit, its process group killed after it). The view is per repository, kept for one minute, and read in the background: the Work screen, the composer and the task screen ask for it after they are drawn, and its failure (no GitHub remote, `gh` not signed in, no network) is a plain sentence that hides the section; nothing waits for it, and Send is never disabled by it.

Everything read there is outside text: titles, branch names, file paths, another workbench's name. A pull request is kept only when GitHub's answer gives it at `https://<host>/<owner>/<name>/pull/<number>` of this very repository, not a fork's (`isCrossRepository` false); its number must be a whole number; the address shown is made by Botbench from the repository and the number, not taken from the answer; a title is cut to one line of at most 300 characters, control characters removed; at most 100 paths of at most 500 characters each; an issue it closes counts only when GitHub names this same repository, and only its number is kept. A branch counts only when it matches the task branch pattern (which also gives the workbench's name, so the name is checked). Nothing of it is passed to git or `gh`, put in a prompt to an agent, or stored. On screen React writes it as text; the link opens GitHub in a new tab with `noopener noreferrer`.

STRIDE for B15:

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: a fork's pull request, or one on another repository, poses as a workbench's | Only this repository's own pull requests, at its own address; a fork's is left out | Done (unit-tested with captured gh output and with crafted entries) |
| Spoofing: somebody pushes `botbench/<this-name>/…` to look like this installation's own | It is left out of the view, as this installation's name; it is never decided, pushed or deleted here unless one of this installation's own tasks names it, and a delivery that finds another commit on its branch refuses, as before | Done, and the case of two installations with the same name is stated above |
| Tampering: a branch name, title or path becomes a git or `gh` argument or markup | None of it is ever an argument; a branch name must match the pattern; React text only | Done (reviewed; the only arguments are the repository, from the remote's address, and the fixed pattern) |
| Repudiation | Nothing is written, so nothing to attribute | n/a |
| Information disclosure | Only what GitHub already shows the owner, read with the owner's own sign-in; nothing is sent | Done |
| Denial of service: a huge list, a slow GitHub or remote | At most 100 pull requests and 100 files each, capped text; time limits on `gh` and `git`; one minute of caching; nothing waits for it | Done |
| Elevation of privilege: another workbench's text steers an agent or Botbench | Never placed in a prompt, never acted on; the composer and review lines are warnings for the owner only | Done |

What it does not cover: a warning is best effort. An issue the owner's message names is matched by its `#number` only; a branch pushed without a pull request says nothing about its issue (P3 makes taking an issue visible); overlapping files are compared by path, and no merge is tried (P4).

Since P3 the list is read with `--state=all` (same fields and limit): a pushed branch whose pull request was merged or closed is left out of the view rather than shown as having none. The list holds the latest 100 pull requests; when gh's answer holds 100 entries (counted before the parser drops a fork's or an unreadable one), each remaining pushed branch (at most 20) is asked about on its own with the read-only `gh pr list --head=<branch> --state=all` delivery already uses, and one that has a pull request, could not be asked about, or is past the 20 is left out. Each row of Other workbenches names the shared repository as GitHub names it, never this Mac's folder name for it.

### Peers P3: claiming an issue with an early branch push

(`src/engine/claims.ts`, `src/engine/claim-branch.ts`, `src/worktrees.ts`, `src/engine/delivery.ts`, `src/config.ts`, the `issue_claims` and `claim_takeovers` tables.) A new write to the shared remote, crossing B15 outward, and a new delete there. It is off unless the owner sets `"claimIssues": true` for a repository in the settings file; with it off a run from an issue writes nothing to the remote or GitHub (engine-tested against a real bare remote, with gh asked nothing). With it on, a run started from an issue, attached with "From an issue" or named once in the message by its `#number` (the composer's spotting rule; a message naming none or several claims nothing), pushes one branch as soon as the run is stored, with the owner's own git and the push permission delivery already uses.

- **What is pushed.** `git push --porcelain --no-verify --recurse-submodules=no --no-signed --no-follow-tags <remote> <commit>:refs/heads/botbench/<workbench>/run-<N>/issue-<number>-at-<YYYYMMDD>T<HHMMSSmmm>Z`, never by force. The commit is made by Botbench for the claim: the empty tree, no parent, Botbench as author, a fixed message naming the workbench, the issue number and the run. No file of the repository and none of the owner's unpushed commits leave with it. The branch name is built from checked parts only (the workbench name's pattern, the run id, a whole issue number, the clock).
- **Where it may go.** The remote must be written as a GitHub address, fetch and push to one address, and git's rewrite rules must send it either to that same GitHub repository or to a folder on this Mac. A rewrite to another GitHub repository, another host, or anything Botbench cannot read as either (an unparsable destination no longer passes) is not claimed on, and says why.
- **Why a branch, not an issue comment.** No new `gh` command and no write to the issue (src/github.ts writes nothing to an issue): a comment would notify the issue's watchers, outlive its deletion in the issue's history, and carry the owner's GitHub account rather than the workbench's name. The other workbenches already read the remote's branches with `git ls-remote`; the name carries the issue number and the time it was made, so nothing else is read.
- **The earliest claim wins.** The remote's claim branches for the issue are read again just after the claim is pushed, before a delivery pushes the task's branch, and before it opens the pull request. Ordered by the time in the name, then the workbench name, then the run number, the same on every workbench. A run that finds an earlier claim of another workbench withdraws: its own claim branch is deleted by the delete rule below, and the run is stopped (at the start), or nothing is pushed, or no pull request is opened (the task's branch, already pushed, stays). Engine-tested with two stores and two clones of one real bare remote: at most one pull request. Not closed: two pushes in the gap between one workbench's read and the other's push both stand as branches until a later read; and the time is each workbench's own clock, so a clock set wrong wins or loses wrongly. Closing that needs an atomic ref per issue, which Botbench's rule of pushing only a task's own branch forbids.
- **Taking over an old claim.** The composer offers it for another workbench's claim at least an hour old on the run's issue, behind a confirm that names the holder. The server checks the same from the name (another workbench's, this issue, an hour old) before the run is stored, and stores the take-over with the run. It only leaves that claim out of the comparison; the holder's branch is never touched.
- **Release, and its delete rule.** When the run ends without a pull request (cancelled, failed, or done with no pull request opened and none on its way: an accepted task of a run that opens pull requests with no delivery step yet, or any delivery not ended in a failure, keeps the claim; a failed delivery releases it), the branch is deleted only when all of these hold: its name parses as a claim under a name this installation has had; `git ls-remote` shows it still at the commit this workbench recorded; and the owner's `gh` (read only, `gh pr list --head=<branch> --state=all`) finds no pull request for it in any state. The delete itself is `git push … --force-with-lease=refs/heads/<branch>:<commit> <remote> :refs/heads/<branch>`: the lease forces nothing (a delete needs no force); it is git's compare-and-delete, so a branch moved between the check and the delete is refused by the remote. Anything that cannot be checked (remote unreadable, `gh` failing, no GitHub remote) leaves the branch in place and says why. Engine-tested with real git and a bare remote: release; refusal for a moved branch, another workbench's branch, and one with a pull request; the lease refusing a delete at the wrong commit.
- **After a restart.** Each start releases, by the same rule, the claims still held by runs that ended without a pull request while no Botbench was there to release them (engine-tested: one action-log row each).
- **Failure never blocks.** No remote, no network, a refused push (including a branch of that name already there) or a remote that is not the GitHub repository it is written as is recorded as `not_claimed` with a plain sentence on the run's screen, and the run goes on (engine-tested). A read of the claims that fails holds nothing up either.

| Threat | Mitigation | Status |
|---|---|---|
| Spoofing: somebody pushes a claim under another workbench's name, or with an early time | A claim warns the owner and can make a later claim of this workbench withdraw; it never makes Botbench write or delete anything of anyone else's. ### Peers: direct messages between paired workbenches (P5)

Planned, not built. New boundary B16: another person's Botbench, which can now send this one bytes directly. The decisions are in `docs/adr/0004-peers-direct-messages.md`. In short:
- **The listener.** A second listener (the peer listener) is off by default and bound only to the loopback, private or carrier-grade address the owner names in the settings file. It has four routes (pair, message, settings, end) and no access to the owner's API or session.
- **Identity.** Each workbench has an Ed25519 key. Every message is signed and checked against the key stored at pairing.
- **Pairing.** Pairing takes a one-use, 15-minute invite, a pairing key that is safe to retry, an answer the inviter signs with the key named in the invite, and both owners' confirmation of each other's fingerprint. The invite's secret is kept owner-only while the invite is open and erased when it is used or expires. Ending refuses the pairing's id, so a new invite can pair the same two keys again.
- **Scope.** A pairing covers one repository and gives no access to files, credentials, tasks, transcripts, diffs or the store.
- **Messages.** There are eight typed kinds, with at most 3 round trips per thread. Messages are stored append-only and are idempotent by message id.
- **Incoming.** An incoming message is outside text and only ever becomes a card for the owner. Work the owner gives it to is marked under the Intake (B14) rules.
- **Outgoing.** Every outgoing message of the eight kinds, the owner's or an agent's draft, leaves only after the owner presses Send on a card that shows its exact text. Fully autonomous runs send nothing. Only protocol traffic of a fixed shape leaves without a Send: the pair request and its answer, acknowledgements, refusals, settings notices and the end notice. Each is logged and carries no text from an agent or the repository.

Every test named below uses real SQLite, a real temporary git repository with a bare remote, real HTTP, and real child processes: two Botbench processes started as separate installations on this Mac, each with its own data folder. None uses a mock, a fake peer or a fake CLI. An agent's draft comes from a session captured from a real CLI run and replayed through the driver contract, as the hard rules allow. The live test (`test/live/peers.live.test.ts`) has a real Claude Code draft a question once.

- no A2A;
- no more than two peers;

- no change to P3 claims or P4 shared checks.

**What this section does not cover**, stated exactly:
- **The network.** Messages are signed, not encrypted. Confidentiality on the wire is the private network's, or loopback's on one Mac. Anyone on that network can see the text of messages and can reach the listener, though not get past its signatures.
- **The key.** The key in the data folder is as strong as the folder. A process of the owner's account can read it and act as this workbench to its peer, as it can already read the login token.
- **The fingerprint check** is only as good as the owners' comparison of it.
- **A modified peer** can send anything a signed message can carry. The receiving end's checks are the control, not the sender's.
- **What the owner sends.** An outgoing draft can carry repository text or a secret the agent read. The owner reads the card, and nothing else stands in the way.
- **A persuaded agent.** A peer's message given to an agent can persuade it as an issue can, within the B14 limits and the cards.
- **Not built.** A relay, a second Mac, more than two peers and A2A are not designed here. Each needs its own decision record and an update of this section.

### Scope: files changed outside the plan, and protected paths

No new boundary: a control on what a builder already writes inside its task's copy (`src/engine/scope.ts`, `src/engine/task.ts` `handOver`, `src/config.ts`). Before a task is Ready for review, Botbench reads the files its work changed, from the task's start commit to its head commit, with the same git call the task screen uses, and marks each one: protected, when it lies under a path the owner's settings file names (`protectedPaths`, at the top level for every repository and per repository; relative paths only, no `..`, `*` or leading `/`, refused at start otherwise); and not expected, when neither the task's own words (its title and criteria, or the owner's prompt) nor the check commands that ran on it name it or a folder it is in, nor a test of the plan's links to it by name. A protected file holds the task for the owner in every mode, with a reason naming the files, and a fully autonomous run never accepts it; a file not expected also stops a fully autonomous run's accept. The owner's own Accept is not refused by either. The reviewer is given the full list of changed files and asked to flag any that do not belong (`reviewerPrompt`), inside an escaped data block, since file names are the builder's.

| Threat | Mitigation | Status |
|---|---|---|
| Tampering: a builder edits a protected file (recordings, licences) and a fully autonomous run accepts it | The paths come from the owner's settings, never from the repository's own files or the task's branch, so the builder cannot remove the protection; a protected file is never accepted by a mode | Done (engine-tested in manual, semi-autonomous and fully autonomous) |
| Elevation of privilege: a builder makes an unrelated file read as expected, to be accepted without the owner | Only words the owner wrote or chose are read: the plan, the prompt and the configured checks. An issue's text, the agents' replies and the contents of changed files are never read for this. A builder that adds a test file only makes test files expected when the plan asks for tests; a test it adds leads to another file only when the plan or the checks name that test | Done (unit-tested); the rule is a heuristic from names, stated in the code |
| Tampering: a file name closes the reviewer's list and writes instructions | The list is set apart with `dataBlock`, which escapes the tag | Done (unit-tested) |
| Repudiation | The reason is stored on the task's history with its move to Ready for review, beside the action log's entries | Done |
| Information disclosure | Nothing new leaves the machine; the file names were already on the task screen and in the reviewer's diff | n/a |
| Denial of service: a builder changes many files | The reasons name the first 20 and count the rest; marking is a pass over names | Done |

What it does not cover: "expected" is a heuristic. A file the plan names loosely (by a word that is not a path) reads as not expected, which only costs a fully autonomous run its accept; a file named in the plan for another reason reads as expected. Protected paths are folders or exact files: no patterns.

### Moving an installation from before the rename (Smelt to Botbench)

The product was called Smelt. On start, before anything opens the store, an installation in the old default folder `~/.smelt` is moved to `~/.botbench` (`src/store/move-home.ts`). No new boundary is crossed: the files moved are the owner's own data folder, and git runs only `worktree repair`, against repositories the store already names as task sources, with the same safe options and time limits as every other git call.

- **Nothing is lost or duplicated (tampering, denial of service).** The folder and the database (journal files first) are renamed, never copied or deleted; a rename is atomic on one file system and keeps the owner-only modes. Only when no variable names the data folder is the old default a candidate, so a test or a second instance with its own `BOTBENCH_HOME` can never move the owner's data. If both folders exist the new one is used and the old one is left as it is. A move that fails stops the start and says what to do; a start stopped half-way is finished by the next one (a marker holding the old path moves with the folder).
- **Git's links follow the folder.** Stored worktree paths under the old folder are rewritten to the new one, and `git worktree repair` points each source repository's record and each worktree's `.git` file at the new place; until that has succeeded the marker stays and each start tries again, because a `git worktree prune` against a stale record would cut a task's copy off from its repository.
- **Old names for one release.** `SMELT_HOME`, `SMELT_PORT`, `SMELT_CONFIG` and a git-ignored `smelt.local.json` are read when the new names are absent, each with a line on stdout; the new names win. The old `smelt_session` cookie is not a session: a browser that holds only it is signed out.

### Connecting an agent (U26)

From Settings the owner can connect a signed-out agent and disconnect a signed-in one. Botbench starts the CLI's own sign-in (`claude auth login --claudeai`; for Codex, ready to register, `codex login --device-auth`) through `launch`, with the same allowlisted environment as a turn, key variables removed, `BROWSER=/usr/bin/true` so no window opens on the Mac, in its own process group. It reads the vendor link (only `https` on the definition's own hosts, no user, password or port) and, for a device code, the code from what the CLI prints, and returns them only in answers to the session-protected connect routes. Claude Code's page shows a code after sign-in that the CLI reads on its input; the owner pastes it in the sheet and Botbench writes it, checked as one line of code characters, to that input and keeps nothing. The CLI exchanges it and keeps its own credentials. Success is the CLI ending with exit 0 and its probe then saying signed in; no output is read to decide it. Disconnect runs the CLI's own sign-out (`claude auth logout`).

STRIDE for B10:
- **Spoofing.** Every connect route needs the owner's session (tested, 401 for each). A link the CLI prints that is not on the vendor's hosts is not shown (tested), so output steered elsewhere cannot send the owner to another page through Botbench.
- **Tampering.** The driver name in the path is a slug, matched against the agents Botbench knows (404 otherwise). The pasted code cannot carry a line break, a blank or a shell character, and goes to the CLI's input, never a command line or a shell. The commands and arguments are fixed in code.
- **Repudiation.** Connecting and disconnecting are not in the action log: the log is for what agents do, and writing a sign-in there is what this unit must not do. Accepted.
- **Information disclosure.** The link, code and pasted code are in memory only, dropped from the answer when the sign-in ends, never in the database, the event log, Botbench's log or the live updates (the update says only the agent and the state). Tested by searching every file of the data folder, every table and the process's output for the sign-in's unique value. The code is a short-lived secret visible to whoever holds a session, which can already do far more. The pasted code passes through Botbench on its way to the CLI: it is bound to the CLI's own PKCE verifier and useless without it, and it is the "relay its code" the hard rule allows; Botbench never sees the credential the CLI gets for it.
- **Denial of service.** One sign-in per agent at a time (409 for a second start, and for a sign-out while one runs); the CLI has 30 seconds to print its link and the owner 15 minutes to finish, after which its process group is killed; output kept is capped at 64 KB; a cancel, the time limits, the end of the process and Botbench's close each kill the whole group (tested with real processes, live with the real CLIs: nothing is left).
- **Elevation of privilege.** A stolen session could disconnect the owner's agent and connect it to a vendor account of its own, so the owner's later tasks would run on that account, or just disconnect the owner's agent (the confirm dialog is the only extra step). Accepted, as for the other routes of a stolen session. A sign-in that can only finish in a browser on the Mac is shown as "Sign in on the Mac" with the command; Botbench does not work around it.
### Dictation (voice input)

The phone posts a recording; Botbench converts it with ffmpeg and transcribes it with its Swift helper over macOS's on-device speech recognition, and answers with the text. STRIDE for B11:

- **Spoofing.** The route needs the session like every other; the gate answers 401 before reading anything. Tested.
- **Tampering (cross-site requests).** It is the one write route whose body is not JSON. The exception is narrow: only `POST /api/voice/transcribe`, only the content types `audio/mp4`, `audio/x-m4a`, `audio/webm`, `audio/ogg`, `audio/wav`, `audio/x-wav`, `audio/wave` (anything else is 415 before the body is read), and the same Host and Origin checks as every write. A form on another site cannot send these types, a cross-site `fetch` with them needs a preflight Botbench never answers, and the cookie is `SameSite=Strict`. Tested: another site's Origin gets 403.
- **Tampering (the converter and helper).** No request data reaches a shell or a file name: the upload is written to `recording` in a new owner-only folder from `mkdtemp`, and both programs get an argument list. The content type only picks one of four fixed ffmpeg readers (`-f mov|matroska|ogg|wav`), so a body that is really a playlist, a concat list or an image is not opened as one, and `-protocol_whitelist file` keeps ffmpeg to plain files. A playlist naming `file:///etc/passwd` sent as `audio/mp4` is refused as not audio. Tested. ffmpeg's own parsers still read attacker-shaped bytes, with the owner's rights; that is the residual risk, as for any media file the owner opens.
- **Repudiation.** Not logged, by design: nothing about a recording or its text is written to the database or the log. Tested by searching every file of the data folder and the captured log for the spoken words after a transcription.
- **Information disclosure.** The recording and the WAV live only in the per-request folder under the system temporary folder (per-user on macOS), removed in a `finally` after success, a refusal, a failure and a time-out; tested for each, the time-out with a named pipe that never delivers. Recognition is on the device: the system service had no sockets open while it ran, and Apple documents the API as on-device. The text goes back only to the device that sent the recording. Error messages carry the helper's first error line, never the transcript.
- **Denial of service.** A recording is capped at 16 MB while it is read (413, tested with a small cap) and at 5 minutes after conversion (413, tested with a small limit); one transcription runs at a time per signed-in device (409, tested); the conversion and recognition together have a 90-second limit after which the process group is killed (504, tested, and no process is left). A body that arrives slowly is bounded only by Node's own request time-out (5 minutes); during it, that device's next recording gets 409. Several signed-in devices can each run one at once.
- **Elevation of privilege.** The helper is compiled from `src/dictation/helper.swift` in the checkout Botbench runs from, into `dictation/helper-<hash of the source>` in the data folder, owner-only. Anyone who can write the checkout or the data folder could change what runs; they can already change Botbench itself. The child processes get the allowlisted environment (`buildChildEnv`), so no provider key reaches them.

## Signed-in devices

A sign-in now lasts on its device: the cookie carries `Max-Age` of 90 days, and the session is kept in the database, so a restart or an update of Botbench signs nobody out. Built against OWASP ASVS V3 (session management), in proportion to one owner.

- **Cookie.** `botbench_session=<secret>; Max-Age=7776000; HttpOnly; SameSite=Strict; Path=/`, plus `Secure` when the request came through a configured HTTPS name (as before). A session used more than a day after it was last renewed gets a fresh 90 days: the row's expiry moves and the same cookie is sent again with its new `Max-Age`. A session unused for 90 days expires. Tested on loopback and through the public host.
- **Secret.** 32 bytes from `node:crypto` `randomBytes` (256 bits), base64url, a new one for each sign-in. It is in the cookie and nowhere else: the table `browser_sessions` holds its SHA-256 (hex), the device label, and when it was created, last used and expires. A request's cookie is hashed and looked up by its hash, then compared with `timingSafeEqual`. A copy of the database therefore signs nobody in (tested: the stored hash sent as a cookie is refused; the secret is in no file of the data folder, the write-ahead log included, and in no line Botbench logs).
- **Writes.** The last-used time is written at most once a minute. Expired rows are deleted at start and when an expired cookie is met.
- **Device label.** Read once at sign-in from the `User-Agent` by a small fixed parser ("iPhone · Safari", "iPhone · Home Screen app", "Mac · Chrome", else "Browser"). Only those fixed words are stored, so a crafted header cannot put text on the screen. It is a hint for the owner, not an identity: a browser can claim any label.
- **Ending a session.** `GET /api/devices` lists the devices (id, label, times, which is the requester's own; no hash). `POST /api/devices/:id/sign-out` and `POST /api/devices/sign-out-others` delete rows, behind the session and the `Host`/`Origin`/JSON checks like every write. Botbench keeps each session's requests in flight, the event stream included, and ends them when their row is deleted, so a signed-out device loses its live updates at once (tested). Signing out this device also clears its cookie (`Max-Age=0`).
- **The login token.** Sessions are not tied to the token, as before this change. When the owner replaces the `login-token` file, Botbench reads the new one at its next start and only it signs in from then on; devices already signed in stay signed in. To end those too, use Sign out everywhere else, then sign this device out or keep it. Changing the token is never needed to stay signed in.
- **Unchanged.** The `Host` allowlist, the `Origin` check, the JSON-only bodies and the global sign-in slow-down. The database is in the data folder, which no confined command may read (tested with the real database file and its write-ahead log).
- **Password managers.** The sign-in form has a fixed, hidden username "Botbench" (`autocomplete="username"`) beside the token field (`autocomplete="current-password"`), and the page loads again after a successful sign-in, so a browser's password manager can offer to save the token. The token then sits in the owner's password manager, under the owner's control.

## What can still run without the owner (U7)

Stated exactly, for a task's attempt on Claude Code 2.1.322:

- **Edits and reads inside the worktree** run without asking, by design, also when the CLI asks about one itself (after the agent moved into a sub-folder). Edits are logged before they run; reads are not logged. Writes to anything named `.git` or `.claude` at any depth, also through a link, are sent to the owner, and so is a search whose pattern is absolute or contains `..`.
- **A Read of the CLI's saved output of the attempt's own session** (`…/projects/<copy>/<session>/tool-results/`) runs without asking and is not logged; nothing else under the CLI's folder does (see Modes).
- **Shell commands** never run unasked, except confined ones the floor does not name, in every mode (unless the owner turned on Ask before every command, for manual), the ones the owner pre-approved for that task's run when starting it (U9) and the ones the owner gave standing permission and has not taken back (U10) (see Modes). All are logged before they run.
- **Web search and fetch** follow the owner's setting Web access (Allow by default), except in a run that read outside text and for a local address; each that runs is logged before it runs. **The CLI's bookkeeping tools** (`ToolSearch`, `TodoWrite`) run.
- **Other tools** (sub-agents, scheduling and messaging tools the CLI ships, and any it adds) are sent to the owner by the hook. If the hook fails for such a call (it crashes, or takes more than 20 seconds because Botbench is stalled), the CLI's own default applies to that one call, and for a tool the CLI runs without a prompt that means it runs. The ask rule covers only `Bash`. Narrowing the CLI's tool list is the fix; it was not part of U9 and is still open.
- A command the owner allows, pre-approved or gave standing permission runs in Claude Code's sandbox (U27): it cannot read the vendor sign-ins, the Keychain, keys, cloud credentials, Botbench's data folder or the rest of the home folder, can write only the worktree and a temporary folder, and reaches the internet only at hosts the repository's settings allow. Within that it runs with the owner's rights. Measured on 2026-11-22 before U27: such a command could read a vendor sign-in from the Keychain; with U27 the same lookup fails (live-tested). What the confinement does not cover is listed under "Confined commands". One container per task (U28) is the next step.

## Open items, most serious first

1. Checks run agent-written code on the host. Since U27 they are confined (no sign-ins, keys, Botbench files or network but allowed hosts, writes only to the worktree), but they can read the rest of the owner's home folder and print it into evidence. The owner should point Botbench only at repositories they trust. Confinement rests on deprecated macOS Seatbelt and works on macOS only.
2. The stop-on-API-key guard is untested on its failing path.
3. Sign-in slow-down is global. A session lasts 90 days from its last use (sliding), so a stolen cookie works until the owner signs that device out in Settings or it goes unused for 90 days; replacing the login token does not end it.
4. Any signed-in client can start chat turns in Botbench's chat folder. Since "A chat asks for your approval" they go through the gate like a task's: a confined command the floor does not name runs (`chat_confined`), any other command asks, edits and reads inside the chat folder run, and Claude Code's web tools follow "Web access in chat" (Allow by default). A chat's approval left pending when Botbench stops is ended at the next start, not kept.
5. On a failure of the pre-tool hook, tools other than the shell fall back to the CLI's own defaults for that call (see "What can still run without the owner"). A CLI update that dropped Botbench's settings object would be noticed only after one shell command had run.
6. Across a restart (U8): an answer the owner stored is lost if Botbench stops again before it is applied (the task is then interrupted and says so), and so is the unanswered half of a task with two parked requests of which one was answered. After a resume the task screen shows only the resuming attempt's transcript, which opens with Botbench's own prompt under the label "You"; the earlier attempt's events stay in the store. If the resumed agent does not repeat its call, the stored answer is discarded, never applied to something else. `stored_answer_applied` is logged before delivery: if the CLI dies in that instant the answer is spent and nothing ran.
7. The repository's instructions are handed to the CLI in a file in an owner-only temporary directory, removed when the CLI process exits. A Botbench that is killed outright leaves that copy behind. The text goes in as appended system prompt, which is more weight than the CLI gives the file when it reads it itself.
8.

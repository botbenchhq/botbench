# Botbench threat model (STRIDE)

Scope: Botbench as built through units 1 to 13 and unit 27, plus the boundaries the plan adds next. Update this file in the same pull request as any unit that adds or changes a trust boundary.

## What is being protected

- The owner's repositories and working trees.
- The owner's vendor logins and subscription allowance.
- The owner's machine: files and commands outside a task's worktree.
- Botbench's own records: transcripts, evidence, approvals, the action log.

## Trust boundaries

| # | Boundary | Trusted side | Untrusted side |
|---|---|---|---|
| B1 | HTTP API | Botbench process | Any client: browser, phone, other local processes |
| B2 | Vendor CLI child process | Botbench process | The CLI, and the model's output that steers it |
| B3 | Repository content | Botbench process | Files, settings and hooks inside a target repository |
| B4 | Data directory `~/.botbench` | The owner's account | Other local accounts |
| B5 | Model provider | The owner's choice of vendor | Network, and what the vendor retains |
| B6 | Push service (unit 23) | Botbench process | Apple and Google push relays |
| B7 | Permission broker socket `broker.sock` in the data directory (U7) | Botbench process | The pre-tool hook the CLI runs, every command an agent runs, any other process of the owner's account |
| B8 | The confinement of commands (U27): Claude Code's sandbox, and macOS `sandbox-exec` for the commands Botbench runs itself | The owner's account outside the sandbox: Botbench, the CLI process, its hook | Every shell command an agent runs, every setup and check command, and every process they start |

### How a tool call is decided (U7)

A task's Claude Code is started with Botbench's own settings object on the command line (`--settings`), no settings files (`--setting-sources ""`), the edit rule `Edit(./**)`, and `--permission-prompt-tool stdio`. Three things then stand between a tool call and its running:

1. **The pre-tool hook** (`src/approvals/permission-proxy.ts`, matcher `*`). The CLI runs it before every tool call. It asks the broker over B7 and prints `ask`, `deny`, or nothing. It never prints `allow`. Edits and reads inside the worktree pass (nothing printed); every shell command and every other tool gets `ask`.
2. **The CLI's own rules.** The only allow rule is file edits below the worktree. An ask rule for `Bash` makes every shell command ask even when the hook did not run; a hook's answer cannot get past it.
3. **The permission prompt**, which the CLI sends to the driver on its stdout and the driver answers on its stdin. It becomes an approval row and waits for the owner. Only `POST /api/approvals/:id` with a session resolves it.

The socket answers one question (pass, ask or deny) and has no message that allows a call or answers an approval. The owner's decision travels only inside the Botbench process and down the CLI's own stdin.

### An approval across a restart (U8)

An approval that is pending when Botbench stops, by a shutdown or a kill, stays pending. The next start marks it parked (`parked_at`), stops what is left of its attempt's CLI process, and leaves its task at `building` without re-driving it. Nothing waits in the new process, so the owner's answer cannot be handed to anyone: it is stored on the approval (`stored_decision`, with the log entry, in one transaction) and the approval stays `pending`. Botbench then starts a new attempt that resumes the same CLI session in the same worktree and tells the agent, in words marked as Botbench's, to make its unanswered call again. The stored answer is given to that attempt's request only if all of these hold:

- the request comes from the attempt the engine admitted as resuming the attempt that asked, for the same task and role;
- tool, command (the text the card showed) and worktree-relative directory are equal to the stored ones, and the directory was reported by the hook;
- the approval is still `pending` with that stored decision, and the log holds the owner's decision for it.

The approval is moved to `allowed` or `declined` and the use logged (`stored_answer_applied`) in one transaction before the answer goes to the CLI, so one answer is given at most once, whatever fails afterwards. If the resuming attempt's first request is anything else, including one Botbench itself refuses, or the turn ends without a request, the stored answer is discarded: the approval ends `superseded` with a `stored_answer_discarded` entry, and the new request is an ordinary new card. A request the run's pre-approved list allows counts as "anything else" here: it runs, and the stored answer is discarded (tested). A stored answer survives no further restart: the next start discards it and marks the task interrupted with the reason.

### Pre-approved commands and the safety floor (U9)

When the owner starts a task, the request may list commands that task's run may use without asking (`preapproved`). They are stored as grants in the same transaction as the task row. A grant is the command's words, the role, the source repository's real path, the directory relative to the worktree (always its top in this unit) and the run. Grants are never changed or removed. Nothing is granted that the start request did not list: the per-repository list in the config file is only what the New task screen offers for the owner to confirm or edit.

The gate (`src/approvals/gate.ts`) is a function of the request, the grants and the floor. For a shell command it goes in this order:

1. **The floor** (`src/approvals/floor.ts`), a table of named rules, tried in this order: `recursive-delete-outside-worktree` (`rm -r`, `find … -delete`, `rsync --delete…`), `git-push` (any word after `git` that is `push`, `send-pack`, `send-email`, `http-push` or `dcommit`), `git-config-override` (`-c`, `--config-env`, `--exec-path`, a `GIT_…=` word, any `git config`), `sudo` (`sudo`, `doas`, `su`), `download-into-shell`, `shell-runs-text` (`sh -c`, `-s`, `--rcfile`, `eval`), `recursive-permissions-outside-worktree` (`chmod`, `chown`, `chgrp`, `chflags` with `-R`), `disk-tool`, `guarded-place`, `not-a-plain-command`. A command under any rule asks, whatever is granted. How the rules read:
   - Every word is looked at as if a program could start there (`env sudo`, `xargs rm -rf`, `find -exec`), and program names are compared without case. An argument with a space in it is read as a command of its own (`env -S 'sudo ls'`, `git submodule foreach 'git push'`).
   - A path is inside the worktree only if it is strictly below it as written and with links followed. A `..` is never followed, `~user`, `~+` and `~-` are never inside, and an operand may start with a dash (`rm -rf sub -x/../..`).
   - `guarded-place` asks for any word, any value after `=`, or any value glued to a one-letter option (`-o/path`) that points at: the shell profiles (`~/.zsh*`, `~/.bash*`, `~/.profile`, fish, oh-my-zsh), `~/.ssh`, `~/.gnupg`, the keychains and login items, `~/.gitconfig`, `~/.config/git`, `~/.npmrc`, `~/.netrc`, `~/.aws`, `~/.kube`, `~/.docker`, `~/.claude`, `/etc`, the cron tables, the home directory itself or a folder that holds one of these, and Botbench's own data directory outside this task's worktree (its token, database and other tasks' worktrees). The keychain and SSH key tools ask by name.
   - The config file can add entries (`floor`): a program and words that, found in that order after it, make a command ask. An entry cannot take the name of a built-in rule, and no route changes the floor.
2. **Is it one plain command?** (`src/approvals/shell.ts`). The command is split into words only if it consists of words separated by spaces, with single- or double-quoted parts. Any of these anywhere outside quotes makes it not plain: `;`, `&`, `|`, `<`, `>`, `(`, `)`, `{`, `}`, `$`, a backtick, a backslash, `*`, `?`, `[`, `]`, `#`, `!`, `^`, `%`, a word starting with `=` (also after an empty quoted part), a tab, a line break or any other control character, and every character outside printable ASCII (other spaces, look-alike punctuation, invisible characters). Inside double quotes `$`, a backtick, a backslash and `!` do the same; an open quote does too. A command that is not plain is never matched. Two things the shell still does to a plain word are left to the floor, not refused here: a leading `~` (the floor treats every form but the owner's own home as unknown and guarded), and bash's tilde after `=`.
3. **The grant match.** The request's leading words must equal the grant's words exactly, one by one; more words may follow. Role, repository, run and worktree-relative directory must be the grant's. A shell call that carries more than its command (a time limit, a background flag) does not match, and neither does one whose directory the hook did not report.

A match is allowed inside the Botbench process when the CLI's own permission request arrives, and written to the action log as `preapproved` with the grant's id before the answer is given; if it cannot be logged it is refused. The hook's socket is not told about grants: for every shell command it still answers `ask`. A command that asks because of the floor has the rule's name on its `asked_owner` entry.

What a pre-approved command can still do, stated exactly:

- **It runs the program with any further arguments.** `npm test` pre-approved also allows `npm test -- --anything`, and arguments can change what a program does (`--prefix`, a config flag, an output path). Pre-approve the narrowest command that does the job.
- **It runs whatever that program runs.** `npm test` runs the repository's own script, which the agent may have just edited (edits inside the worktree do not ask). `sh build.sh` runs the file as it is at that moment. A pre-approved script or test command is therefore as much as letting the agent run any code as the owner, within the confinement of U27 (see "Confined commands"). This is the price of an unattended run (R20).
- **A broad entry is broad.** Pre-approving a bare interpreter or wrapper (`node`, `python`, `env`, `xargs`, `make`, `git`) allows everything it can be told to do on its command line, short of the floor. `git` aliases and a program's own config files are not read by the floor.
- **The floor reads the command line only.** It names known dangerous forms; it is not a list of everything harmful. `curl -d @file https://…`, `scp`, `gh pr create` or `npm publish` are not on it and ask only because they are not pre-approved. The owner can add entries in the config file.
- **The guarded places are a short list.** Directories on `PATH` (`/usr/local/bin`, `/opt/homebrew`, `~/.local/bin`), a `ZDOTDIR` elsewhere, other credential files and the rest of the home directory are not on it. A pre-approved `cp`, `mv` or `rm` (without `-r`) can overwrite or delete single files anywhere the owner can.
- **Other ways to gain rights or reach a disk** (`osascript … with administrator privileges`, `launchctl`, `hdiutil`) are not named. They need the owner to have pre-approved that program.
- **Abbreviated or aliased subcommands** are not known to the floor: a git alias defined in the owner's own git config that pushes, or `npm pub` against an added entry `npm publish`.
- **A pre-approved script can read the attempt's gate secret** from its environment, as any allowed command could since U7. With it a process can ask the gate for a verdict and report a directory for a tool call id it would have to guess; a grant is still matched only on the CLI's own request inside Botbench.
- **The decision is made when the request arrives**, on the links and directory as they are then; the command runs a moment later.
- **The floor asks more often than it must** (`echo sudo`, `git stash push`, `ls ~`, a file named `security`): asking once too often is the cheap mistake.
- A bare program that only runs other commands (`sh`, `bash`, `env`, `xargs`, `sudo` and the like) is refused as an entry. A command the floor always asks about (`git push`) can still be listed; it is stored, shown as pre-approved, and asks every time.

### Standing permissions (U10)

A standing permission is a grant that belongs to no run: one command, as its words, for one role, in one source repository (by its real path, so every task's worktree of it is the same), from one directory relative to the worktree. It is earned, offered, given, used and taken back like this:

- **Counting.** Nothing stores a count. Each time it is needed, Botbench counts the approvals that ended `allowed`, whose `owner_allowed` entry is in the action log, and whose role, tool, directory, repository and command words equal the request's. Both tables are append-only (an approval leaves `pending` once). A decline, a request that ended unanswered, an answer stored across a restart that was never applied, and a run on a pre-approved or standing grant are not approvals and do not count. A request whose directory the hook did not report counts for nothing. Approvals from before a standing permission for the same key was taken back do not count: what was taken back is earned again from nothing.
- **The offer.** A pending card carries an offer only when the broker, from its own records, finds all of: the request waits in this process (not one parked by a restart); it is a `Bash` call whose shown command is one plain command (`src/approvals/shell.ts`); the floor does not name it; it could be a pre-approved entry (no leading variable or option, not a bare program that only runs others, at most 500 characters, reads back as the same words); it is not one of the forms that are never eligible (below); its directory was reported, is written plainly, and is inside the worktree with links followed (the hook's directory is recorded with links followed); no standing permission for it is in force; and the count has reached `autonomy.offerStandingAfter` (default 3; the config loader and the broker both refuse anything but a whole number of at least 1). A request the floor names, or that is not plain, never offers, however often it was allowed (AE6). Tools other than the shell are never offered: a grant for a tool's name would allow any input, and the floor reads command lines only.
- **Never eligible, though not on the floor** (`standingProblem` in `src/approvals/grants.ts`; a standing grant of such a form, however stored, is not matched either): a command with a `~` in any word (the reading drops quotes, so `cat '~/x'` and `cat ~/x` are the same words and only a shell knows which is the home directory); a program that runs the command handed to it (`env`, `xargs`, `nice`, `timeout`, `exec`, `find` and the like); a program that reaches beyond the machine or changes what starts on it (`curl`, `wget`, `scp`, `rsync`, `ssh`, `nc`, `gh`, `docker`, `kubectl`, cloud CLIs, `open`, `osascript`, `crontab`, `launchctl`); an interpreter handed its code on the command line (`-c`, `-e`, `--eval`, `-p`, and `awk`, `sed`, `jq` always); and any command with a word `publish`, `push`, `deploy`, `release`, `upload`, `login`. This is a list of known forms, not of everything that sends data away: a script or a test command can do all of it (next list), and a program not named here is eligible. These still ask every time and can be allowed from each card.
- **Giving.** Only `POST /api/approvals/:id` with `{ "decision": "allow", "standing": true }` and the owner's session gives one. The flag asks; the broker decides eligibility again, inside the transaction that also marks the approval allowed, stores the grant, and writes `owner_allowed` and `standing_granted` (with the grant's id). If any of it cannot be written, none of it is and the card still waits. An ineligible card answers 409 and is neither granted nor allowed. The scope granted is computed from the approval's own row, which cannot be changed once written, and its task's repository: nothing a client sends names a command, a repository, a directory or a role. In the client the offer is a secondary control below Allow that opens a statement of the scope and does nothing until that is confirmed.
- **Use.** The gate asks the floor first, then the grants. A standing grant matches only a request whose words are exactly the grant's, no more, with the same role, repository and directory, on a call that carries nothing but its command, from an attempt whose directory the hook reported. It is honoured only if it names no run, was not taken back, and the log holds its `standing_granted` entry. The use is written to the log as `standing` with the grant's id before the answer is given; if it cannot be logged the request is refused. The transcript says the command ran on standing permission, not that the owner allowed it.
- **Taking back.** `POST /api/grants/:id/revoke` with the owner's session adds a row to `grant_revocations` and a `standing_revoked` log entry in one transaction. Grants and revocations are never changed or removed (triggers, which with `recursive_triggers` on also refuse `INSERT OR REPLACE` on every append-only table; tested); a grant is taken back once; only a standing grant can be. Grants are read from the store for every request, so the very next request asks. `GET /api/grants` lists what is in force with how often and when each was used, counted from the log.

What a standing permission can still do, stated exactly:

- **It outlives the task.** Unlike a pre-approved command it applies to every later task of that repository for that role, until the owner takes it back. Injected text in any such task can make the agent run it as often as it likes, with no card.
- **It runs whatever the command runs at that moment.** `npm test` runs the repository's script and `sh build.sh` the file, which the agent may have just edited without asking. A standing permission for a script or test command is as much as letting agents in that repository run any code as the owner. The same price as a pre-approved command, paid for longer.
- **Exactly the words, and nothing about the environment.** No further argument is allowed, but the files the command reads, the branch the worktree is on and the environment are not part of the grant.
- **The repository is a path.** A task stores its repository's real path when it is started, and grants and counts compare that stored path; a link pointed elsewhere afterwards carries nothing over (tested). A different repository later placed at the very same real path inherits the grant.
- **Words, not quotes.** Two spellings that split into the same words are the same command for counting and for the grant (`npm  test`, `'npm' test`). The one case where quoting changes what a shell does with a plain word, a leading `~`, is never eligible.
- **Three approvals may be one afternoon.** The count has no time window and does not look at which tasks the approvals came from; an agent that asks for the same command repeatedly in one task reaches the number as soon as the owner has allowed it that often. Every one of those is the owner's own Allow.
- **The Trust screen is read when it is opened.** It does not follow the stream: a permission used or given in another tab shows after a reload of the screen.
- **A stolen session can give and take back.** It could already allow any card; with an eligible card it can also make that allow permanent. It cannot make a card eligible except by allowing real requests of an agent, and cannot grant what the floor names.
- **A process that rewrites the database file** can forge a grant together with its log entry, as it can forge the rest of the log: accepted, as before. The floor still applies to a forged grant (tested).

### Runs, the planner and the plan gate (U11)

New boundaries: a client names a file for Botbench to read (the spec), a planner agent reads a repository, and what the planner writes becomes the tasks later agents are given.

- **The spec file path (information disclosure, denial of service).** `POST /api/runs` takes `specPath`, behind the session like every route. Botbench reads it only when it is a full path whose real location is a regular file named `.md`, `.markdown` or `.txt`, outside Botbench's own data folder, at most 200,000 bytes, with one name only (a hard link is refused: it could be a second name for a file in Botbench's folder), valid UTF-8 with no NUL. The path is resolved once, the real path is opened with no-follow and non-blocking flags, the open file is the one measured and read, a pipe or device is refused without being read, and the whole read ends after 2 seconds. A refused file's content is never echoed. The repository and the spec are checked before a run row or a worktree exists. What remains possible: whoever holds the owner's session can make Botbench read any text file with one of those endings that the Botbench process can read, see it again through `GET /api/runs/:id`, and have it sent to the model provider as the planner's prompt. That is the feature; the session is the control. A read that stalls in the file system past the limit keeps one of Node's file threads busy until the system lets go.
- **The planner is read-only (elevation of privilege, tampering).** Enforced three times over. (1) At launch: Claude Code is started with `--tools Read,Glob,Grep,Bash` and `--disallowedTools Write,Edit,MultiEdit,NotebookEdit`, so the model has no tool that writes, fetches or starts an agent, and with `--setting-sources ""` so no settings, hooks or MCP servers of the repository or the owner load. (2) At the gate: the planner's admission is read-only, so the pre-tool hook is answered "deny" for every tool but Read, Glob, Grep and the shell, also inside its worktree, and "ask" for every shell command; the CLI's own request for any other tool is refused in the broker as well, should the hook not have been heard; its request is then decided with no grants at all (a run's pre-approved list belongs to the implementer role, and a planner's request earns no standing permission), so every command becomes a card under the role `planner`, naming the run. (3) By place: it works in a detached worktree of the base commit under the Botbench home, on no branch, never the owner's checkout, removed with `--force` when planning ends however it ends; at every start, before any planner works, every planning worktree still under the home is removed, whatever its run says by then. A shell command the owner allows runs in Claude Code's sandbox (U27) with no network, the repository's allowed hosts never applying to the planner; reads inside the worktree are not asked about.
- **Plan content is untrusted model output (tampering, injection).** The reply is parsed as JSON from its last fenced block and validated (1 to 20 tasks, a one-line title of at most 200 characters, 1 to 10 one-line criteria of at most 500, none holding a line break, control character or direction override, so the owner approves the text the builder is sent); anything else goes back to the planner once and then fails the run with the reason. Titles and criteria are stored as text and rendered as React text children, never as markup, and are never run or read as instructions by Botbench. Repository text can steer the planner (prompt injection): the result is still only a plan, which the owner reads, edits and must approve before any task row exists. The owner's prompt, the current plan and feedback are set apart in the planner's prompt as data. An approved task's title and criteria become an implementer's prompt in unit 12; that agent is behind the gate and the floor like any other.
- **The plan gate (tampering, repudiation).** A plan changes only while the run waits for approval: the engine refuses otherwise (409) and triggers on `plan_tasks` refuse it in the store. Every edit, approval and request for changes names the plan version it saw; a stale window is refused, so what is approved is what was on screen. Approval, its task rows and its event are one transaction; two approvals at once yield one. Run events are append-only, runs are never deleted, and a trigger keeps an ended run ended and an approved plan closed. A cancel that arrives while start-up recovery is at work stands: recovery moves only a run that is still planning.
- **Restart.** A run found `planning` at start is failed with the reason (or returned to approval with its plan as it was), its planner process stopped, its pending cards ended, its worktree removed. An approved run's queued tasks are left queued by the task engine's recovery.

### The build line and setup commands (U12)

New boundary: commands Botbench runs itself, outside the permission gate, in a worktree. An approved run's tasks are now built: one at a time, in plan order, each in its own worktree from the run's base commit, after the repository's setup commands.

- **Setup commands are the owner's, run by Botbench (elevation of privilege, tampering).** They come only from the owner's settings file (`repositories.<path>.setup`), which no route writes; a client cannot add, change or reorder one, and nothing an agent or a repository writes becomes one. They do not pass through the gate: the owner configured them, so asking the owner about them would only ask the owner to approve their own settings. Each runs as `/bin/sh -c <command>` with the owner's rights, in the task's worktree, with Botbench's environment less every `GIT_*` variable (as for Botbench's git calls), no input, in a process group of its own. They are run before any agent of that task has started, in a worktree freshly made from the base commit, so what they run is the repository's own code as the owner committed it. Since U27 each runs confined (see "Confined commands"): it cannot read the owner's sign-ins, Keychain, keys, cloud credentials or Botbench's data folder, can write only its worktree and a temporary folder, and reaches only the hosts the repository allows, through Botbench's proxy. It gets the allowlisted environment a CLI gets, not Botbench's whole environment.
- **A worktree that already holds agent-written files.** Setup runs only in a worktree no agent has worked in: a new one, or, after a restart or the owner's Resume (U15), one whose setup was stopped before the task named any attempt. An agent is sent its prompt only after its task names its attempt (a CLI started just before that is stopped on start, unprompted), so a task with an attempt is never set up again: only its turn is re-driven (tested with a setup that is not repeatable). Check commands (unit 13) always run agent-written code; see below.
- **Time limits and leftovers (denial of service).** Each command has a time limit: 10 minutes, or the `timeoutSeconds` the owner gives it (1 to 86,400). When it passes, the whole process group is killed with `SIGKILL` and the command is recorded as timed out; the task fails with the reason, before any agent starts. When the command ends by itself, whatever it left running in its group is killed too. A cancel or a shutdown stops a running setup command the same way and records it as stopped. Tested with a real script that leaves a background child (gone afterwards, checked with `ps`). What escapes: a process that leaves the group on purpose (`setsid`, a daemon that double-forks) is not followed.
- **A Botbench that is killed outright (closed, U15).** Setup and check commands run in process groups of their own, so they outlive a `SIGKILL` of Botbench. Each is recorded in `command_processes` before it starts, with its process group and the time it was started once it runs and its temporary folder, and the row is closed in the same transaction that stores its evidence. On the next start, before any task is taken up or committed, every open row's group is stopped if it is still that command's (the same check as for a CLI: the machine has been up since the record and the leader began no later than it, times read in UTC, or the leader is gone while members remain; never on the bare number, and never when no start time was recorded), its temporary folder is removed (only a `botbench-command-*` folder directly in the system's temporary folder), and the command is recorded as stopped by the restart. Evidence stays append-only: the stopped command keeps its row, and the list is run again from the start as the next round. A task one of whose commands could not be stopped is stopped for the owner with nothing more run or committed in its copy. Tested with real surviving groups, a leaderless group, and an unrelated process under the recorded number.
- **Evidence (repudiation, tampering).** Each command's text, outcome, exit code or signal, the last 200,000 characters of its combined output, its limit and its times are one row in `evidence`, which triggers keep append-only (update, delete and `INSERT OR REPLACE` are refused; tested). Output is shown as text, never as markup, and is not sent anywhere. What setup writes into the worktree is committed by Botbench with the agent's work unless the repository ignores it: an output that holds a secret is then on the task's branch.
- **One agent per worktree, one task at a time.** The line is one queue for every task of every run and every task started on its own; a task's worktree is made only when its turn comes, and a task waiting for the owner's answer holds up the tasks after it. Tested: the second task's worktree does not exist while the first is building, and stays absent while the first waits on an approval.
- **Cancel after approval.** The run and its tasks not yet started are cancelled in one write; the task at work has its setup command or its turn stopped, what it did committed to its branch, and is recorded as cancelled; finished tasks keep their branches; the run's pending approvals are closed as superseded, never allowed. A task cancelled while its worktree was being made has that unused worktree and branch removed again. A cancelled run stays cancelled (a trigger keeps an end an end).
- **Restart (U15).** A task that was at work when Botbench stopped (killed or shut down) is taken up again once, from where it was: its setup again from the start (no agent had started), its agent's turn re-driven from the session it reported (or with the task's own prompt when it reported none), or its checks again from the start on the committed work, nothing a check left being committed. The count is in the store (`tasks.restarts`), so a second restart stops the task for the owner, its turn's work committed, and no loop is possible; the owner's Resume (409 for a task in any other state, or with no copy left, or being discarded) sets the count to 0 and takes it up the same way. A run being planned is planned again once, from the start, in a fresh read-only copy, and fails the second time (`runs.restarts`). The run then goes on with its tasks that had not started. A task parked on an approval across a restart holds up its run until it is resumed.

### The verify station: check commands (U13)

After a task's builder finishes and Botbench has committed its work, Botbench runs the repository's configured check commands in that task's worktree, the same way it runs setup commands (owner's settings only, `/bin/sh -c`, own process group, time limit of 10 minutes or `timeoutSeconds`, killed with the group at the limit, on a cancel and on shutdown, leftovers in the group killed when it ends).

- **Checks run code the agent may have just written (elevation of privilege).** `npm test` runs the test files and the `package.json` scripts the agent may have edited, on the host, with no card. The approval gate does not stand in front of it: the owner configured the command, the agent chose what it does. Since U27 checks run confined, as setup commands do (see "Confined commands"): they cannot read the owner's sign-ins, Keychain, keys, cloud credentials or Botbench's data folder, can write only the worktree and a temporary folder, and reach only allowed hosts. They can still read the rest of the owner's home folder and print it into evidence, and do anything the confinement allows. The task and run screens say so beside every check result: "Checks run this repository's own commands on the agent's work, on this Mac, in a sandbox: they cannot read the sign-in, key and credential folders Botbench keeps them from or Botbench's own files, can change files only in this task's copy and a temporary folder, and reach the internet only at hosts allowed for this repository in Botbench's settings file. They can still read the rest of your home folder. The agent may have changed the code they run, so read the output, not only the result." Point Botbench only at repositories you trust, and read the diff before accepting.
- **A check cannot forge its own result into the work (tampering).** Checks run after Botbench's commit; nothing they write is committed, so the branch is what the builder produced. What a check prints is stored as text and shown as text. A check can still lie about passing (exit 0); the output and the diff are the evidence.
- **Evidence is immutable (repository).** Check rows go into the same append-only `evidence` table as setup rows (migration 11 rebuilds it to allow the new kind, keeping every row and id, and puts the triggers back; tested from a literal copy of the version 10 schema). The task's `checks` mark (passed, failed, none) is written once; a trigger refuses changing or clearing it. A timed-out check counts as not passed. A repository with no checks is marked `none` and shown as "No checks are set up for this repository", never as a pass.
- **Restart and cancel.** A task found at Checking on start is ended as interrupted with its committed work; nothing a check left in the worktree is committed. A cancel stops the running check (recorded as stopped) and ends the task as cancelled.
- **Files a check leaves behind** (coverage output, caches) stay uncommitted in the worktree. Unit 14's decisions list them and remove them only once the owner confirms; see below.

### Decisions: accept and reject (U14)

New boundary: a client request now deletes things in the owner's repository: a task's worktree, the files in it, and, for a reject that discards, the task's branch. The routes are `POST /api/tasks/<id>/accept` and `POST /api/tasks/<id>/reject`, behind the owner's session and the `Host`/`Origin` checks like every other route.

- **Only Botbench's own things are removed (tampering, elevation of privilege).** The worktree removed is the task's stored path, and only after the same check every worktree operation makes: a linked worktree of that repository, on a Botbench task branch, whose git folder is the repository's own entry. A copy already removed by hand is forgotten by its own path only (`git worktree remove --force <path>`); nothing repository-wide is pruned, so the owner's own worktrees on a drive that is not mounted keep their records (tested). A branch is deleted only when it is a Botbench task branch (`botbench/` or the old `smelt/` prefix), still points at the commit Botbench made, and is checked out nowhere but the task's own copy; all three are checked before anything is removed, so a refused reject changes nothing (tested for a commit added by the owner and for the branch checked out in the owner's own worktree). The delete itself is `git update-ref -d <ref> <commit>`, an atomic compare-and-delete, so a commit added in the meantime keeps the branch. Accept and a reject that keeps the branch are refused when the branch is no longer there, so the screen never offers a merge of a branch that does not exist. Nothing is merged, pushed or written to the owner's checkout or current branch (tested: the checkout state is unchanged after accept and both rejects). No path, branch or file name from the request reaches git: the request carries the decision, keep or discard, and the list of files the owner confirmed, which is only compared.
- **Work is never deleted unasked (tampering).** Files in the task's copy that are not on its branch (what the checks wrote after Botbench committed, or tracked files changed since) go with the copy. A decision is refused with 409 and the list while there are any, until the request carries `removeLeftovers` with exactly that list, which the client sends only from the dialog that showed it. A file that appeared after the dialog opened makes the lists differ: the decision is refused and the new list shown (tested). Files git ignores (dependency folders, caches) are not counted. Messages and the log name at most 20 files and say how many more; the decision row stores them all.
- **One decision, recorded (repudiation).** A decision is one row of `decisions` (migration 12): decided by the owner, accept or reject, branch kept or deleted, the branch name and commit, the files removed, the time. Triggers refuse updating or deleting it, refuse a row for a task that is not ready for review, and refuse moving a task to accepted or rejected without its row (tested). Each decision is also an `owner_accepted` or `owner_rejected` entry in the append-only action log, shown on Permissions → Activity. Two requests for one task at once: one is made and the other refused (tested).
- **A half-made decision (denial of service).** The worktree is removed before the branch is deleted, and the decision is written only after both. If the branch still cannot be deleted after those checks, the task stays ready for review with its copy gone, says so, and a second reject finishes the job (a missing copy is forgotten, not an error; tested). The task screen then shows only that its changes cannot be read from the copy; saying plainly that the copy is gone is left for later.
- **A run's end.** A run is done once none of its tasks is left to decide and at least one was decided; a run whose every task failed or was stopped stays at Ready for review, as unit 13 left it.

### Confined commands (U27)

New boundary B8 (ADR 0002, step 1). Before this unit a command the owner allowed, a pre-approved or standing one, and every setup and check command ran with the owner's rights anywhere on the machine; measured on 2026-11-22, such a command could read Claude Code's sign-in from the Keychain. Now each runs confined. Claude Code 2.1.322 on macOS 27.2; every key below was checked against the settings reference (code.claude.com/docs/en/settings-reference, sandboxing) and against the CLI by experiment.

**An agent's commands.** Every Claude Code attempt (a task's builder, a run's planner, a chat turn) is started with Botbench's one settings object on the command line (`--settings`, with `--setting-sources ""` for an attempt in a worktree), holding:

- `sandbox.enabled: true` and `sandbox.failIfUnavailable: true`: every shell command, and every process it starts, runs under macOS Seatbelt, and the CLI refuses to start rather than run commands unconfined.
- `sandbox.autoAllowBashIfSandboxed: false`. Critical: with `true` (the CLI's default before 2.1.324; this Mac runs 2.1.322) a sandboxed command runs without a permission prompt and the bare `Bash` ask rule is skipped, so Botbench's gate would silently disappear. Live-tested: with the sandbox on, every shell command of a task still became a request to the owner, and each ran only after its allow (`test/live/sandbox.live.test.ts`, `e2e/sandbox.e2e.ts`).
- `sandbox.allowUnsandboxedCommands: false` and no `excludedCommands`: the model's `dangerouslyDisableSandbox` is ignored, and no command runs outside the sandbox. A call that carries that field is not a plain command to the gate either, so no grant lets it through without a card.
- `sandbox.filesystem.denyRead`: `~/.claude`, `~/.claude.json`, `~/.codex`, `~/.grok`, `~/.gemini`, `~/.antigravity`, `~/Library/Application Support/Antigravity`, `~/Library/Keychains`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config/gcloud`, `~/.azure`, `~/.kube`, `~/.docker`, `~/.netrc`, `~/.npmrc`, `~/.config/gh`, `~/.git-credentials`, `~/.config/git/credentials`, the token files of common registries and tools (`~/.pypirc`, `~/.cargo/credentials{,.toml}`, `~/.gem/credentials`, `~/.m2/settings.xml`, `~/.gradle/gradle.properties`, `~/.terraform.d`, `~/.vault-token`, `~/.pgpass`, `~/.yarnrc.yml`, `~/.config/op`, `~/.password-store`, `~/.config/configstore`), shell history (`~/.zsh_history`, `~/.bash_history`), the old data folder `~/.smelt`, a sign-in folder moved with `CLAUDE_CONFIG_DIR` or `CODEX_HOME`, and Botbench's data folder, each as a full path and, where a link leads elsewhere, where it leads too (one list, `src/confinement.ts`, shared with setup and check commands).
- `sandbox.filesystem.allowRead`: the attempt's own folder, by its real path. A task's copy and the chat folder lie inside the denied data folder. Seen on 2.1.322: with the deny alone the copy was unreadable to its own commands (and still writable); with the narrower allow added, the copy is readable and writable and the rest of the data folder (login token, database, broker socket, other tasks' copies) is not. Other tasks' commits stay readable through the repository's shared git folder (below). The sandbox settings reference says the narrower entry wins; the experiment and the live test confirm it.
- `sandbox.filesystem.denyWrite`: the repository's shared git folder, for a task's copy and the planner's, found by asking git in the source repository the task was started on, never in the copy (whose `.git` file an agent can rewrite). For a linked git worktree the sandbox would otherwise open that folder for writes; seen on 2.1.322, a command could then create a branch in the owner's repository. With it, `git status`, `git log` and `git diff` still work in the copy, and `git add`, `git commit` and `git branch` by the agent fail. Botbench makes the task's commit itself, outside the sandbox. Live-tested: the agent's `git branch` fails and no branch appears in the owner's repository.
- `sandbox.network.allowedDomains`: the repository's `allowedHosts`, none by default; `sandbox.network.strictAllowlist: true`, so a host outside the list is refused rather than put to a prompt (honoured from `--settings`, per the sandboxing guide). No local binding, no Unix socket.
- `sandbox.credentials.envVars`: `BOTBENCH_BROKER_SOCKET` and `BOTBENCH_BROKER_SECRET` denied, so no command sees the gate's address or secret; the hook, which runs outside the sandbox, still has them. Live-tested.
- `permissions.blockReadsOutsideWorkingDirectories: true`: Claude Code's own file tools (Read, Glob, Grep, and the LSP tool), which run outside the sandbox, refuse every read outside the attempt's folder in every permission mode, before the hook or a prompt is reached. Live-tested: a Read of a decoy in the data folder is refused with no card, for a task and for a read-only attempt as the planner is started. The same key also closes the rest of the home folder to sandboxed commands, apart from the folder, the CLI's temporary folder, parts of `~/.claude` the CLI needs (skills, plugins), the repository's shared git folder and the owner's global git configuration (`~/.gitconfig`, `~/.config/git/{config,ignore,attributes}`), which the CLI re-opens so git keeps working.

The planner's commands reach no network whatever the repository allows; a chat turn's neither.

**Setup and check commands.** Botbench runs them itself, so Claude Code's sandbox does not apply. Each runs as `sandbox-exec -p <profile> /bin/sh -c <command>` (`src/engine/stations.ts`, profile from `src/confinement.ts`): everything is allowed except opening apps through LaunchServices and sending Apple Events (`(deny lsopen)`, `(deny appleevent-send)`: a review found, and an experiment confirmed, that without them `open` of an app the command wrote starts it through launchd with the owner's full rights; tested), reading the same list of places (the copy is opened again by a later rule; seen on macOS 27.2 that a later rule wins, and that the folders above the copy must be allowed metadata reads, not listing, for git to resolve its path); writing anywhere but the copy, a temporary folder made for the command and removed after it (`TMPDIR`), and the terminal devices; and all network, unless the repository allows hosts. Then the command may reach one local port, Botbench's own proxy, started for that command on 127.0.0.1 and closed after it, and the proxy variables point at it. The proxy opens a tunnel (HTTP `CONNECT`) only to an allowed host name, on any port, and refuses a name that resolves to a loopback, unspecified or link-local address, an address given directly, and any plain request. A name that resolves to one of the Mac's own network addresses or a private range is let through, as an intranet host the owner allowed may lead there. So hosts are filtered by name for these commands too, as for an agent's. Seen on this Mac: the rules hold for child process trees; with the network denied a name does not resolve; `npm ci` fails when npm's cache in the home folder cannot be written, and passes with `npm ci --cache "$TMPDIR/npm-cache"` and `registry.npmjs.org` allowed (live-tested), and fails without the allowance. The commands get the allowlisted environment a CLI child gets (`src/drivers/launch.ts`): no provider key variable, no `GIT_*` variable, the owner's own proxy settings replaced. Where `/usr/bin/sandbox-exec` is missing or the system is not macOS, a setup or check command is not run and has failed, with the reason in its output.

Writes from setup and check commands are stricter than an agent's: not even the repository's shared git folder or the home folder's caches. Reads are looser: only the listed places and the data folder are closed to them, not the rest of the home folder, because the owner's own toolchains often live there (a version manager's `node`, `~/.cargo`). A credential kept anywhere else in the home folder is readable to them, and a check could write it into the copy, where an agent's next turn would read it; the screen beside the check results says they can read the rest of the home folder.

**The per-repository network allowance** is `repositories.<path>.allowedHosts` in the owner's settings file, a list of plain host names such as `registry.npmjs.org`: lower case, at least two labels of letters, digits and `-`, no wildcard, no address, no port, no scheme or path, not `localhost`. Anything else stops Botbench at start with a message naming the file, the repository, the setting and the value; the driver checks again before a host reaches the command line. No route or screen writes it. A host allowed is allowed for that repository's builder commands and its setup and check commands.

**When the sandbox cannot run.** The driver's probe asks first: on anything but macOS, or without `/usr/bin/sandbox-exec`, Claude Code is reported as not usable, with the reason, and no attempt starts (a task fails, a chat turn is refused with that sentence). The same holds when Claude Code has managed settings on this Mac (`/Library/Application Support/ClaudeCode/managed-settings.json`, `managed-settings.d`, `managed-mcp.json`, or the `com.anthropic.claudecode` preferences file a device-management profile leaves): they come before `--settings` and could set `autoAllowBashIfSandboxed`, exclude commands or allow hosts. An attempt folder whose path holds `*`, `?` or `[` is refused too, as the read block then does not reach sandboxed commands. Should the CLI itself then refuse to start (`failIfUnavailable`), the turn ends with "Claude Code did not start: its sandbox cannot run on this computer (...), and Botbench does not let an agent run commands without it. Nothing was run." That stderr text is taken from the CLI's own code; it was not seen, because this Mac's sandbox works.

**Reporting a refusal.** A tool result whose output holds the CLI's `<sandbox_violations>` block (`deny network-outbound example.com:443 ...`), macOS's "Operation not permitted", or the CLI's own read rule, carries `confined` (hosts, files) in the transcript. The task screen says so on the call's line ("kept from the network", "kept from a file"), opens it, and says in plain words what the output says, with the output and the technical details below. This is read from the output, which the command also writes: a program can print the block or the phrase itself. It is a report, and Botbench decides nothing on it. A file refusal of the CLI's read rule with no hook in front of it (a chat turn) is said as "The agent may read only the folder it works in."

**What the confinement does not cover**, stated exactly:

- **The CLI itself, its hooks and MCP servers** run outside the sandbox with the owner's rights. Botbench gives the CLI no settings file of anyone's, no MCP server, and one hook of its own; a future MCP server or plugin would run unconfined. The CLI's web tools (web search, and fetch where the CLI offers it) are not limited by the sandbox's network list; they go to the owner through the gate.
- **A secret a command prints reaches the model provider** in the transcript, as everything a tool returns does. The control is that the secret cannot be read; there is no second one.
- **Network filtering is by host name only.** Neither Claude Code's proxy nor Botbench's looks inside the encrypted connection. A command allowed to reach a broad host (for example `github.com`) can send anything there, and domain fronting can reach other hosts behind the same front. Allow as few, and as narrow, hosts as the repository needs.
- **Places not on the list.** An agent's commands cannot read the home folder outside their folder; files elsewhere on the machine that the owner's account can read (`/tmp`, `/etc`, `/opt`) stay readable to them; `/Volumes` is closed by the read block. Setup and check commands can read the home folder apart from the listed places. A credential the owner keeps somewhere else (a project `.env` in another folder, a password manager's export) is readable by setup and check commands, and by an agent's commands outside the home folder.
- **The task's own copy is fully writable**, its `.git` file included, and so is a temporary folder. Whatever a command writes into the copy is committed by Botbench unless the repository ignores it.
- **The repository's shared git folder is readable** to an agent's commands (the sandbox re-opens it so git works): its `config`, where a remote URL can carry a token, every object, the owner's stashes, and other tasks' branches. Denying its `config` would stop git. So are the owner's global git settings.
- **A process a setup or check command leaves behind** with `setsid` stays confined but outlives the command and can still write the copy until Botbench commits or removes it.
- **The per-user temporary folder** (`/private/var/folders/.../T`, where setup and check commands get their own folders) is readable to an agent's commands, which may read the temporary folder of a setup or check command running at the same time.
- **macOS Seatbelt is deprecated** by Apple, though every vendor CLI relies on it, and both mechanisms here depend on it. Only macOS is supported: elsewhere nothing an agent would run is started.
- **The Keychain** is closed by denying `~/Library/Keychains`; the `security` command then cannot find the item (exit status 44, tested with an attribute lookup that never decrypts the item). Other ways a process can reach the Keychain service were not explored.
- **Managed settings from a server.** Botbench refuses to start an agent when a managed settings file or profile is on the Mac, but does not detect server-managed settings of a Team or Enterprise login, which could set `autoAllowBashIfSandboxed: true` (then no shell command would ask; the driver's watch stops the attempt after the first one that ran unasked), exclude commands or allow hosts.
- **Other CLIs.** This unit confines Claude Code only; no other driver exists yet (ADR 0002: a driver that cannot do this is offered for read-only roles only).

### Moving an installation from before the rename (Smelt to Botbench)

The product was called Smelt. On start, before anything opens the store, an installation in the old default folder `~/.smelt` is moved to `~/.botbench` (`src/store/move-home.ts`). No new boundary is crossed: the files moved are the owner's own data folder, and git runs only `worktree repair`, against repositories the store already names as task sources, with the same safe options and time limits as every other git call.

- **Nothing is lost or duplicated (tampering, denial of service).** The folder and the database (journal files first) are renamed, never copied or deleted; a rename is atomic on one file system and keeps the owner-only modes. Only when no variable names the data folder is the old default a candidate, so a test or a second instance with its own `BOTBENCH_HOME` can never move the owner's data. If both folders exist the new one is used and the old one is left as it is. A move that fails stops the start and says what to do; a start stopped half-way is finished by the next one (a marker holding the old path moves with the folder).
- **Git's links follow the folder.** Stored worktree paths under the old folder are rewritten to the new one, and `git worktree repair` points each source repository's record and each worktree's `.git` file at the new place; until that has succeeded the marker stays and each start tries again, because a `git worktree prune` against a stale record would cut a task's copy off from its repository.
- **Old names for one release.** `SMELT_HOME`, `SMELT_PORT`, `SMELT_CONFIG` and a git-ignored `smelt.local.json` are read when the new names are absent, each with a line on stdout; the new names win. The old `smelt_session` cookie is not a session: a browser that holds only it is signed out.

## What can still run without the owner (U7)

Stated exactly, for a task's attempt on Claude Code 2.1.322:

- **Edits and reads inside the worktree** run without asking, by design. Edits are logged before they run; reads are not logged. Writes to anything named `.git` or `.claude` at any depth, also through a link, are sent to the owner, and so is a search whose pattern is absolute or contains `..`.
- **Shell commands** never run unasked, except the ones the owner pre-approved for that task's run when starting it (U9) and the ones the owner gave standing permission and has not taken back (U10). Both are logged before they run.
- **Other tools** (web search and fetch, sub-agents, scheduling and messaging tools the CLI ships) are sent to the owner by the hook. If the hook fails for such a call (it crashes, or takes more than 20 seconds because Botbench is stalled), the CLI's own default applies to that one call, and for a tool the CLI runs without a prompt that means it runs. The ask rule covers only `Bash`. Narrowing the CLI's tool list is the fix; it was not part of U9 and is still open.
- A command the owner allows, pre-approved or gave standing permission runs in Claude Code's sandbox (U27): it cannot read the vendor sign-ins, the Keychain, keys, cloud credentials, Botbench's data folder or the rest of the home folder, can write only the worktree and a temporary folder, and reaches the internet only at hosts the repository's settings allow. Within that it runs with the owner's rights. Measured on 2026-11-22 before U27: such a command could read a vendor sign-in from the Keychain; with U27 the same lookup fails (live-tested). What the confinement does not cover is listed under "Confined commands". One container per task (U28) is the next step.

## Open items, most serious first

1. Checks run agent-written code on the host. Since U27 they are confined (no sign-ins, keys, Botbench files or network but allowed hosts, writes only to the worktree), but they can read the rest of the owner's home folder and print it into evidence. The owner should point Botbench only at repositories they trust. Confinement rests on deprecated macOS Seatbelt and works on macOS only.
2. The stop-on-API-key guard is untested on its failing path.
3. Sign-in slow-down is global, sessions never expire, and there is no sign-out.
4. Any signed-in client can start turns in Botbench's scratch directory with every tool prompt denied. Those turns are not behind the gate (U7 gates tasks only): there, "denied" still means what Claude Code itself would have asked about, so commands it classes as read-only run in the scratch directory unasked. Since U27 those commands run in the same sandbox as a task's, with no network.
5. On a failure of the pre-tool hook, tools other than the shell fall back to the CLI's own defaults for that call (see "What can still run without the owner"). A CLI update that dropped Botbench's settings object would be noticed only after one shell command had run.
6. Across a restart (U8): an answer the owner stored is lost if Botbench stops again before it is applied (the task is then interrupted and says so), and so is the unanswered half of a task with two parked requests of which one was answered. After a resume the task screen shows only the resuming attempt's transcript, which opens with Botbench's own prompt under the label "You"; the earlier attempt's events stay in the store. If the resumed agent does not repeat its call, the stored answer is discarded, never applied to something else. `stored_answer_applied` is logged before delivery: if the CLI dies in that instant the answer is spent and nothing ran.
7. The repository's instructions are handed to the CLI in a file in an owner-only temporary directory, removed when the CLI process exits. A Botbench that is killed outright leaves that copy behind. The text goes in as appended system prompt, which is more weight than the CLI gives the file when it reads it itself.
8. Two plan scenarios have no test: a command the owner's personal CLI settings allow (not testable without changing the owner's own settings; covered by the argument check that no settings file loads), and the driver's handling of a cancelled or duplicate permission request (reached only with a live CLI).
9. A task cannot be stopped from the client and has no time limit; stopping Botbench interrupts it and commits its work.
10. A planner and a builder have no time limit of their own: the owner cancels the run. A stale `single` run row is written for every task started on its own; it carries no state. Setup commands run outside the gate, confined (see "Confined commands"); a process that leaves its group escapes the time limit, though not the confinement.
11. Interception for Codex, Gemini CLI and Grok is unproven; a driver without it is limited to read-only roles.
